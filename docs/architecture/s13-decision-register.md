## §13 Decision Register

Each entry records the decision, its rationale, and — where an alternative was seriously considered — the disqualifying flaw.

<a id="d-001"></a>D-001 — libSQL as dependency, not fork (0.1.0). [Doctrine I](s0-s3-foundations.md#doctrine-i). Forking inherits a C codebase and an upstream merge burden; the project has two engineers. Every capability we need — WAL, JSON1, window functions, ATTACH, user_version, F32\BLOB, DiskANN — is in the public, stable surface.

<a id="d-002"></a>D-002 — transaction_log replaces CDC (0.2.0). [Doctrine IV](s0-s3-foundations.md#doctrine-iv). The WAL and replication frame log are engine-owned: truncated, compacted, checkpointed at the engine's discretion. A ledger built on them inherits their lifecycle. An ordinary table with an ordinary index has a retention policy we own. Rejected: CDC consumption — the frames can vanish beneath us.

<a id="d-003"></a>D-003 — 5-column bitemporal PK on links (0.2.0). The 4-column key (source, target, type, valid_from) cannot express re-assertion after mistaken retirement without mutating history. Adding recorded_at makes every assertion a distinct row. [Doctrine III](s0-s3-foundations.md#doctrine-iii).

<a id="d-004"></a>D-004 — links_current materialization (0.2.0). Latest-belief resolution via window function inside every traversal hop would tax every query forever. A trigger-maintained materialization moves the cost to write time (one upsert per assertion) and makes traversals index-simple. The WHERE excluded.recorded_at > links_current.recorded_at clause makes out-of-order inserts unable to roll belief backward. Cost: a second structure — auditable and rebuildable ([Doctrine VI](s0-s3-foundations.md#doctrine-vi), [§5.8](s5-modules.md#58-integrity--audit-and-rebuild)).

<a id="d-005"></a>D-005 — Per-model embedding tables (0.2.0). A shared F32_BLOB(768) column would hold mixed dimensions during a model migration; per-model tables make migration additive. [Doctrine VII](s0-s3-foundations.md#doctrine-vii).

<a id="d-006"></a>D-006 — AttributeMode with log hydration (0.3.0-A). The honest price of [§4.4](s4-schema.md#44-asymmetric-versioning-deliberately)'s asymmetry: Current / AtTime / Omit, with a runtime warning when Current meets as_of. Rejected: a concepts_current twin — a permanent join tax on every hop.

<a id="d-007"></a>D-007 — Byte-budget cost model for vector-filter strategies (0.3.0-A). Strategy selection by estimated bytes touched, not by rule of thumb; estimates logged so tuning is empirical.

<a id="d-008"></a>D-008 (revised 0.5.3) — Archive guard via main.sqlite_master probe. SQLite forbids a trigger in main from referencing objects in another database, temp.sqlite_master included; the restriction is enforced by the trigger compiler at CREATE TRIGGER time, so the original 0.4.0 design fails during migration and never reaches runtime. The guard instead probes main.sqlite_master for a marker table macrame_archive_session, created as the first statement and dropped as the last statement of the single archive transaction ([D-012](s13-decision-register.md#d-012)). Connection-locality — the property the temp probe was reaching for — is preserved by two independent mechanisms: uncommitted DDL is visible only to the writing connection, so no other connection ever sees the marker; and the archive transaction holds the write lock for its duration, so no other connection can reach the guard at all. The marker cannot outlive the transaction: commit drops it, rollback discards it, and there is no crash path that leaves the guards disarmed — which is structurally stronger than the temp marker, which would have persisted on the Write Actor's connection had the archive code ever failed to drop it. One behavioural shift: an ad-hoc DELETE issued during an archive transaction receives SQLITE_BUSY (lock contention) rather than ArchiveViolation (trigger abort). The outcome is identical — the delete is blocked — and the busy error is arguably the more informative of the two. Note also that BEFORE DELETE is a row trigger: a DELETE against an empty guarded table fires nothing and succeeds trivially, which is harmless because it removes nothing. Rejected: temp.sqlite_master probe (engine restriction, unimplementable); a persistent marker in main created and dropped in separate transactions (opens a window in which ad-hoc deletes from any connection are permitted — a [Doctrine V](s0-s3-foundations.md#doctrine-v) violation).

<a id="d-008a"></a>D-008a — Concepts carry an unconditional delete guard (0.5.3). Because concepts are never physically archived ([D-022](s13-decision-register.md#d-022)), there is no session in which deleting a concept row is legal. trg_concepts_guard_delete therefore has no WHEN clause and no marker probe: it aborts every physical delete unconditionally. Physical concept removal for legal compliance remains out of scope and outside the archive path ([Appendix C](appendices.md#appendix-c--future-considerations-deliberately-deferred)).

<a id="d-008b"></a>D-008b — transaction_log carries a delete guard (0.5.3). The archive path removes superseded log rows ([§5.7](s5-modules.md#57-temporalarchivers--cold-storage), Archive scope), so transaction_log is a hot table from which the archive session deletes — and [Doctrine V](s0-s3-foundations.md#doctrine-v) requires that every such table refuse deletes outside the session. The 0.4.0–0.5.2 DDL guarded concepts and links but left transaction_log unprotected, meaning the ledger itself was the one hot table an ad-hoc DELETE could truncate. It now carries the same marker-probing guard as links.

<a id="d-009"></a>D-009 — Reject the Mutex-wrapped shared write connection (0.4.5). A mutex serializes acquisition but not occupancy: a 50K-row transaction holds the file lock end-to-end, and the UI queues behind the whole job. The lock is held at the file-system level for the duration of a transaction; only bounded transactions plus controlled succession can cure it. Rejected: tokio::sync::Mutex, read-write lock variants (same occupancy problem).

<a id="d-010"></a>D-010 — Two-tier biased channel over a generic priority queue (0.4.5). Two mpsc arms and biased select! give strict preemptive ordering at every transaction boundary with zero allocation and no dependency; a third tier is one arm away. Rejected: heap-based scheduler, per-command priority fields — machinery for a problem two tiers solve.

<a id="d-011"></a>D-011 — Cooperative chunking at 500–1,000 rows (0.4.5). The priority queue cannot preempt a running transaction; bounding chunk duration to 2–3 ms bounds UI latency to the same. Rejected: unbounded bulk commands (starvation), time-based slicing mid-statement (impossible — the lock is per-transaction).

<a id="d-012"></a>D-012 — Archive stays a single atomic transaction (0.4.5). Copy-then-delete must be atomic, or a crash between phases duplicates or loses rows; archive is therefore the one scheduled lock hold that exceeds a chunk, and it runs at idle ([R7](s11-s12-milestones-and-risks.md#r7)). Rejected: chunked archive with cross-chunk verification — not crash-safe.

<a id="d-013"></a>D-013 — rebuild_current on the high-priority tier (0.4.5). Drift repair is a corrective act triggered by audit; it must not queue behind analytics. It is a single millisecond-scale transaction, so the preemption is cheap.

<a id="d-014"></a>D-014 — Chunked writes are not transaction-time atomic; the atomic variant is explicit (0.4.5). Each chunk is a distinct learning event with its own recorded_at; reconstruct mid-write sees a prefix. Callers needing all-or-nothing visibility pay one stall, knowingly, via write_analytics_results_atomic. [Doctrine VIII](s0-s3-foundations.md#doctrine-viii) applied to the write path: fidelity is a parameter.

<a id="d-015"></a>D-015 — No automatic writer restart (0.4.5). A dead writer means a bug; a respawn would mask it and re-enter on a connection whose last-transaction state the caller cannot reason about. Containment (typed errors) plus reopen is the policy; tracing reports the death. Restart remains available as a recorded deferral ([Appendix C](appendices.md#appendix-c--future-considerations-deliberately-deferred)).

<a id="d-016"></a>D-016 — Withdraw transaction() from the public surface (0.4.5). A caller-held closure can hold the write lock for arbitrary time — the exact starvation 0.4.5 removes. Every normative operation in [Appendix A](appendices.md#appendix-a--public-api-normative) is expressed through typed methods; the BEGIN IMMEDIATE … COMMIT shape survives as the actor-internal unit of work.

<a id="d-017"></a>D-017 — Unify all identifiers to snake_case (0.5.0). The prior document mixed snake_case declarations with flatcase usage in primary keys, triggers, and prose — residue of multiple editing passes. One convention, declared in [§4](s4-schema.md#4-schema)'s preamble, enforced by review. Rejected: flatcase (loses word boundaries); quoting all identifiers (verbose, fragile, non-idiomatic).

<a id="d-018"></a>D-018 — recorded_at monotonicity trigger on concepts (0.5.0). [Doctrine II](s0-s3-foundations.md#doctrine-ii) requires the two clocks to be independent, but nothing in the 0.4.5 schema enforced this for concept updates. A BEFORE UPDATE trigger rejecting non-advancing stamps closes the gap at the engine level. This is a constraint, not a default. Rejected: application-level validation only (breakable by the next endpoint, script, or migration tool).

<a id="d-019"></a>D-019 — PRAGMA query_only = ON on read connections (0.5.0). The write-serialization guarantee was enforced by Rust ownership. query_only converts the ownership invariant into a runtime enforcement at the engine level. Cost: one pragma per connection open. Rejected: relying on ownership alone (defense in depth is cheap and permanent).

<a id="d-020"></a>D-020 — Rename "checkpoint" to "snapshot" for the application-level concept (0.5.0). SQLite uses "checkpoint" for WAL-to-main-file truncation. Two different operations sharing a name is a persistent source of confusion. The rename is cosmetic but permanent. Rejected: coexistence with disambiguation comments (comments rot; naming doesn't).

<a id="d-021"></a>D-021 — Explicit PRAGMA recursive_triggers = OFF (0.5.0). SQLite defaults recursive triggers to OFF, which is correct here. But relying on a default for a correctness property is fragile. Stating the pragma makes the dependency visible. Cost: one line in configure().

<a id="d-022"></a>D-022 — Concepts are never physically archived (0.5.1). The archive path targets only links (closed intervals) and transaction_log (superseded rows). Concepts remain in the hot database permanently, managed by retired (soft-delete) and valid_to (temporal expiry). Three structural reasons: (1) FK constraints on embeddings*.concept_id would be violated or require CASCADE, destroying embeddings; (2) F32_BLOB and DiskANN indexes are libSQL-specific and do not exist on the ATTACHed cold database; (3) concepts are entities, not intervals — they have no "closed" state analogous to a retired edge. The trg_concepts_guard_delete trigger remains as a safety net. Rejected: physical concept archival with embedding extraction (structurally infeasible without a custom serialization layer that [Doctrine I](s0-s3-foundations.md#doctrine-i) forbids); ON DELETE CASCADE on embeddings (silently destroys [Doctrine VII](s0-s3-foundations.md#doctrine-vii) artifacts).

<a id="d-023"></a>D-023 — rebuild_current() stays atomic; sizing note added (0.5.1). A chunked rebuild would create a window where links_current is partially populated, and concurrent traversals would silently omit edges — a correctness failure worse than a latency stall. The rebuild is therefore a single atomic transaction, and the lock-hold cost is documented ([§5.8](s5-modules.md#58-integrity--audit-and-rebuild)): ~500 ms at 100K edges, ~5 s at 1M, ~50 s at 10M. Operational guidance: run at startup or idle; in normal operation (triggers functioning), drift should be zero and rebuild should never be needed. The high-priority status is retained because it governs ordering (fix before the next analytics chunk), not urgency (fix before the user's next click). Rejected: chunked rebuild with a "rebuilding" flag blocking traversals (adds a second consistency mode to an already complex temporal model; the flag itself becomes a failure mode if the rebuild crashes mid-chunk).

<a id="d-024"></a>D-024 — seq_id is strictly monotonic, not gap-free (0.5.1). SQLite AUTOINCREMENT guarantees monotonicity and non-reuse, but a rolled-back transaction still increments sqlite_sequence, leaving a gap. **(Mechanism corrected in 0.5.4 — see [D-049](s13-decision-register.md#d-049). Measured against libSQL 0.9.30, a rollback also undoes the `sqlite_sequence` write, so the number is reused and no gap appears. Gaps are real all the same: the archive path deletes superseded rows from `transaction_log`, scattered through the sequence. The rule below stands; the reason given for it did not.)** The prior document's "strict, gap-free total order" claim was incorrect. All replay and delta-fold logic uses inequality comparisons (seq_id > :anchor), which skip gaps correctly. The prose is corrected and a gap-tolerance test is added ([§8](s6-s10-flows-to-dependencies.md#8-testing-strategy)). Rejected: application-level gap detection and backfill (adds complexity for a property the logic does not require; the inequality comparisons are already correct).

<a id="d-025"></a>D-025 — SystemClock monotonicity floor (0.5.1). SystemClock::now() returns max(wall_clock, last_issued + 1μs). On construction, it queries MAX(recorded_at) from the database and floors the interior state, so that a restart after an NTP backward correction cannot issue a timestamp older than the newest row. This guarantees that trg_concepts_monotonic_ra never rejects a legitimate update due to clock drift. FakeClock is monotonic by construction. Rejected: relying on the OS clock alone (NTP corrections can move the wall clock backwards; the monotonicity trigger would reject legitimate updates); disabling the trigger for the first update after restart (creates a [Doctrine II](s0-s3-foundations.md#doctrine-ii) violation window).

<a id="d-026"></a>D-026 — Cold-database read path via per-query ATTACH (0.5.2). When reconstruct(ts) targets a ts older than the hot log's horizon, the replay module ATTACHes the archive database on read_conn, folds a UNION ALL of main.transaction_log and cold.transaction_log with the identical window-function query, then DETACHes. ATTACH/DETACH bracket exactly one fold and never persist, so no file handle is held between calls and a moved cold file cannot leave a stale handle. The hot entry wins for entities present in both files because its seq_id is greater — the same last-writer-wins rule as snapshot composition. If the cold file is absent, the module returns a typed ReplayCorrupt rather than a wrong answer ([R14](s11-s12-milestones-and-risks.md#r14)). Rejected: a persistent ATTACH at open() (holds a file handle for the process lifetime and fails hard if the archive is moved); merging cold rows into the hot log before folding (defeats the purpose of archiving and re-inflates the hot file).

<a id="d-027"></a>D-027 — Strict SystemClock timestamp parsing with graceful fallback (0.5.2). SystemClock::new() parses MAX(recorded_at) with a strict in-crate parser for the exact format the crate produces (YYYY-MM-DDTHH:MM:SS.ffffffZ, plus second-precision backward compatibility), rejecting offsets and missing Z. On parse failure it falls back to SystemTime::now() with a tracing::warn! — never a startup panic; the monotonicity trigger ([§4.3](s4-schema.md#43-the-transaction-log)) prevents a corrupt stored timestamp from propagating into new writes. SQLite's lexicographic MAX() is safe because [§4.1](s4-schema.md#41-concepts-and-per-model-embeddings) mandates a single fixed UTC Z format. (Corrected in 0.5.4: as written in 0.5.2 this was not true. [§4.1](s4-schema.md#41-concepts-and-per-model-embeddings) mandated a Z suffix but no fixed width, and mixed-precision values do not order lexicographically — see [D-029](s13-decision-register.md#d-029). The claim holds only under the canonical form 0.5.4 introduces.) Rejected: chrono/time dependency (one call site does not justify the dependency); panicking on parse failure (a corrupt row must not make the database unopenable); accepting arbitrary ISO-8601 (this is a crate-internal format; strictness catches corruption early).

<a id="d-028"></a>D-028 — Timeout is not cancellation on the write path (0.5.2). A HighPriCommand awaiting its oneshot responder waits in Rust, not in SQLite, so busy_timeout does not bound it; during an in-flight rebuild_current() or archive() transaction the caller stalls for that transaction's duration while WAL readers remain unaffected. Every write method's rustdoc states this and shows the tokio::time::timeout pattern. Dropping the responder does not cancel the command — it remains queued and commits when the actor yields; for a ledger, an asserted fact is asserted whether or not anyone is still listening. True abandonment is an application-layer CancellationToken checked before send. Rejected: crate-level command cancellation (would require the actor to dequeue and discard, adding a failure mode — a "cancelled" command that actually ran — for a property the ledger does not want); making busy_timeout the documented bound (it does not apply to channel waits and would mislead callers).

<a id="d-029"></a>D-029 — Canonical timestamp form: fixed width, not merely a Z suffix (0.5.4). [Doctrine II](s0-s3-foundations.md#doctrine-ii). Every temporal column is exactly 27 characters, YYYY-MM-DDTHH:MM:SS.ffffffZ, enforced by a table-level CHECK (GLOB) on concepts, links, links_current, and transaction_log. The prior rule — "ISO-8601 text with an explicit Z suffix, because they must sort lexicographically" — named the right requirement and specified an insufficient mechanism. Two values that differ only in precision do not order lexicographically: '2026-01-01T00:00:00Z' <= '2026-01-01T00:00:00.000000Z' is FALSE, since 'Z' (0x5A) sorts after '.' (0x2E). Every comparison in the system is lexicographic — SQL valid-time predicates, the traversal CTE's join condition, MAX(recorded_at) in SystemClock::new(), Rust str ordering in Interval — so the defect's blast radius is the whole temporal surface, and its failure mode is silence: a traversal whose edges all fail the predicate returns the anchor node alone, with no error to attribute it to. This manifested as a real test failure (a 3-node traversal returning 1) once the schema first installed successfully. The sentinel widens to 9999-12-31T23:59:59.999999Z for the same reason: an exempt value is a carve-out that reintroduces the bug, and the all-nines form is also the maximum representable instant, which is what [valid_from, valid_to) requires. Enforcement is at the storage layer because the failure is silent — a convention cannot be violated loudly, a CHECK can. util::timestamp::normalize() widens the legacy second-precision form at the boundary; offsets, missing Z, and other precisions are typed errors. Rejected: normalizing only in Rust (leaves every raw SQL path, migration, and external tool free to write mixed precision — and the crate's own test suite was exactly such a path); comparing via SQLite datetime() (reintroduces the ambiguous type [§4.1](s4-schema.md#41-concepts-and-per-model-embeddings) exists to avoid, and defeats index use); keeping the second-precision sentinel as a special case (the carve-out above).

<a id="d-030"></a>D-030 — audit_current() counts the symmetric difference (0.5.4). [Doctrine VI](s0-s3-foundations.md#doctrine-vi). The 0.4.5–0.5.3 query chained four compound-SELECT arms flatly: A EXCEPT B UNION B EXCEPT A. SQLite gives EXCEPT and UNION equal precedence and evaluates them left-associatively, so this parses as (((A EXCEPT B) UNION B) EXCEPT A), which reduces to a constant zero — the audit reported "no drift" for every possible state of the database, including a links_current deliberately corrupted by the test suite. An integrity check that cannot fail is worse than no integrity check, because it is trusted. Parentheses do not fix it: SQLite rejects a parenthesised compound-SELECT operand outright. The corrected query names both sides as CTEs and computes each direction inside its own scalar subquery, summing the two — the grouping is then structural rather than syntactic, so no future edit can silently regroup it. Both directions are required: a row links_current lacks is a missed materialization, a row it holds that the projection does not is a stale or spurious one, and either alone is drift. Rejected: a one-sided EXCEPT (misses missed-materialization drift entirely); COUNT(*) equality between the two relations (equal cardinality with different contents reports clean).

<a id="d-031"></a>D-031 — format_iso8601_utc and parse_iso8601_utc are real implementations (0.5.4). The 0.5.2 skeleton stubbed both: the formatter hard-coded a literal date and derived only the time-of-day from the SystemTime, so every stamp the crate produced claimed the same calendar day regardless of the clock; the parser validated the Z suffix and then returned SystemTime::now() unconditionally, so SystemClock's monotonicity floor ([D-025](s13-decision-register.md#d-025)) was seeded with wall-clock time rather than with MAX(recorded_at) and the restart-after-NTP-correction guarantee did not hold. Both are now implemented over Hinnant's civil-calendar algorithm in util::timestamp — around sixty lines, no chrono dependency, consistent with [D-027](s13-decision-register.md#d-027)'s rejection. The parser validates the calendar as well as the shape, so 2026-02-30T00:00:00.000000Z is rejected rather than accepted as a timestamp no round-trip can reproduce; :60 is rejected because SystemTime counts SI seconds and has no slot for a leap second, and aliasing it to :59 would break the strictly-increasing clock contract. Rejected: leaving the stubs pending a chrono dependency (the monotonicity floor is a doctrinal guarantee, not a nicety).

<a id="d-032"></a>D-032 — Legacy-free schema baseline at user_version = 2 (0.5.4). Macrame is pre-1.0 and declares no on-disk compatibility: there is no migration path into the canonical form, only a baseline that applies to an empty database. The baseline is numbered 2 rather than 1 because builds before 0.5.4 stamped user_version = 1 over the pre-canonical schema — no CHECK constraints, second-precision timestamps, the narrow sentinel. Had the canonical baseline reused the number 1, such a file would open silently and every guarantee [D-029](s13-decision-register.md#d-029) buys would be void on it while user_version insisted all was well; reserving 1 as a value the ladder refuses by name is what makes "no legacy support" an enforced property rather than a README sentence. migrations::run() reads user_version before writing anything and refuses three cases with a typed DbError::Migration: a version greater than this build's (operating on a schema you do not understand is how a ledger loses history); a version with no rung leading out of it, which is exactly the pre-0.5.4 v1; and an unstamped database that already holds objects, since user_version defaults to 0 and an unrelated SQLite file is otherwise indistinguishable from a fresh one. Each rung runs in one BEGIN IMMEDIATE transaction with the version stamp inside it, so "the schema exists" and "the schema is declared to exist" are the same commit and a crash mid-step leaves a database still honestly at its old version. A post-condition check counts the objects sqlite_master actually holds against what the DDL arrays declare, because CREATE … IF NOT EXISTS hides precisely the failure that matters: an object that exists with a different definition is silently kept. Rejected: retrofitting the canonical form by table rebuild (correct engineering for a released system, unjustifiable ceremony for a pre-1.0 crate with no deployed data — and the rebuild's two traps, sqlite_sequence continuity under AUTOINCREMENT and the [D-008](s13-decision-register.md#d-008) delete guards, are failure modes bought for nothing); accepting v1 databases unchanged (silently voids [D-029](s13-decision-register.md#d-029)); a no-op version guard without a ladder (the mechanism is needed the first time the schema moves, and building it against a single known rung is cheaper than retrofitting it under pressure).

<a id="d-033"></a>D-033 — One classification boundary for engine error text (0.5.4). SQLite reports a RAISE(ABORT) as a generic constraint failure carrying the message, so the message text is the only thing distinguishing "you violated the single-open-interval rule" from "the disk is full". error::abort_kind() is the sole place in the crate that matches on engine error text; classify() turns an AbortKind plus a WriteOp into the typed error [§7](s6-s10-flows-to-dependencies.md#7-errors) specifies, **Update (Wave 1, 2026-07-30): archive::classify_archive_violation is deleted.** It delegated correctly and was called from nowhere, so DbError::ArchiveViolation was unconstructible by any path in the crate — logged as defect H, marked Fixed by the commit that made it delegate, and reopened as AC when a review found the delegation had not made it *called*. classify() with WriteOp::Delete already produced the identical error from the identical AbortKind, so the redundant classifier was removed and archive()'s two DELETEs routed through classify(). This decision's own rule is what settled it: one classification boundary means one, and "delegates rather than carrying a second copy of the needle" was a weaker property than this decision was reaching for — the second function was still a second place a caller had to know about. The needles themselves are the schema::ddl::ABORT_* constants spliced into the trigger DDL by concat!, so the guard and its classifier are the same string by construction, with a unit test asserting each constant appears in some trigger. Scattered string matching fails silently in the worst direction: an upstream wording change degrades an unknown number of typed errors into opaque Engine errors that no caller can match on, and nothing announces it. Concentrated, a change breaks one function and the tests covering it. classify() takes a connection because RecordedAtRegression reports the value it clashed with and the trigger does not put it in the message — one extra query on an error path buys an error a caller can act on. Rejected: matching at each call site (the failure above); parsing SQLite extended result codes instead (a RAISE(ABORT) carries SQLITE_CONSTRAINT_TRIGGER for every guard, so the code cannot tell them apart).

<a id="d-034"></a>D-034 — Write commands carry typed payloads, not SQL strings (0.5.4). The 0.4.5 skeleton declared WriteBulkAtomic { rows: Vec<String> } and the chunked background commands as Vec<String>. Whatever those strings were meant to be, the only thing an actor can do with a Vec<String> is execute it, which makes the write channel an arbitrary-SQL channel: it bypasses edge-type validation, timestamp canonicalisation ([D-029](s13-decision-register.md#d-029)), and every typed error [§7](s6-s10-flows-to-dependencies.md#7-errors) defines, and it means the sole write connection will execute whatever any caller in the process hands it. The commands now carry EdgeAssertion and ConceptUpsert values, validated and canonicalised at the public boundary before they cross the channel, so a malformed edge type or a second-precision timestamp is a typed error at the call site rather than an engine CHECK failure surfacing from the far side of an actor with no context attached. HighPriCommand::execute and LowPriCommand::execute are exhaustive matches with no wildcard arm — the pre-0.5.4 `_ => LoopCtl::Continue` dropped the responder for four of six high-priority and all three low-priority commands, and a dropped responder is indistinguishable from a hung database from the caller's side. Exhaustiveness makes that a compile error rather than a runtime silence; Database::high()/low() additionally map a send failure to WriterUnavailable and a dropped responder to WriterDroppedResponder, so the actor going away is a typed error rather than a wait that never ends. Rejected: keeping Vec<String> with a validation pass over the strings (validating SQL by inspecting it is the problem, not the solution); a WriterUnavailable stopgap for unimplemented arms (correct while arms are missing, but all nine are now implemented and exhaustiveness is the stronger guarantee).

<a id="d-035"></a>D-035 — Archive re-derives links_current instead of describing the deletion's shadow (0.5.4). [Doctrine II](s0-s3-foundations.md#doctrine-ii), [Doctrine VI](s0-s3-foundations.md#doctrine-vi). archive() deletes from links under LINKS_ARCHIVABLE and must leave links_current equal to the latest-belief projection of what remains. As written in 0.5.2 it did so with a hand-written compensating statement, DELETE FROM links_current WHERE valid_to <> sentinel AND valid_to <= :cutoff — a predicate over *valid* time standing in for one that also requires recorded_at < :cutoff. The two are not the same set. An interval closed at the cutoff but recorded at or after it fails LINKS_ARCHIVABLE and survives in links, while the compensation deletes it from links_current: permanent drift, produced by the archive path itself, that no later audit can explain and only a rebuild can clear. The compensation is now integrity::rebuild::rebuild_within(&tx), executed inside the archive transaction, so the materialization is re-derived from the definition rather than from a second description of it. A description of a set can drift from the set; a derivation cannot. The same commit made rebuild_current() transactional in its own right — it had been a bare DELETE followed by an INSERT, and the window between them is the whole of current belief, so a failure across it (or a concurrent reader landing in it) sees a graph with no edges and no error, contradicting [D-023](s13-decision-register.md#d-023)'s atomicity claim in the code that claimed it. Found by property test, not by inspection: the defect requires a cutoff that separates an interval's valid time from its transaction time, and every seeded test in the suite used a cutoff comfortably after both. Rejected: adding recorded_at < :cutoff to the compensating DELETE (restores agreement today and reinstates the same failure mode — two predicates that must be kept identical by hand); auditing after the archive and rebuilding only on drift (the archive transaction has already committed by then, so the window is real, and a repair conditional on a check is only as good as the check).

<a id="d-036"></a>D-036 — 1.0 on-disk compatibility contract: core-frozen, periphery-rebuildable (0.5.4). Macrame 1.0 commits to strict on-disk backward compatibility for the normative ledger tables (concepts, links, transaction_log). Post-1.0 schema changes to these are restricted to additive operations: ALTER TABLE ADD COLUMN and new indexes. Changing a primary key, dropping a column, or altering bitemporal semantics is forbidden and requires a major version with an explicit ETL migration path. Bitemporal data is the hardest data to migrate: a changed links PK cannot be repaired by CREATE TABLE AS SELECT, because doing so means replaying history, re-resolving conflicting assertions, and recomputing transaction-time boundaries — an operation that rewrites the past, which [Doctrine III](s0-s3-foundations.md#doctrine-iii) forbids. Freezing the core also plays to SQLite's shape: ADD COLUMN is exact and cheap, while a table rebuild requires a temp table, drops and recreates every trigger attached to the original, and invalidates the WAL. Conversely, derivative tables — links_current ([Doctrine VI](s0-s3-foundations.md#doctrine-vi)) and the per-model embedding tables ([Doctrine VII](s0-s3-foundations.md#doctrine-vii)) — carry no schema-stability guarantee at all. A minor version needing a different materialization drops the table, recreates it from the DDL, and calls integrity::rebuild::rebuild_within() inside the same migration step transaction; a model change adds a new embeddings table and leaves the old one for the previous model. The bifurcation is exactly [Doctrine VI](s0-s3-foundations.md#doctrine-vi)'s "source-of-truth or rebuildable, there is no third category," applied to time rather than to structure.

Two mechanical premises were verified rather than assumed, both in tests/compat_contract_tests.rs. First, the additive escape hatch preserves [D-029](s13-decision-register.md#d-029): SQLite has no "add table constraint", so the table-level canonical_ts_check! covering today's columns cannot be extended, and an additive temporal column would have no canonical-form guard unless ADD COLUMN accepts a *column-level* CHECK. It does, and enforces it, and the ALTER leaves all nine triggers intact — so the rule is that any post-1.0 temporal column must carry its own inline CHECK, and the contract would otherwise have silently readmitted the mixed-precision ordering defect on a schema nobody is permitted to rebuild. Second, the periphery is genuinely disposable: dropping links_current entirely, recreating it from DDL, and rebuilding from links reproduces it byte for byte, which is the executable form of the claim that no information lives solely in the materialization. The frozen shapes themselves are pinned by PRAGMA table_info assertions — a change detector before 1.0, a release blocker after it.

Rejected: full on-disk compatibility including derivative tables (buys nothing — the tables are reconstructible by definition — and forfeits the ability to ever change the materialization strategy); no compatibility commitment at 1.0 (a ledger whose central promise is that the past is never rewritten cannot also reserve the right to rewrite the format the past is stored in — [D-032](s13-decision-register.md#d-032)'s legacy-free stance is correct precisely because it is pre-1.0, and it expires at 1.0); a single ladder arm per release with an `unreachable!()` default (the ladder must remain a loop that composes steps, and a panic on an unrecognised user_version turns an unfamiliar file into a crash instead of the typed DbError::Migration refusal [D-032](s13-decision-register.md#d-032) requires).

<a id="d-037"></a>D-037 — F32_BLOB dimension enforcement is carried by the vector index, not by the column type (0.5.4). [Doctrine VII](s0-s3-foundations.md#doctrine-vii). **This entry corrects [§4.1](s4-schema.md#41-concepts-and-per-model-embeddings), which was wrong.** The pre-0.5.4 text stated that libSQL rejects a wrong-dimension vector at insert time, and drew the conclusion that the crate-level check in embedding.rs "exists for error quality" while "the engine-level check exists for correctness". Measured against libSQL 0.9.30: a two-float blob inserted into a column declared F32_BLOB(4) is **accepted** when the table carries no vector index, and rejected — with the row not landing — once a libsql_vector_idx index exists, reporting "vector index(insert): dimensions are different: 2 != 4". Enforcement is therefore a property of the DiskANN index, not of the declared column type. Two consequences follow and both are now structural. First, register_model() creates the table and its index in one transaction and there is no supported way to have one without the other, because a per-model table without its index is a table with no dimension enforcement at all — which also means dropping the index to accelerate a bulk load silently disarms the only storage-layer check, and it must not be offered as an option. Second, the crate-level check is not merely cosmetic, so it had better be real: search_vector() previously called EmbeddingCodec::encode(query_vec, query_vec.len(), model), comparing the vector's length against itself, which made the check true by construction and DimMismatch unreachable through the search path. It now resolves the dimension by reading F32_BLOB(n) back out of PRAGMA table_info for the model's table. That is deliberate: the declared dimension in the schema is the single copy, so the Rust-side check and the engine-side one cannot disagree, and the crate holds no registry of its own to fall out of date — the same reasoning [D-035](s13-decision-register.md#d-035) applied to the archive's compensating delete. Both halves of the asymmetry are pinned by tests, including the negative one on an unindexed table; if libSQL ever begins enforcing the column type itself, that test fails and this entry should be revisited rather than quietly outgrown. Rejected: a macrame-maintained model registry table (a second description of a fact the schema already states, which is the drift [D-035](s13-decision-register.md#d-035) exists to prevent); trusting the declared type without the index (measured false); accepting the caller's asserted dimension (that is precisely the tautology being removed).

<a id="d-038"></a>D-038 — Migration verification checks for required objects by name, not by counting sqlite_master (0.5.4). The 0.5.4 verify() compared the number of tables, triggers and indices against expected totals and refused to open the database on any mismatch. The intent was sound — catch a CREATE … IF NOT EXISTS that no-ops instead of creating — but a total is the wrong instrument, because it treats every *extra* object as corruption. Three legitimate sources of extras now exist: a registered embedding model adds embeddings_<model> ([D-037](s13-decision-register.md#d-037)), libSQL's vector index adds libsql_vector_meta_shadow plus a shadow table and shadow index per model, and [D-036](s13-decision-register.md#d-036) explicitly permits post-1.0 migrations to add indexes. Under the counting check, registering a single model made a healthy database fail verification on its next open, with a message blaming the schema version. Verification now asserts the presence of each required object by name and reports exactly which are missing. The names are parsed out of the CREATE_TRIGGERS and CREATE_INDICES arrays rather than kept in a parallel list, so adding a trigger extends what verify() requires with nothing else to remember. Rejected: raising the expected counts (restores the bug the moment a second model is registered); excluding embeddings_% and %_shadow from the count (an allowlist of everything that may exist, maintained by hand, versus a checklist of what must exist — the latter is what the check is actually for); dropping verification (it is the only guard against IF NOT EXISTS silently no-opping).


<a id="d-039"></a>D-039 — Native graph analytics, dropping petgraph (0.5.4). [Doctrine I](s0-s3-foundations.md#doctrine-i). The in-memory analytics surface is exactly five algorithms — Dijkstra, A*, SCC, k-core, Louvain — over an adjacency list, and it is now owned in-crate. petgraph is rejected because the translation cost it was supposed to save was already being paid: SubgraphLoader built a HashMap<String, NodeIndex> by hand on the way in and mapped NodeIndex back to ULIDs on the way out, so the dependency bought a graph representation the crate immediately wrapped. Only four items of its surface were used (DiGraph, NodeIndex, algo::dijkstra, algo::tarjan_scc), Louvain was never among them, and a k-core and an A* over ULID keys had to be written regardless. Rejected: petgraph (a dependency whose entire used surface is smaller than the adapter around it); graaf (maturity risk for a pre-1.0 project); keeping petgraph solely for its track record (addressed below).

Three things this decision is honest about. First, what was replaced was not working code. `louvain_communities` assigned every node its own index and returned — the all-singletons partition, labelled "basic community detection" — so the fact it was named after an algorithm it did not implement is what made the gap invisible. Second, the guideline's proposed acceptance test for Louvain, that modularity be non-decreasing against the singleton partition, is satisfied by construction by exactly that stub; [§8](s6-s10-flows-to-dependencies.md#8-testing-strategy)'s oracle for Louvain is therefore an upper bound (modularity must not exceed the enumerated optimum over all set partitions) rather than a lower one. Third, replacing a well-used library forfeits its track record, and the substitute for that is differential testing rather than assurance: every algorithm is checked against an independent brute-force definition — exhaustive simple-path enumeration for Dijkstra and A*, an O(V³) reachability closure for SCC, recompute-from-scratch peeling for k-core, and enumeration of every set partition via restricted growth strings for Louvain. The oracles were confirmed to have teeth by mutation: `scc` with its second pass walking out_edges instead of in_edges — Kosaraju minus the transpose — is caught and shrunk to a two-node counterexample, which is kept in tests/graph_property_tests.proptest-regressions with a note recording that the defect never shipped.

Determinism is a property of the data structures, not of a sort applied at the end. Subgraph uses BTreeMap, the algorithms return BTreeMap/BTreeSet rather than the hashed equivalents, and every tie is broken explicitly — equal-distance heap entries by node id, equal-gain Louvain moves by the lower community index. Any one of the three left as a HashMap reintroduces per-process variation, and in Louvain's case a different partition run to run: Rust's default hasher is seeded per process, so a caller iterating a HashSet result to write it back emits rows in a different order every run. Distances additionally need a total order that f64 does not have; OrdF64 wraps total_cmp so a NaN weight cannot corrupt the heap's invariant silently.

Two defects in adjacent code were found while doing this and are fixed here. TraversalBuilder spliced edge types into the CTE as quoted literals via format!("'{t}'"), and validate_edge_type — whose own doc comment cited the CTE as its justification — runs only from EdgeAssertion::normalized on the write path, so a traversal never passed through it. Edge types are now bind parameters: unlike a table name, an edge type is a value, and values can be parameters, so the question is removed rather than answered (contrast [D-037](s13-decision-register.md#d-037), where a model name is an identifier and validation was the only option). And TraversalBuilder stored attribute_mode, exposed a builder method for it, and never read it — build_sql always emitted the Current join — so a caller asking for AtTime received live attributes with no indication the mode had been ignored, which is the silent wrong answer [Doctrine II](s0-s3-foundations.md#doctrine-ii) exists to prevent. Hydration now runs as a second step through the already-correct hydrate_attributes.

Two further gaps are recorded rather than closed. DbError::SubgraphTooLarge existed in the error enum but was constructed nowhere, so [D-007](s13-decision-register.md#d-007)'s byte budget was declared and unenforced; load_subgraph now measures during the load and both halves are tested. And links.weight is a bare REAL NOT NULL with no CHECK, while Dijkstra and A* are only correct for non-negative weights — a negative weight would yield a shortest path that is merely a path. Adding a CHECK constraint is a schema change against the [D-036](s13-decision-register.md#d-036) freeze and is not taken unilaterally; load_subgraph refuses such an edge with a typed NegativeEdgeWeight instead, which puts the failure at the boundary. Whether the constraint should also exist in the schema is open.

<a id="d-059"></a>D-059 — The superlinearity is diagnosed: both paths are superlinear in the size of the **structure being probed**, not in chunk size — and on the edge path that is a wrong-index defect that also slows every interactive assertion on a high-degree node (0.5.5). [D-004](s13-decision-register.md#d-004), [D-036](s13-decision-register.md#d-036), [D-055](s13-decision-register.md#d-055), [D-058](s13-decision-register.md#d-058), [§4.2](s4-schema.md#42-links-assertion-history-and-current-belief-materialization), [§5.1.5](s5-modules.md#515-cooperative-chunking--the-golden-rule). Answers [D-058](s13-decision-register.md#d-058)'s open question and **corrects two of its claims**. Evidence: `examples/chunk_diag.rs`.

**The confound first, because it invalidates a claim I made rather than merely leaving one open.** [D-058](s13-decision-register.md#d-058)'s sweep measured each chunk size into a *fresh* database. Chunk size and table size were therefore the same variable, and reading the curve as a property of chunk size was not warranted by the measurement. Separating them: a **fixed** 90-row chunk committed into a hub that already has 0 / 2,000 / 8,000 edges takes **4.4 / 18.4 / 47.7 ms**. The cost is in the table, not the chunk.

**So [D-058](s13-decision-register.md#d-058)'s throughput claim is wrong.** It said 1,000 edges cost 88.5 ms as one chunk against ~27 ms as eleven 90-row chunks, a 3.3× speedup — computed as eleven times a 90-row chunk *into an empty database*. Measured end to end, with both arms finishing at the same 1,000-row table: **85.5 ms as one transaction, 94.7 ms as eleven chunks.** Chunking is ~11% *slower*, not 3.3× faster. Smaller chunks buy latency and cost throughput on every path, which is what [D-056](s13-decision-register.md#d-056) said before [D-058](s13-decision-register.md#d-058) contradicted it. The per-path constants and the 3 ms bound stand — those were measured directly, not extrapolated — but they are a trade again, and the entry claiming otherwise was reasoning from eleven measurements of the first chunk.

**The edge path: `trg_links_single_open` reads the wrong index.** Its guard is `EXISTS (SELECT 1 FROM links_current WHERE source_id = … AND target_id = … AND edge_type = … AND valid_from <> … AND valid_to = OPEN)`. The plan:

```text
SEARCH links_current USING COVERING INDEX idx_lc_traversal_cover (source_id=?)
```

**One** equality column. `idx_lc_traversal_cover` is `(source_id, valid_from, valid_to, weight, edge_type, target_id)` — [D-004](s13-decision-register.md#d-004)'s traversal-covering index — and because it happens to *contain* every column this predicate mentions, the planner takes it as covering and scans the whole `source_id` range, filtering `target_id` and `edge_type` row by row. The PK autoindex `(source_id, target_id, edge_type, valid_from)` would bind three columns but lacks `valid_to`, so it is not covering and loses. Every edge insert therefore costs **O(out-degree of its source)**, and a hub degrades quadratically: 90 rows into a 90,000-edge hub takes **1.06 s**.

Attribution is by isolation, not inference. Dropping the guard flattens the table-size curve completely — 2.4 / 7.4 / 7.4 ms against 4.4 / 18.4 / 47.7. An earlier arm that dropped `trg_links_current_sync` instead looked like it exonerated the guard, and it was worthless: with the sync trigger gone `links_current` is never populated, so the guard's `EXISTS` searches an empty table and is free for the wrong reason.

**Proof by fix.** `CREATE INDEX idx_lc_open_interval ON links_current (source_id, target_id, edge_type, valid_to, valid_from)` changes the plan to four equality columns and the cost to **8.0 ms at 8,000 and flat** — 5.5× at that size, unbounded improvement as degree grows. `valid_from` is in the index despite being a `<>` purely so the index stays covering; without it the planner keeps preferring the wrong one, which the first attempt demonstrated by changing nothing at all.

**This is not a chunking problem, which is the part that matters most.** The guard runs on every insert into `links`, so a single interactive `assert_edge` against a node with 90,000 out-edges pays the same scan. [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets)'s ≤ 5 ms single-assertion budget is met on an empty database and not on a large one. **Not fixed here**: an index is a schema change against [D-036](s13-decision-register.md#d-036)'s freeze and needs a migration rung, which is a decision rather than a diagnosis.

**The embedding path is the same shape and is not a defect.** A fixed 30-vector chunk into a corpus of 0 / 2,000 / 8,000 costs **49 / 168 / 224 µs per vector**; a single chunk of 30 / 250 / 1,000 into an *empty* corpus costs 43 / 108 / 129 µs. Both curves are the same phenomenon — DiskANN insertion traverses and rewires a graph that grows as the chunk fills it — and graph insertion getting dearer as the graph grows is what DiskANN *is*. There is no wrong index here and nothing to fix.

**What is left unexplained, stated precisely.** With the guard dropped, the `links_current` upsert still costs 25 µs/row in a 90-row chunk and 66 µs/row in a 1,000-row one, plateauing there. Ruled out: the commit (loop 61.5 ms vs commit 2.2 ms at n=1,000), the page cache (a 512 MB `cache_size` gives 64.8 against 65.7), the secondary indexes (dropping both is a constant-factor 1.5× and leaves the 2.4× growth intact), and table size (90 direct upserts into a `links_current` of 0 / 2,000 / 8,000 / 32,000 rows: 0.34 / 0.44 / 0.48 / 0.61 ms — essentially flat). What remains is the upsert's per-row conflict probe against an index growing *inside the open transaction*, which would make this the same structure-size story once more. Not confirmed.

**And a third correction to [D-058](s13-decision-register.md#d-058), which its own verification could not have caught.** `chunk_budget` seeds concepts and starts with **zero links**, so 2.39 ms for a 90-edge chunk is the empty-database figure. On a database with an 8,000-edge hub the same chunk takes 47.7 ms as shipped, or ~8 ms with the guard index — both outside the 3 ms bound. So the constants satisfy the rule on an empty database and not on a realistic one, the fixture is what needs fixing first, and re-deriving them requires picking a reference table size, which is a design question and not a measurement. Recorded as open; nothing is changed on the strength of it.

Rejected: shipping `idx_lc_open_interval` in this entry (a [D-036](s13-decision-register.md#d-036) schema change wants its own migration rung and its own test, and this entry is a diagnosis); rewriting the guard's `EXISTS` to defeat the covering-index preference instead of adding an index (fragile — it depends on planner behaviour rather than on an available access path, and the planner is free to change); dropping `idx_lc_traversal_cover` (it exists for traversal, which is a read path with its own budget); re-deriving the chunk constants against a preloaded fixture right now (the reference table size is a design decision, and guessing it would repeat exactly the mistake this entry is correcting).

**Fixture: `star_of_stars`, hub arm ([D-088](s13-decision-register.md#d-088), added 0.6.0).** The 2,000 / 8,000 / 90,000-edge "hub" the chunk figures are taken on is this shape's defining property, so unlike most entries annotated in this pass the measurement is on the shape it is the worst case for and the diagnosis stands as stated. What is still unmeasured is the *other* shapes' insert cost: `clustered` and `dense_small` have out-degrees of 12 and 299 against the hub's hundreds of thousands, so the probe they provoke is a different size of probe, and nothing here says by how much.

<a id="d-058"></a>D-058 — §5.1.5's golden rule is re-derived: it is a bound on duration, `CHUNK_ROWS` becomes four measured constants, and on two of the four paths smaller chunks are faster in total (0.5.5). [D-011](s13-decision-register.md#d-011), [D-014](s13-decision-register.md#d-014), [D-055](s13-decision-register.md#d-055), [D-056](s13-decision-register.md#d-056), [D-057](s13-decision-register.md#d-057), [§5.1.5](s5-modules.md#515-cooperative-chunking--the-golden-rule), [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets). Closes the re-derivation [D-056](s13-decision-register.md#d-056) opened and [D-057](s13-decision-register.md#d-057) sharpened.

**The rule was never a row count.** [§5.1.5](s5-modules.md#515-cooperative-chunking--the-golden-rule) exists because the SQLite write lock is not preemptible: the biased poll picks who goes *next*, so an interactive assertion queued behind a background chunk waits that chunk out in full. What the rule requires is that the wait be short — a **duration** — and `CHUNK_ROWS = 1000` was an answer to it, stated as if it were the rule. Restating it as [`CHUNK_BUDGET`] = 3 ms with a per-path row count derived from measurement is the whole of this entry. 3 ms is [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets)'s own figure, kept rather than renegotiated; end to end it puts a worst-case interactive write at 3 ms of queueing plus its own ≤ 5 ms, inside a 60 Hz frame.

**The measurement §5.1.5 never took.** `chunk_scaling` in `benches/budgets.rs` sweeps n ∈ {1, 10, 50, 100, 500, 1000} across all four bulk paths. The model being fitted is `T(n) = f + c·n`, and it needed fitting rather than assuming: 37 ms at 500 rows is equally consistent with a 35 ms fixed cost and a 4 ms one, and those imply opposite chunk sizes. Median durations, in ms:

| n | edges | concepts | annotations | embeddings |
|---|---|---|---|---|
| 1 | 0.90 | 0.86 | 0.72 | 0.77 |
| 10 | 1.00 | 1.13 | 0.76 | 1.08 |
| 50 | 1.63 | 1.80 | 1.07 | 3.73 |
| 100 | 2.70 | 3.12 | 1.16 | 9.77 |
| 500 | 36.8 | 12.4 | 2.28 | 67.4 |
| 1000 | 88.5 | 23.6 | 3.48 | 143 |

**Three of §5.1.5's quantitative claims are wrong, and they fail in different directions.**

*One constant cannot express one duration across four paths.* The bottom row is the refutation on its own: the same `CHUNK_ROWS` produced 3.5 ms, 24 ms, 89 ms and 143 ms. Per-row costs span 60× — an annotation at ~2.5 µs against an embedding at ~150 µs — because the four write to tables carrying no triggers, an FTS5 pair, the two ledger triggers, and a DiskANN index respectively. So `CHUNK_ROWS` is replaced by `chunk_rows::{EDGES, CONCEPTS, ANNOTATIONS, EMBEDDINGS}` = **90, 70, 600, 30**, each verified at its own size by the new `chunk_budget` group: **2.39, 2.35, 2.36, 2.06 ms**, no upper estimate above 2.42.

*Per-transaction overhead is not noise — it is 0.8 ms, over a quarter of the bound.* A one-row chunk costs 0.72–0.90 ms on every path, and the flatness of that figure across four different tables is what identifies it as BEGIN/COMMIT/fsync rather than row work. §5.1.5 asserts this "amortizes to noise" at 500–1,000 rows, which is true and beside the point: it means only ~2.2 ms of the 3 ms is ever available to rows, which is what makes the sizes above as small as they are. It is also a floor — below ~30 rows a chunk spends more time in overhead than in work — so the rule is bounded on both sides, which the original states nowhere.

*And the throughput-for-latency trade does not exist on half the paths.* Marginal cost per row on the edge path rises from ~11 µs at n=10 to ~103 µs at n=1,000, and on the embedding path from ~35 µs to ~151 µs. Both are **superlinear**, so for both the old 1,000-row chunk was the worst latency *and* the worst throughput simultaneously: 1,000 edges cost 88.5 ms as one chunk against ~27 ms as eleven 90-row chunks — **3.3× faster in total for a 37× lower stall**. [D-056](s13-decision-register.md#d-056) recorded this decision as "a throughput-for-latency trade that is a §5.1.5 design decision" and deferred it on those grounds; on two of four paths there was nothing to trade, and the deferral was protecting a cost that does not exist. The trade is real on the two linear paths (concepts ~23 µs/row, annotations ~2.5 µs/row), where these sizes do give up a few percent, and that is the part that was a decision.

**Sized for the tail, not the median.** The first pass solved `f + c·n = 3 ms` exactly and produced 100/90/800/30, measuring 2.70/2.93/2.94/2.09 ms with upper estimates at 2.96 — inside the bound as reported, outside it for any chunk slower than typical. A latency bound is a claim about the chunk an unlucky write actually queues behind, not about the median one, so the constants solve for ≈2.5 ms and keep the rest as headroom. On the superlinear paths that headroom is free.

**Two things this corrects in my own earlier entries.** [D-056](s13-decision-register.md#d-056) computed "~40 rows for a 3 ms bound" from the 74 µs/row implied by the 500-row measurement. That extrapolation was wrong because it assumed the linearity this sweep disproves — marginal cost at n≈90 is ~22 µs/row, not 74, so the answer is 90. And [D-056](s13-decision-register.md#d-056) concluded the ≤ 3 ms budget was "unreachable by construction" since the *un-amplified* 500-row commit alone takes 2.96 ms. That conclusion holds only at 500 rows. The budget is reachable, fully amplified, at 90 — what was unreachable was the pairing of a duration with a row count, and [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets) had been reading as though both were requirements.

**Open: the superlinearity is unexplained.** Two paths cost 4–9× more per row at n=1,000 than at n=10, and this entry does not say why. Both maintain a secondary structure per row and the shape is consistent with dirty pages spilling to the WAL mid-transaction, but neither is confirmed, and confirming it matters beyond chunk sizing — if it is WAL spill it is a function of page-cache size and every one of these constants is really a function of `PRAGMA cache_size`. The re-derivation stands either way, because it rests on measured durations rather than on a mechanism.

Rejected: keeping one constant and setting it to the smallest of the four (30 rows) — correct on latency, and it would throw away 10× the transaction overhead on the annotations path for no reason; expressing the sizes as a runtime calibration measured at startup (attractive, and it turns a `PRAGMA`-dependent constant into a measured one — but it makes chunk boundaries, and therefore [D-014](s13-decision-register.md#d-014)'s fidelity boundary, vary run to run, which is a worse property than a stale constant); renegotiating the 3 ms bound now that it is known to be achievable (the number was never the problem); gating the four `chunk_budget` measurements in CI ([D-055](s13-decision-register.md#d-055)); leaving `CHUNK_ROWS` in place as a deprecated alias (there is no value it could hold that is right for any path, and a wrong constant that still compiles is how this survived four cycles).

[`CHUNK_BUDGET`]: s5-modules.md#515-cooperative-chunking--the-golden-rule

<a id="d-057"></a>D-057 — The other three bulk paths get the same statement hoist, and the numbers say the edge chunk was the *least* affected of the four (0.5.5). [D-011](s13-decision-register.md#d-011), [D-041](s13-decision-register.md#d-041), [D-048](s13-decision-register.md#d-048), [D-055](s13-decision-register.md#d-055), [D-056](s13-decision-register.md#d-056), [§5.1.5](s5-modules.md#515-cooperative-chunking--the-golden-rule). Closes the carve-out [D-056](s13-decision-register.md#d-056) rejected keeping in that change.

| embeddings (`upsert_embeddings`) | 73.4 ms | **67.4 ms** | 8% |
| edges (`bulk_import`), from [D-056](s13-decision-register.md#d-056) | ≈62 ms | ≈37 ms | 41% |

**The spread is the finding, and it inverts the intuition [D-056](s13-decision-register.md#d-056) was reasoning from.** That entry explained the edge chunk's 41% by noting that `links` carries two triggers, so each preparation compiles their bodies too — implying the effect scales with how much trigger work hangs off the table. It does not. `analytics_annotations` carries *no* triggers at all ([Doctrine VI](s0-s3-foundations.md#doctrine-vi)'s third category, deliberately outside the ledger) and still gave back 54%; `concepts` with its FTS5 trigger pair gave 65%; the embedding tables, whose DiskANN index maintenance is the largest per-row cost in the table above, gave 8%. Preparation cost is roughly *constant per row* and what varies is the work it is being compared against — so the saving is largest where the row itself is cheapest, which is the opposite of the trigger-count reading. The honest summary is that the edge chunk's 41% was mid-range, and it looked explanatory only because it was the only one measured.

**Two things the table settles that were open.** The annotations row is the control this project did not previously have: 2.13 ms for 500 un-triggered upserts, ≈4.3 µs per row, agreeing with [D-056](s13-decision-register.md#d-056)'s trigger-free edge diagnostic at 2.96 ms and confirming that figure was measuring the engine rather than an artifact of the scratch database. And the embedding row shows where [D-048](s13-decision-register.md#d-048)'s chunking budget actually goes — at ≈135 µs per vector, DiskANN maintenance dwarfs everything else in this entry, so an embedding chunk is the one bulk path where `CHUNK_ROWS` at 1000 is *far* outside any interactive latency bound. That is the same open question [D-056](s13-decision-register.md#d-056) left on §5.1.5, now with a second and much larger data point attached; it is still not decided here.

The concepts path no longer routes through `upsert_concept`, which prepares per call by construction. To keep the two from drifting into different column sets, the statement text and its parameter row are shared as `UPSERT_CONCEPT` and `concept_params` — the single-row path binds through the same two. Error classification is unchanged in all three: the concepts chunk still runs `classify` with `WriteOp::Concept` before rolling back, which is what made this worth doing as its own change rather than inside [D-056](s13-decision-register.md#d-056).

Rejected: leaving the embedding path alone because 8% is small (it is 6 ms per chunk on a path that runs over an entire corpus, and the change is three lines); benchmarking these against a restated SQL diagnostic as [D-056](s13-decision-register.md#d-056) did for triggers (unnecessary — these go through the public API, so the number is what a caller gets, and the before/after came from measuring the pre-change code directly); lowering `CHUNK_ROWS` for the embedding path only (a per-path chunk size is a real option and a bigger decision than this entry, and it belongs with the §5.1.5 re-derivation).

<a id="d-056"></a>D-056 — The chunk commit prepares its statement once; the residual is trigger amplification, and §9's ≤ 3 ms budget is the *un-amplified* figure (0.5.5). [D-011](s13-decision-register.md#d-011), [D-014](s13-decision-register.md#d-014), [D-055](s13-decision-register.md#d-055), [Doctrine IV](s0-s3-foundations.md#doctrine-iv), [§5.1.5](s5-modules.md#515-cooperative-chunking--the-golden-rule). Acts on the one row [D-055](s13-decision-register.md#d-055) measured as missing.

**The defect, and it was real.** `write_edges_atomic` called `tx.execute(INSERT_LINK, …)` once per row, and libsql's `execute` prepares on every call. `links` carries two triggers, so each preparation compiled their bodies along with the insert — 500 preparations per chunk. Hoisted to one `tx.prepare` outside the loop, with `reset()` between rows because libsql's `execute` binds and steps without resetting. **≈62 ms → ≈37 ms at 500 rows, a 41% saving**, measured with [D-055](s13-decision-register.md#d-055)'s harness.

**And the first diagnosis was wrong about magnitude, which the same harness caught.** [D-055](s13-decision-register.md#d-055) named statement preparation as the suspect and this entry's own first draft called it "most of the chunk". It was 41%, not most. Isolating the rest by dropping `trg_links_log_insert` and `trg_links_current_sync` on a scratch database: the same 500-row commit takes **2.96 ms**. So trigger amplification is **~92% of the remaining 37 ms**, and `trg_links_log_insert` building a JSON payload per row — `json_object(…)` including `json(NEW.properties)`, which parses and re-serialises — is the bulk of it.

**The consequence for §9 is the interesting part: 2.96 ms is almost exactly the ≤ 3 ms budget.** §9's preamble states "Trigger amplification is included: a single edge assertion produces three writes", and the measured un-amplified cost lands on the budget to within 1%. The most economical explanation is that the number was derived from an insert without its triggers and then labelled trigger-amplified. That makes the budget unreachable by construction, not by defect: the only way to hit it is to stop writing the ledger entry, which is [Doctrine IV](s0-s3-foundations.md#doctrine-iv).

**So §5.1.5's golden rule needs re-deriving, and this entry does not do it.** The rule is that a chunk must be short enough that an interactive write waits no longer than the bound; the tunable is `CHUNK_ROWS`, not the trigger. At ~74 µs per amplified row, a 3 ms bound implies chunks of roughly 40 rows rather than 500 — a throughput-for-latency trade that is a §5.1.5 design decision with [D-014](s13-decision-register.md#d-014)'s fidelity boundary attached, not a constant to quietly edit. Recorded as open with the numbers attached so whoever takes it is choosing rather than guessing.

Rejected: editing §9's budget to match the measurement (a budget revised to whatever the code does is not a budget); dropping or simplifying the log trigger's JSON payload ([Doctrine IV](s0-s3-foundations.md#doctrine-iv) and [§4.3](s4-schema.md#43-the-transaction-log) require the payload, and `reconstruct` folds it); lowering `CHUNK_ROWS` here (the right answer may well be that, and it is a decision with throughput consequences that belongs with whoever owns the latency bound); hoisting the prepared statement in the other bulk paths in the same change (`write_annotations`, the analytics chunk and the embedding chunk share the shape and should get the same treatment — kept separate because each carries its own error classification and none of them is the row §9 measures).

<a id="d-055"></a>D-055 — [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets)'s budgets are measured, and deliberately not CI-gated; the chunk-commit row misses by 20× (0.5.5). [D-011](s13-decision-register.md#d-011), [D-042](s13-decision-register.md#d-042), [D-047](s13-decision-register.md#d-047), [§5.1.5](s5-modules.md#515-cooperative-chunking--the-golden-rule), [§8](s6-s10-flows-to-dependencies.md#8-testing-strategy). §9 has carried a table of targets since 0.4.0 asserting "these budgets are CI gates", and until this entry no criterion harness existed and nothing measured a single row. `benches/budgets.rs` covers twelve of them.

**They measure; they do not gate, and that contradicts §9's own wording on purpose.** The numbers are stated for named reference hardware. CI is not that machine, so `≤ 5 ms` in a gate is an assertion about whichever runner took the job — and this project's position on that class of red is already on record twice: the R15 quarantine note ("a suite that fails for reasons unrelated to the code under test trains people to ignore red") and [D-047](s13-decision-register.md#d-047)'s growth test, which asserts a ratio because "absolute timings are a property of the machine, the growth rate is a property of the algorithm". The mechanism that *is* sound compares a machine against itself, which is what criterion baselines do; a hardware-independent gate belongs in `tests/` as an assertion about shape, where [D-042](s13-decision-register.md#d-042) and [D-047](s13-decision-register.md#d-047) already live. Fixture sizes are reduced by default and scale with `MACRAME_BENCH_SCALE`, because §9's 1M-entry and 10M-edge rows cost minutes of construction each; every bench names the row it stands for so the shortfall is visible rather than implied. The cadence ([D-053](s13-decision-register.md#d-053)) is disabled in every fixture — a background task folding state mid-measurement is noise landing in whichever sample it overlaps.

**Eleven rows pass with room; one misses by 20×, and it is the one holding up an argument.** `Chunk commit, 500 rows, trigger-amplified` measures ≈62 ms against ≤ 3 ms. That row is [§5.1.5](s5-modules.md#515-cooperative-chunking--the-golden-rule)'s golden-rule calibration — the figure [D-011](s13-decision-register.md#d-011)'s two-tier design cites when it promises the actor yields promptly at chunk boundaries. At 62 ms an interactive assertion arriving behind a chunk waits twenty times longer than the design claims. Diagnosed but **not fixed here**: `write_edges_atomic` calls `tx.execute(INSERT_LINK, …)` per row, so each of 500 rows re-prepares a statement whose plan includes both of `links`'s triggers. Hoisting a prepared statement is the next move, kept separate because instrumenting and optimising in one change leaves neither reviewable — and because the harness that would verify the fix is the thing being added.

**The first version of the chunk benchmark measured its own fixture.** It reused one database and appended 500 edges per iteration, so the last iteration committed into a table tens of thousands of rows larger than the first. The tell was the spread — `[296 ms … 780 ms]`, 2.6×, where every other row in the file is flat to a few percent, and a stable operation does not do that. `iter_batched` fixes it properly: setup is untimed, so every iteration commits into an identically-shaped database, and the spread closed to 2.6% at ≈62 ms. Worth recording because it is the same failure as the retention fixture one entry earlier and the chunk-merge test two before that — a measurement that moves while being taken is the benchmark equivalent of a test that asserts nothing, and the *variance* was what exposed all three.

Rejected: gating absolute durations in CI (§9's literal instruction, and unimplementable honestly on hardware that is not the reference machine); building §9's stated sizes by default (minutes per group, so nobody would run it); putting the budgets in `tests/` as `assert!(elapsed < …)` (the same hardware problem with worse ergonomics); fixing the chunk-commit path in this entry (see above).

**Fixture: `star_of_stars` ([D-088](s13-decision-register.md#d-088), added 0.6.0).** Every one of the twelve §9 rows measured here was taken on `benches/budgets.rs`'s chain-of-stars and on nothing else — which is the single largest instance of what D-088 exists to make visible, because §9's table is the project's public statement of what it costs. The `fixture_matrix` group added in 0.6.0 measures the load row across all four shapes at comparable coverage and finds a **77×** spread; the §9 figure is the cheapest of the four. The other eleven rows remain single-shape.

<a id="d-054"></a>D-054 — Snapshot retention gains its daily tier, and the container header gains the snapshot's own instant (0.5.5). [D-036](s13-decision-register.md#d-036), [D-043](s13-decision-register.md#d-043), [D-053](s13-decision-register.md#d-053). [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots) has specified "the last five plus one daily for thirty days" since 0.4.0; the implementation was newest-five-flat, and [D-046](s13-decision-register.md#d-046) recorded the divergence without acting on it.

**It was harmless until [D-053](s13-decision-register.md#d-053) and then it was not.** Through 0.5.4 a snapshot was written once per clean shutdown, so five anchors were five shutdowns — days or weeks of coverage — and the daily rule bought nothing anybody would notice. A cadence writes one every 10,000 log entries, so under load five anchors can span *minutes*: every instant older than that falls back to folding the whole log, which is exactly the cost snapshots exist to avoid. The flat rule went from harmless to defeating the feature that had just been added, which is why this follows immediately rather than waiting.

**The header grows, and that is a second copy of something the payload already holds.** `MaterializedState.timestamp` is the instant a snapshot reflects; the header now carries it as microseconds since the epoch. This codebase normally refuses exactly that ([D-030](s13-decision-register.md#d-030), [D-035](s13-decision-register.md#d-035), [D-047](s13-decision-register.md#d-047) are all about a second description drifting from the first), so the exception needs its reason: retention has to bucket *every* snapshot by day, and the alternative is decompressing and deserializing a full state per file on every pass — making the cadence's own maintenance cost more than the work it exists to save. Eighteen bytes read without touching zstd is what a versioned header is *for* ([D-043](s13-decision-register.md#d-043)). The copy cannot drift, because both are written from the same value in the same statement and nothing rewrites a snapshot in place.

**The format bump costs nothing new.** `SNAP_FORMAT_VERSION` goes 1 → 2, so snapshots written by earlier builds are refused. That is already the established behaviour for a *schema* change, and the `v4 → v5` FTS rung ([D-051](s13-decision-register.md#d-051)) had just invalidated every snapshot on the same rule. Refusal is graceful by construction — [D-043](s13-decision-register.md#d-043)'s `SnapshotIncompatible` is skipped rather than raised, the fold answers from the log, and the cadence writes a fresh anchor within one interval.

**"Today" is the newest snapshot's own day, not the wall clock.** Retention is then a function of the directory's contents and nothing else — deterministic, testable, and safe for a database left untouched for a year, which would otherwise have its entire history deleted by the first write after it wakes up. A snapshot whose header carries no readable instant survives only under the newest-five rule: it is a file this build would refuse to *load*, so keeping it for its date would be keeping it for a date nothing will ever use.

**A fixture bug caught by the mutation pass, worth recording because it is the third of its kind this cycle.** The retention tests built timestamps with `format!("2026-01-{:02}", day + 1)`, which produces `2026-01-41` past day 39 — shape-valid, calendar-invalid, and correctly refused by `parse`. Those snapshots landed with *no* instant in their header, so two tests were exercising the dateless path while claiming to test the daily one, and one passed for the wrong reason. Rebuilt on epoch arithmetic. Mutations then verified the two tiers separately: dropping the daily tier fails three of the four retention tests and leaves `retention_orders_by_sequence_not_by_filename` green, which is correct — that one pins the newest-five rule, which the mutation does not touch.

Rejected: file mtime as the date source (a genuine second description, wrong after any copy or restore, and the payload already knows the answer); loading each snapshot during retention (correct and unaffordable at cadence frequency); putting the date in the filename (changes the naming contract `seq_from_filename` and the retention ordering both rest on).

<a id="d-053"></a>D-053 — The snapshot cadence is implemented, and its lifecycle is settled (0.5.5). [D-011](s13-decision-register.md#d-011), [D-019](s13-decision-register.md#d-019), [D-049](s13-decision-register.md#d-049), [§5.1.5](s5-modules.md#515-cooperative-chunking--the-golden-rule), [§5.1.7](s5-modules.md#517-shutdown-and-snapshot-coordination). Closes [D-049](s13-decision-register.md#d-049)'s second carve-out. [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots) had specified "written every 10,000 log entries… a lightweight maintenance task watches `seq_id`", and only `close()` ever wrote one — so a cleanly-shut-down application composed from its shutdown anchor while a long-running session accumulated an unbounded delta, and [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets)'s "≤ 200 ms with snapshot" described a mechanism that ran once, at exit.

**The specified design is honoured: read-side, not write-side.** Everything the task does is a fold plus a file write, so it never touches the write connection and cannot lengthen the actor's loop — which is the point, because [§5.1.5](s5-modules.md#515-cooperative-chunking--the-golden-rule)'s latency bound is a property of how long that loop takes. The rejected alternative, writing an anchor from the actor at a chunk boundary, cannot miss a threshold but taxes every write to buy that.

**The lifecycle, which is what was actually left open.** *Owner:* `Database` spawns it in `open()` and holds the `JoinHandle`. *Stop signal:* a `watch` channel; dropping the sender also stops the task, so a handle that is dropped rather than closed does not leave it running against a connection whose database is going away — which matters because [§7.3](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor) leaves `close()` merely conventional and there is still no `Drop` impl. *What `close()` does:* stops the cadence and joins it **before** stopping the actor and taking the final snapshot. Both the cadence and `write_final` end by running retention, which deletes files; overlapping them means one pass enumerating the directory while the other removes from it, and a final anchor that a cleanup begun earlier could delete. Stopping the cadence first leaves exactly one writer at each step.

**A distance, not a schedule.** The trigger is `MAX(seq_id) - last_anchor >= every_entries`, so an idle database writes nothing however long it stays open. A time-based cadence would rewrite an identical snapshot forever and call it maintenance. `poll_interval` is how often that distance is *checked*, and it is an implementation cost rather than a property — the check is an index lookup on an integer primary key — which is why §5.5 does not specify it and this entry does.

**Two smaller choices.** The task anchors at `MAX(recorded_at)` rather than the clock's `now()`: the two differ by however long it has been since the last write, and anchoring later than anything the snapshot reflects would produce a file whose name and header claim an instant nothing in it corresponds to. And it shares `read_conn` rather than opening a third connection — `libsql::Connection` is an Arc-backed handle, and [R15](s11-s12-milestones-and-risks.md#r15) makes every extra local connection in one process a cost not worth paying for nothing.

**The stop test asserted nothing, and mutation is what said so.** The obvious form — close the handle, wait, check no new snapshot — passes whether or not the task is alive, because nothing is writing after `close()` and an idle task is indistinguishable from a stopped one. Verified by leaking the stop signal: that version still passed. The test now keeps the log growing after `close()` through a second handle with its own cadence disabled, so the only thing that could write an anchor is the task that should not exist; under the same mutation it fails with two snapshots where one was expected. Rejected: a `Drop` impl that aborts the task (`Drop` cannot await, so it cannot join, and [D-045](s13-decision-register.md#d-045) already declined that shape for the actor); a cadence measured in wall-clock time (rewrites identical snapshots on an idle database); leaving the cadence off by default (the delta it bounds is unbounded precisely in the long-running case nobody remembers to configure).

**Left open deliberately: retention is now load-bearing and is still "newest five, flat".** [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots) specifies "the last five plus one daily for thirty days", and until now the divergence cost nothing because snapshots were written once per shutdown. A cadence writes them continuously, so five anchors can span minutes and every older instant falls back to a full fold. That is a *cost* regression only — no answer changes, and reconstruction was already folding from genesis for those instants before this entry — but it is the next thing to look at, and it needs a source for each snapshot's date that the filename does not carry.

<a id="d-052"></a>D-052 — The archive read path is made sound: `hot_log_covers` was a reach test, not a completeness test, and composition now spans the boundary (0.5.5). [Doctrine II](s0-s3-foundations.md#doctrine-ii), [D-024](s13-decision-register.md#d-024), [D-026](s13-decision-register.md#d-026), [D-049](s13-decision-register.md#d-049). Closes [D-049](s13-decision-register.md#d-049)'s first carve-out, and fixes a **live wrong-answer defect** that carve-out had been sitting beside without naming as one.

**The defect.** `reconstruct(ts)` chose between the hot log and the cold file by asking `MIN(recorded_at) <= ts`. That is a question about how far back the hot log *reaches*; the question that matters is whether it is still *complete* at `ts`. `LOG_ARCHIVABLE` ([§5.7](s5-modules.md#57-temporalarchivers--cold-storage)) removes **superseded** rows, scattered through the sequence rather than forming a prefix, and one archived entity beside one unarchived entity is enough to separate the two questions. Reproduced through the public API: write `F` once and `E` three times, archive, then ask for belief at `E`'s second write. `F`'s single row is never superseded, so it survives and keeps `MIN` pointing before the cutoff; `E`'s winning row is in cold and its third row is later than `ts`. The fold ran over hot alone and **`E` vanished from the result entirely** — no error, no missing file, a state that had quietly forgotten a concept it was asked about. That is precisely the class [Doctrine II](s0-s3-foundations.md#doctrine-ii) exists to prevent, and it had been shipping.

**The sound test rests on the one guarantee the archive makes.** The newest row per entity is never archivable, because archivability *requires* a later row to exist. So if `ts` is at or after the newest hot stamp, every entity's winning row at `ts` is its newest row overall, and every such row is hot. That is exactly `reconstruct(now)` — the case [§5.7](s5-modules.md#57-temporalarchivers--cold-storage) designed `LOG_ARCHIVABLE` around — and nothing else. Anything earlier consults the cold file. Note what is *not* sound and was considered: `ts > MAX(recorded_at)` of the **cold** log fails, because an entity's rows can straddle that mark with the winner below it; and `ts >= cutoff` fails for the same reason, which is why no cutoff is persisted to make it work. With no archive in play the reach test *is* the completeness test — nothing has been removed — and it is kept, because it is also what distinguishes "before recorded history" from "the cold file is missing" ([D-026](s13-decision-register.md#d-026)).

**The cost is more ATTACHes, and the trade is not close.** Every reconstruction of an instant before current belief now opens the cold file once an archive exists. The old rule was cheaper because it was answering a question nobody asked.

**Composition follows for free.** With `ANCHORED_COLD_FOLD` unioning both files above the anchor, the reason [D-049](s13-decision-register.md#d-049) refused to compose across the boundary is gone rather than worked around — the archived row the delta needed is visible again. Rows keep their `seq_id` when they move, because the cold schema declares a plain `INTEGER PRIMARY KEY` precisely so history is not renumbered, so `seq_id > :anchor` partitions the two files consistently and [D-024](s13-decision-register.md#d-024)'s inequality rule binds across them.

**Two tests, and the second replaces one that pinned the workaround.** The regression test is written from the public API and fails on the shipped code before the fix. The acceptance gate is [D-049](s13-decision-register.md#d-049)'s shape extended to the carved-out case: composed must equal full-fold at instants on both sides of the cutoff, mutation-verified by folding the delta over hot alone, which fails at a pre-cutoff instant. The old `an_existing_archive_disables_composition` asserted the refusal itself, so it had to go — but its virtue is kept: the snapshot is still planted *wrong*, claiming a concept the database never had, because a test that only checked the answer was right could not tell composition from a silent fall back to the full fold. Rejected: persisting the archive cutoff to widen the hot-only fast path (unsound, as above, and it would have looked right); keeping the composition carve-out and fixing only `hot_log_covers` (the two are one mechanism, and the plan already said they should be looked at together).

<a id="d-051"></a>D-051 — Hybrid search is implemented; the FTS index is external-content, and arbitrary text never reaches the query language (0.5.5). [Doctrine VI](s0-s3-foundations.md#doctrine-vi), [Doctrine VII](s0-s3-foundations.md#doctrine-vii), [D-022](s13-decision-register.md#d-022), [D-036](s13-decision-register.md#d-036), [D-047](s13-decision-register.md#d-047). [Appendix A](appendices.md#appendix-a--public-api-normative).2 had listed `db.hybrid_search` among the operations that exist in no form: `reciprocal_rank_fusion` was a pure function over two rank lists, nothing produced the keyword half, and `grep -ci fts5 src/schema/ddl.rs` returned 0 while [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets) budgeted the path at ≤ 50 ms for top-10 over 100K concepts. The schema decision 0.5.4 declined to take is taken here: `concepts_fts` on a `v4 → v5` rung ([§4.6](s4-schema.md#46-the-concept-text-index--the-third-derivative-table-055-d-051)).

**External content, and the rebuild is the reason.** The table declares `content='concepts'`, so FTS5 stores the inverted index and reads column values back from the ledger by rowid. One copy of the text means the index cannot come to disagree with the concept about what the concept says; a standalone FTS table would be a second description of data the ledger already holds, which is what [D-030](s13-decision-register.md#d-030) and [D-035](s13-decision-register.md#d-035) were both about. It also makes [D-036](s13-decision-register.md#d-036)'s rebuildability the engine's own `'rebuild'` command rather than code of ours that could drift from the triggers it is supposed to reproduce — `Database::rebuild_fts()` is that one statement, on the low-priority tier because a search index a few seconds stale costs less than an interactive write queued behind a full reindex. The rung **backfills**, which the [D-041](s13-decision-register.md#d-041) rung could not: the index is a pure function of text the ledger already holds, so `'rebuild'` produces exactly what the triggers would have written had they always existed.

The price of external content is that it does not maintain itself. An `UPDATE` must retract the old terms using the **old** column values before inserting the new ones, and omitting that leaves an index still matching words the concept no longer contains — no error, no symptom, detectable only by searching for something that should be gone. Mutation-verified by deleting the retraction from `trg_concepts_fts_update`. There is deliberately no delete trigger, because [D-022](s13-decision-register.md#d-022)'s guard is unconditional and concepts are never physically deleted; that dependency runs the wrong way round to be noticed later, so it is recorded in [§4.6](s4-schema.md#46-the-concept-text-index--the-third-derivative-table-055-d-051) as well — a change to the *archive* would break the *search index*.

**Arbitrary text is escaped, and the default is the decision.** FTS5's MATCH is a language. Handing a search box to it fails twice over: a malformed expression raises `SQLITE_ERROR`, so a user who typed a query gets an exception, and — worse — a query containing `NOT` silently *means* something, excluding documents and returning a plausible wrong answer. Each run of alphanumeric characters therefore becomes one quoted term with implicit AND. `raw_match(true)` opts back in for a caller composing the expression themselves, and the test asserts that the flag genuinely bypasses the escaping, since an option that quietly did nothing would leave the guarantee resting on an untested branch.

**Fusing ranks rather than scores**, because cosine distance and BM25 are not comparable numbers and anything that adds them invents an unmeasured conversion. Depth defaults to `max(5 × top_k, 50)`: fusing two top-k lists is not the top k of the fusion, since a document ranked twelfth by *both* arms can outscore one ranked first by a single arm and is invisible if neither list was read past k. The acceptance test is that each arm returns something the other cannot — a rare term placed far away in vector space, and a paraphrase containing no rare term — and it asserts that each arm *alone* misses one of them, so "the fusion works" cannot be satisfied by a vector search that happened to rank everything.

One defect fixed in passing: `reciprocal_rank_fusion` sorted on the fused score alone, leaving ties to `HashMap` iteration order. Ties are the common case, because two documents at the same pair of ranks score identically by construction, so the same query could answer in a different order twice — [D-047](s13-decision-register.md#d-047)'s procedural-versus-structural determinism trap, arriving as a search result that will not sit still. Rejected: a standalone (non-external-content) FTS table (duplicates the text and makes the rebuild ours to write); weighted score fusion instead of RRF (requires a conversion between BM25 and cosine that nobody has measured); indexing `retired` into the FTS table to avoid the join (external content cannot, and the join is where the filter belongs anyway); passing MATCH through unescaped by default (the `NOT` case makes it a wrong-answer generator, not merely an error-prone one).

<a id="d-050"></a>D-050 — Filtered vector search is implemented, `TwoPhaseTempTable` is removed, and the strategy is forbidden from changing the answer (0.5.5). [D-007](s13-decision-register.md#d-007), [D-019](s13-decision-register.md#d-019), [D-037](s13-decision-register.md#d-037), [Doctrine II](s0-s3-foundations.md#doctrine-ii), [Doctrine VIII](s0-s3-foundations.md#doctrine-viii). [§5.3](s5-modules.md#53-graphvector_filterrs--strategies-and-the-byte-budget-cost-model) had specified three strategies, an enum with no execution bodies, and a `CostEstimator` that carried a `byte_budget` it never read while branching on `candidate_count` against two hard-coded thresholds — D-007's interface with none of its mechanism, the same shape as the pre-[D-039](s13-decision-register.md#d-039) Louvain.

**The third strategy is removed because the engine offers neither of its mechanisms, and both were measured rather than argued.** `CREATE TEMP TABLE` on `read_conn` fails with `SQLITE_READONLY (8)`: `PRAGMA query_only = ON` ([D-019](s13-decision-register.md#d-019)) covers the TEMP database, and D-019 is the runtime half of write serialization, so it is the strategy that gives way. And there is no allow-list to push a candidate set into — `vector_top_k` refuses a fourth argument at runtime (*"too many arguments on vector_top_k() - max 3"*), and `vectorIndexSearch` in the bundled amalgamation rejects `argc != 3` before inspecting its arguments. So `TwoPhaseTempTable` named an access path this engine does not have, and the cost table's third row priced an operation that cannot be issued. Removing the variant follows [D-039](s13-decision-register.md#d-039)'s precedent with `louvain_communities`: a name with nothing behind it is worse than an absence, because it is planned around. If a future libSQL gains a constrained index walk the variant returns with a body, which is a smaller change than the confusion it would otherwise cause. The reformulation the 0.5.4 note suggested — candidates carried in the statement as bound parameters — is what `PreFilterCTE` does, and it needs no write privilege, so it is better than the mechanism it replaces rather than a workaround for it.

**Selectivity is measured, not estimated.** SQLite has no histograms and `sqlite_stat1` gives average rows-per-key, which cannot estimate multi-hop reachability — the predicate actually being priced. The planner runs a bounded counting probe: the traversal under a cap, which costs a fraction of what it prices and is bounded by the cap. The probe doubles as the candidate set, so the walk is paid for once. `CandidateCount::Exact` versus `::AtLeast` keeps the distinction in the type, because a capped probe has *not* measured a count, and code that read it as one would be quietly wrong for exactly the large candidate sets the budget exists to catch.

**The strategy may never change the answer, and this is the entry's central claim.** `PostFilter`'s failure is not slowness but silence: when the filter is tight the survivors fall off the end of k′ and a top-ten returns four rows reporting success — a wrong answer that looks like a small result, which is what [Doctrine II](s0-s3-foundations.md#doctrine-ii) exists to prevent. So a post-filtered pass that comes back short *while its index scan was saturated* escalates to the exact strategy rather than returning. The acceptance gate is that the two strategies agree, swept across filter tightness and k: strategy is then a performance decision and nothing else. A planner choosing between different answers would be precisely the fidelity leak [Doctrine VIII](s0-s3-foundations.md#doctrine-viii) forbids.

`FilteredVectorSearch` is the public surface, a builder mirroring `TraversalBuilder`, which is the crate's established shape for a read with options. The strategy is planner-chosen and not a caller parameter — D-007's content is that the choice is arithmetic — with `strategy()` forcing one for tests. `execute_explained` returns the `CostEstimate` alongside the results, so D-007's empirical-tuning requirement is met by a value a test can assert on rather than by log output a test would have to scrape.

Mutation-verified, and one of the tests was fixed before it was trusted: the chunk-merge test ran 60 candidates against a 500-id statement chunk, so it exercised a single chunk while claiming to cross the boundary — and because candidate ids arrive in id order while the fixture made distance monotone in id, even a corpus large enough to chunk would have passed under a merge that simply concatenated. The fixture now reverses the embedding order so the nearest rows land in the *last* statement. Three mutations were then applied together and each failed its own test: dropping the merge sort, disabling the escalation, and restoring the old candidate-count heuristic. Rejected: keeping `TwoPhaseTempTable` as an alias degrading to `PostFilter` (it is not a third access path, and a variant that always means another one is a name that misleads); keeping it as a typed refusal (ships a variant that always fails); making the strategy a caller parameter (contradicts D-007 and lets a caller choose the slow-and-equal option for the wrong reason); estimating selectivity structurally from depth and degree (a guess, and worst on the skewed neighbourhoods the budget exists to bound).

<a id="d-049"></a>D-049 — Snapshot composition is implemented; the anchored fold is the first code [D-024](s13-decision-register.md#d-024) has ever bound (0.5.4). Closes [D-046](s13-decision-register.md#d-046). `reconstruct(ts)` now selects the newest snapshot at or before `ts`, folds the hot log above its anchor with `seq_id > :anchor AND recorded_at <= :ts`, and merges under last-writer-wins by `seq_id` — the same rule `trg_links_current_sync`'s upsert applies and the same rule the cold fold applies. `Database::reconstruct(ts)` wires the archive path and the snapshot directory from the handle, so composition is the default rather than something a caller opts into by remembering two arguments.

**Absence and deletion are different facts, and composition is where the difference starts to matter.** The pre-0.5.4 fold treated a winning `'D'` row as `continue` and a `retired = 1` concept as "do not insert". Folding from nothing that is right — both end as absence. Composed onto a snapshot they are opposites: the entity is *in* the base, and skipping the row leaves it standing as though nothing had happened. Tombstones are therefore collected and applied, and the full fold runs the same code against an empty base, so there is one path rather than two that must agree.

The acceptance gate is a property test: for a generated history with a snapshot taken mid-way, composed and full-fold results must agree at every transaction-time instant in the delta. That is [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots)'s "three paths, one rule, verified by the property suite" made executable — the claim had been in the document since 0.4.5 with nothing behind it.

**Two things this exposed, both worth recording.** First, the property test *passed under mutation* on its first run: dropping the tombstone changed nothing, because the generator had no operation that produced one. `Op::RetireConcept` was added and the mutation then failed, shrinking to a two-operation history ending in the retirement. A gate for the exact defect the design is about, satisfied by construction because the generator could not reach the case, is the same failure as [D-030](s13-decision-register.md#d-030)'s audit and the pre-[D-039](s13-decision-register.md#d-039) Louvain oracle — the third time this cycle a test has needed mutation to show it was asserting nothing.

Second, **[D-024](s13-decision-register.md#d-024)'s stated mechanism is wrong and is corrected below.** It attributes `seq_id` gaps to rolled-back transactions. Measured against libSQL 0.9.30: `sqlite_sequence` is written inside the transaction, so a rollback undoes it and the number is reused — `INSERT`, `BEGIN … INSERT … ROLLBACK`, `INSERT` yields ids `1, 2`, not `1, 3`. Gaps in the hot log are real regardless, because the archive path deletes superseded rows from `transaction_log` ([§5.7](s5-modules.md#57-temporalarchivers--cold-storage)) and those are scattered through the sequence rather than forming a prefix. So [D-024](s13-decision-register.md#d-024)'s rule is right and its reason was not; the gap-tolerance test builds the state the real mechanism produces, by deleting a log row inside a session marker, and fails under `seq_id = :anchor + 1`.

**Composition is disabled once an archive database exists, and that is a correctness requirement rather than caution.** Because archived rows are scattered, a row above the anchor and at or before `ts` can be gone from the hot log while a newer row for the same entity — recorded *after* `ts`, and so invisible to this fold — is what displaced it. The delta would miss it, the snapshot would answer with the older value, and the result would be wrong with nothing to indicate it. The full fold is slower and right. Composing across the archive boundary needs the cold log in the delta, which is a larger change and stays open. Note the same reasoning applies to `hot_log_covers`, which decides the cold path on `MIN(recorded_at)` — that is also not a sound completeness test after a scattered archive, and is recorded as open rather than fixed here.

> **Superseded by [D-052](s13-decision-register.md#d-052) (0.5.5).** Both halves are now closed, and the second one was worse than this entry recorded: `hot_log_covers` was not merely "not a sound completeness test", it was returning silently wrong answers on the shipped code — an entity could vanish from a pre-cutoff reconstruction entirely. Noting it as open here and not as a defect is itself the lesson: an unsound test named as a caveat reads as a limitation rather than as a bug.

Anchor selection loads candidates newest-first and stops at the first whose timestamp is at or before `ts`, so `reconstruct(now)` reads exactly one file. `SnapshotIncompatible` ([D-043](s13-decision-register.md#d-043)) is skipped rather than raised: an incompatible snapshot is the ordinary consequence of an upgrade, and being able to carry on without it is the entire reason that variant is distinct from corruption.

Still open, and not closed by this entry: **there is no snapshot cadence.** [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots) specifies a read-side maintenance task writing an anchor every 10,000 log entries; only `close()` writes one. The effect is that a cleanly-shut-down application composes from its shutdown anchor — the common case, and the one that matters most — while a long-running session accumulates an unbounded delta. The cadence is a spawned task whose lifecycle is a decision (owner, stop signal, what `close()` does with it), and it is left as one. Rejected: composing across the archive boundary now (needs the cold log in the anchored fold and a coverage test that is sound after scattered deletion — both larger than this); putting the anchor timestamp in the snapshot header to avoid loading candidates (worth it only if the newest-first scan ever reads more than one file, which `reconstruct(now)` does not); keeping `Database::reconstruct` off the surface (the free function's `None` for the snapshot directory is a correct answer that quietly folds the whole log, and a fast path nobody takes is not a fast path).

<a id="d-048"></a>D-048 — The vector write path goes through the Write Actor; `register_model` goes with it (0.5.4). [Doctrine VII](s0-s3-foundations.md#doctrine-vii), [D-011](s13-decision-register.md#d-011), [D-019](s13-decision-register.md#d-019). Phase 3 was delivered, tested and **unreachable**: `upsert_embedding` and `register_model` both take a `&libsql::Connection`, `Database::read_conn()` carries `PRAGMA query_only = ON`, and the write connection is moved into the actor at `open()` and cannot be named. An application could search vectors it had no way to store. Fifteen passing tests said otherwise because every one of them opened its own connection and reached around the actor — the same shape as [D-041](s13-decision-register.md#d-041)'s annotations and the pre-[D-039](s13-decision-register.md#d-039) Louvain, a capability that is green and absent at the same time, and the third instance this cycle of a test suite certifying its own workaround.

`Database::upsert_embeddings(model, rows)` chunks at `CHUNK_ROWS` onto the low-priority tier behind `LowPriCommand::UpsertEmbeddingChunk`. Low, not high: embedding is bulk derived work, and a 50,000-vector backfill must yield to an interactive assertion at every chunk boundary ([§5.1.5](s5-modules.md#515-cooperative-chunking--the-golden-rule)). Atomic per chunk and not across chunks, following `bulk_import` — and the trade is safer here than there, because an embedding is derived ([Doctrine VII](s0-s3-foundations.md#doctrine-vii)), so a partially written batch is recoverable by re-embedding, whereas a partially written history is not recoverable at all. The declared dimension is resolved **once per chunk**, not once per row: `declared_dimension` is a `PRAGMA table_info` round trip, and it cannot change inside a chunk, because the chunk holds the write lock and only `register_model` creates the table that declares it. No clock reading is taken, because an embedding carries no timestamp on either axis; the ledger already records when the content changed.

**`register_model` moved behind the actor too, and that was a deferred decision rather than an obvious one.** It issues DDL, which everywhere else in this crate is the migration runner's exclusive business ([D-032](s13-decision-register.md#d-032)), and the case for leaving it on a caller-supplied connection was that DDL is setup rather than steady-state work. That case does not survive the gap above: with the write connection actor-owned, "a caller-supplied write connection" is not a thing an application has, so leaving `register_model` outside would have made the write path reachable in principle and not in fact. The exception is bounded — a model's table is created once, by an explicit call, in one transaction ([D-037](s13-decision-register.md#d-037) requires the table and its DiskANN index be created together or dimension enforcement does not exist). It sits on the *high*-priority tier despite being setup, because every embedding write for a model blocks on it and queueing it behind a bulk job would stall the thing it gates.

Five tests, and the constraint on the first is what it *uses* rather than what it asserts: it touches `Database` and nothing else on the write side, so if the only route to a stored vector is again a connection the caller had to build, it stops compiling. The others pin that re-embedding replaces rather than versions and never reaches `transaction_log`; that a bad vector rolls back its whole chunk rather than leaving a prefix; that an unregistered model is a typed `ModelNotRegistered` rather than an engine complaint about a missing table; and that a backfill larger than one chunk lands completely.

Rejected: the high-priority tier for embedding writes (a backfill would preempt the user, which is the starvation [D-009](s13-decision-register.md#d-009) removed); one transaction for the whole batch (unbounded lock hold, and [Doctrine VII](s0-s3-foundations.md#doctrine-vii) makes the atomicity it buys unnecessary); resolving the dimension per row (one `PRAGMA` round trip per vector); keeping a `HashMap<model, dim>` on the handle to avoid the per-chunk read (a second description of a fact the schema already states, which is [D-037](s13-decision-register.md#d-037)'s rejected alternative and [D-035](s13-decision-register.md#d-035)'s defect); leaving `register_model` on a raw connection (per above — it makes the path reachable only for a caller who cannot exist).

<a id="d-047"></a>D-047 — The byte budget is enforced incrementally; the integer-index rewrite of `Subgraph` is deferred until something measures it (0.5.4). [Doctrine VI](s0-s3-foundations.md#doctrine-vi), [D-007](s13-decision-register.md#d-007).

**The defect.** `load_subgraph` called `graph.estimated_bytes()` inside the row loop, and that function is O(V + E) — it walks every node and both adjacency maps. Loading was therefore O(E²), measured on the reference machine at 500 edges in 26 ms, 1,000 in 76 ms, 2,000 in 231 ms: time tripling for each doubling of the input. The irony is exact. The byte budget exists to bound what a hub node in a dense neighbourhood can do to a load, and the budget *check* was the part that did not scale — a graph well inside its budget could take seconds to refuse or accept. Nothing caught it because the one large-graph test (20,000 nodes, SCC depth) builds its `Subgraph` in memory and never goes through the loader; every test that does go through the loader uses a handful of edges.

The fix is a running total carried through the load, and `estimated_bytes()` stays a derivation over the whole graph so a caller can still ask. Two accounts of one quantity is the drift [D-035](s13-decision-register.md#d-035) is about, so they are not two accounts: `node_bytes` and `edge_bytes` are the single definition of the estimate, `estimated_bytes()` sums them over a graph, and the loader adds them as it inserts. `hydrate` now also refuses *inside* its loop rather than after it — checking once at the end allocates the whole oversized result before declining to return it, which is the failure the budget exists to prevent rather than to report. Two tests: one asserting the loader's running total and the derivation give the same number (budget set one byte under the derived total, so an undercount — counting an edge once when `add_edge` stores it twice — fails), and one asserting the growth rate. The second is a ratio and not a duration, because absolute timings are a property of the machine and the growth rate is a property of the algorithm. Its sizes are 8× apart because at 4× the quadratic term does not yet dominate: mutation-tested, the per-row check gives 21.3× against a linear 8.0×, and the bound sits at 16×. A 4× spread measured 8× against an expectation of 4× and no CI-safe bound would have caught it.

**The rewrite is deferred.** The same review proposed carrying five of `petgraph`'s internal design choices into `Subgraph`: integer node/edge indices, topology separated from payloads, explicit directional adjacency, borrowing iterators, and deterministic insertion ordering. Two of the five are already implemented — `out_adj` and `in_adj` have been maintained as a pair since [D-039](s13-decision-register.md#d-039), and `out_edges`/`in_edges` already return borrowed slices, which are *more* capable than the proposed iterators, since `degree()` is `.len()` in O(1) and `k_core` calls it in a loop. Two are real: algorithms key `BTreeMap`s by 26-byte ULID, so every relaxation is a logarithmic number of string comparisons (comparisons, not hashes — `BTreeMap` does not hash), and `add_edge` clones the `EdgeRef` for the reverse direction, so every edge's three strings exist twice.

They are deferred rather than taken because **nobody has measured the algorithms**. The load path dominated everything until this entry fixed it, [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets)'s budgets are documented and not implemented as gates, and the case for a rewrite that touches every algorithm and the public `Subgraph` API should rest on a number rather than on an appeal to a well-engineered crate's internals. The condition for revisiting is a benchmark of Louvain and Dijkstra on a budget-sized loaded graph.

**And the rewrite has a cost the proposal does not price.** Determinism is currently structural: `BTreeMap` in, `BTreeMap`/`BTreeSet` out, explicit tie-breaks. Integer indices assigned in insertion order make it *procedural* — a property of the loader's `ORDER BY` and its `ids.sort()` continuing to be right. Both are right today. But substituting a description of a property for a derivation of it is this project's recurring defect ([D-030](s13-decision-register.md#d-030)'s audit, [D-035](s13-decision-register.md#d-035)'s compensating delete, the Louvain stub), and this instance fails silently in the worst way: a reordered `ORDER BY` would not error, Louvain would return a different partition, and [§8](s6-s10-flows-to-dependencies.md#8-testing-strategy)'s oracle would still pass, because an upper bound on modularity does not detect a *different* valid answer. If the rewrite happens it needs a test that loads one graph under two different SQL orderings and asserts identical index assignment — not a comment saying to sort. Relatedly, the proposal's "sort by ULID **or `recorded_at`**" is not a free choice: `recorded_at` is not a total order over nodes and its ties are unspecified.

Three smaller defects in the proposed blueprint, recorded so a later implementation does not inherit them: its `NodeData` drops `embedding_model`, which the current struct carries and the loader populates; its `ulid_to_idx` stores every id a second time, partly cancelling the memory win that justifies it; and it does not deliver its own second point, because `out_adj: Vec<Vec<EdgeId>>` indexing into `edges: Vec<EdgeData>` still pulls three `String`s into cache to read a `weight` — the separation that pays puts the weight beside the topology, which is what `petgraph` actually does, since for `petgraph` the edge payload *is* the weight.

Rejected: caching the running total as a field on `Subgraph` (the struct's fields are public and tests build graphs by mutating them directly, so a cached field would be silently wrong for any graph not built by the loader — a stale description of state, which is the thing being avoided); keeping the per-row `estimated_bytes()` and raising the default budget (treats a complexity class as a tuning parameter); taking the integer-index rewrite now on the strength of the argument (the argument is sound and the measurement does not exist, and this document's standard since [D-037](s13-decision-register.md#d-037) is that a claim about performance carries a number).

**Fixture: `star_of_stars` ([D-088](s13-decision-register.md#d-088), added 0.6.0).** Both halves rest on it. The `the_loader_stays_linear_in_edge_count` ratio test asserts linearity in *edge* count on a tree, where path count equals node count — the term that is identically 1 on this shape and 88,509× on `dense_small`; the test is still the right regression guard, but "linear" is a claim about this fixture rather than about the loader. And the deferral of the integer-index rewrite was framed in milliseconds, which [D-087](s13-decision-register.md#d-087) later re-opened as a *memory* question and answered on `Subgraph`'s own byte accounting rather than on any graph.

<a id="d-046"></a>D-046 — Snapshot composition is specified and not implemented; [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots), [§4.3](s4-schema.md#43-the-transaction-log) and [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets) are corrected to say so (0.5.4). **CLOSED by [D-049](s13-decision-register.md#d-049) later in the same cycle — the inventory below describes the state this entry was written against, and is kept because the six claims it lists are why the work was scoped the way it was.** Snapshots are written — `close()` calls `write_final`, the file lands atomically, retention runs — and they are read by nothing. `load_snapshot` has no caller in `src/` outside its own module: `reconstruct` folds the hot log, or hot and cold together ([D-026](s13-decision-register.md#d-026)), and never consults a snapshot at any `ts`. Six claims in the document depended on the composition that does not exist, and each is now marked rather than left standing:

1. **The anchored fold does not exist.** `HOT_FOLD` and `COLD_FOLD` filter on `recorded_at <= ?1` alone; there is no `seq_id > :anchor` term anywhere. [§4.3](s4-schema.md#43-the-transaction-log)'s index rationale distinguishes "the unanchored cold-start fold" from "the anchored fold", and only the first is real. This also makes [D-024](s13-decision-register.md#d-024)'s guarantee — that all replay logic uses inequality comparisons and never successor arithmetic — vacuously true rather than satisfied: there is no anchor to compare against, so the discipline is untested at the moment a maintainer first writes one.
2. **The composition and merge rule is unexercised.** [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots)'s "for each entity the fold's row wins; for entities absent from the fold, the snapshot's row stands" never runs.
3. **"Three paths, one rule, verified to agree by the property suite" was false on both halves.** Two paths exist (the `links_current` upsert and the cold fold); the third does not, and no test compares them.
4. **There is no 10,000-entry cadence and no maintenance task.** [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots) describes "a lightweight maintenance task [that] watches `seq_id` through `read_conn`"; nothing of the kind is spawned. `write_final` on clean shutdown is the only path that writes a snapshot, so an application that crashes, or one that simply runs for a long time, accumulates no anchors at all.
5. **Retention is five newest, flat.** The "plus one daily for thirty days" tier is not implemented.
6. **[§9](s6-s10-flows-to-dependencies.md#9-performance-budgets)'s "with snapshot, ≤ 200 ms at 1M entries" is unreachable**, and the row above it ("snapshot composition expected at this scale") describes an expectation nothing meets.

The consequence is not incorrectness — `reconstruct` returns the right answer — but unboundedness: it costs what the entire log costs, at every `ts`, forever, and the mechanism specified to bound that is the one missing. The gap is recorded here rather than closed because closing it is a real piece of work with a decision inside it (below), and because a document that describes writing-without-reading as a working cache is the same failure [D-037](s13-decision-register.md#d-037) and [D-040](s13-decision-register.md#d-040) corrected elsewhere: prose asserting a capability the code does not have, in a section a reader has no reason to doubt.

What closing it requires: an anchor-selecting read that picks the newest snapshot at-or-before `ts` and is robust to `SnapshotIncompatible` ([D-043](s13-decision-register.md#d-043)) by discarding and falling back to the full fold; an anchored fold variant carrying `seq_id > :anchor`, which is where [D-024](s13-decision-register.md#d-024)'s inequality discipline finally has something to be true about; a merge with the last-writer-wins rule; a property test asserting anchored-plus-snapshot equals full-fold at arbitrary `ts` over generated histories, which is the "three paths, one rule" claim made executable; and a decision on the cadence — the specified maintenance task watching `seq_id` on the read side is one option, and writing an anchor from the actor at a chunk boundary is another that costs the write path something and cannot miss. The read-side watcher is the specified design and should be honoured absent a reason not to.

<a id="d-042"></a>D-042 — A covering index for the traversal CTE, with the column order measured rather than reasoned (0.5.4). [§5.2](s5-modules.md#52-graphbuilderrs--traversal-valid-time-and-attribute-fidelity)'s recursive step ran on `idx_lc_src_active (source_id, valid_to)`, which pushes the seek and the open-interval bound into the index and leaves `valid_from`, `weight` and `edge_type` to be evaluated against a base-table row fetched for every candidate edge at every hop — random IO proportional to degree, not to result size. `idx_lc_traversal_cover (source_id, valid_from, valid_to, weight, edge_type, target_id)` carries everything the walk reads, so `EXPLAIN QUERY PLAN` reports `SEARCH l USING COVERING INDEX … (source_id=? AND valid_from<?)` and the base table is not touched until the terminal join to `concepts`. It subsumes `idx_lc_src_active` — same seek column, strictly more payload — which the `v3 → v4` rung therefore drops rather than keeping alongside; two index writes per assertion on a table that already takes three is a real cost for no read.

**The column order was where the reasoning went wrong, twice, and both errors are worth recording.** The review that prompted this proposed `(source_id, edge_type, valid_from, …)`. Measured against that proposal *with `idx_lc_src_active` still present*, the unfiltered traversal — the default, since `edge_types` is empty unless a caller sets it — declined the new index entirely and kept the old plan, which looked like a decisive argument that `edge_type` must come last. Measured again with the subsumed index dropped, both orders are covering, and the first conclusion was an artifact of the planner having a narrower alternative to prefer. The order still matters, for a smaller and different reason: with `edge_type` ahead of the range columns the unfiltered seek degrades to `(source_id=?)` and the valid-time window becomes a filter across that whole source's slice, while the shipped order constrains `valid_from` in the seek. The test asserts the seek text and not merely the word `COVERING`, because asserting `COVERING` alone passes under both orders — confirmed by mutation, which is also how the original claim was found to be overstated. A plan-shape assertion is the only honest form here: [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets)'s latency budgets are documented and not implemented as gates, so "this protects the budget" is an argument from a number nobody is measuring, whereas the plan is a fact the test can hold. Rejected: `(source_id, edge_type, …)` as proposed (weaker seek on the default query); adding the index while keeping `idx_lc_src_active` (pays for a read nobody gets); leaving it alone pending benchmarks (the benchmarks do not exist, and the plan shape is evidence that does).

<a id="d-043"></a>D-043 — The snapshot file is a versioned container, and an incompatible one is refused rather than parsed (0.5.4). Snapshots were bare `zstd(bincode(MaterializedState))`. `bincode` is not self-describing, so a file written against a different shape of `MaterializedState` does not reliably fail to load — it loads into wrong values, and the newest snapshot is the first thing a restart reaches for, so those values arrive labelled as the most recent state anyone believed. The `PayloadVersion` discipline the log has carried since 0.2.0 ([§4.3](s4-schema.md#43-the-transaction-log)) simply had no counterpart here. Files now open with a ten-byte header — magic `MACR`, a `u16` container format version, and the `u32` `user_version` this build understands — written uncompressed and checked before anything is decompressed, so the decision to reject costs nothing and commits to nothing. The failure is `DbError::SnapshotIncompatible`, deliberately not `ReplayCorrupt`: corruption is a fault to report, an incompatible snapshot is the ordinary consequence of an upgrade, and the two want opposite responses — the second should discard the file and fold from the log, which is a path that already exists. Headerless files from 0.5.4 and earlier are caught by the same check, since their first bytes are zstd's own magic. The container version is bumped when `MaterializedState` changes shape, independently of the schema version, because the two can move apart. Rejected: relying on `bincode` to fail on mismatch (it does not, which is the defect); a `serde` self-describing format such as JSON or MessagePack (pays a permanent size and speed cost on every snapshot to detect a condition a ten-byte header detects for free); versioning by filename (the name already encodes the anchor, and a name is not carried by the bytes if the file is moved).

<a id="d-044"></a>D-044 — A leaked `cold` attachment heals on the way in; the `Drop` guard that suggests itself does not work (0.5.4). Both ATTACH sites ([§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots), [§5.7](s5-modules.md#57-temporalarchivers--cold-storage)) pair with an unconditional DETACH on every `Result` path, which leaves exactly one hole: a panic unwinding between the two skips the DETACH regardless of which exit the `Result` would have taken, and a leaked handle then makes every later `reconstruct` *and* every later `archive` fail with "database cold is already in use" — permanent poisoning of the connection from one transient fault. The reflex fix is an RAII guard whose `Drop` issues the DETACH. **It does not work here:** `libsql::Connection::execute` is `async` and `Drop` cannot await, so such a guard constructs a future, discards it, and leaves the handle attached while presenting as cleanup — strictly worse than the honest single exit path, because it stops anyone looking. `Handle::block_on` inside `Drop` deadlocks on a current-thread runtime, and spawning a detach task races the next ATTACH. Recovery on the way *in* needs no destructor: `detach_stale_cold` issues a best-effort DETACH before each ATTACH, which in normal operation fails harmlessly with "no such database" and after a leak turns permanent poisoning into one failed statement nobody sees. It also works regardless of how the handle leaked, which a guard scoped to one function does not. The hole is currently hypothetical — neither span contains an `unwrap`, an `expect`, or an index — and the fix is taken anyway because it is two lines and the failure it prevents is unrecoverable without reopening the database. Verified by mutation: with the pre-ATTACH detach removed, the test reproduces the poisoning exactly. Rejected: an RAII `Drop` guard (does not execute the statement, per above); `catch_unwind` around the fold (addressed in [D-045](s13-decision-register.md#d-045)); accepting the hole because it is unreached today (the cost of prevention is two lines).

<a id="d-045"></a>D-045 — Actor `catch_unwind` and single-flight read coalescing are both declined (0.5.4). Recorded because both were proposed with sound general reasoning and both are wrong for this system, and an unrecorded rejection gets re-proposed.

*Wrapping the actor's `execute` in `catch_unwind` so a panicking chunk does not kill the writer* contradicts [D-015](s13-decision-register.md#d-015) without engaging it. [D-015](s13-decision-register.md#d-015) declines automatic writer recovery on the grounds that a dead writer means a bug that should surface in a crash report, and that resuming on a connection whose last-transaction state the caller cannot reason about is worse than stopping; catching the unwind and continuing the loop *is* that resumption, and the panic would have dropped a `Transaction` rather than rolling it back explicitly, which is precisely the unknown state [D-015](s13-decision-register.md#d-015) names. The behaviour the proposal treats as the defect — every later call returning `WriterUnavailable` — is the designed containment, and it already works: the panic unwinds the spawned task, the receivers drop, sends fail, and `Database::high`/`low` map that to the typed error ([§7](s6-s10-flows-to-dependencies.md#7-errors), [D-034](s13-decision-register.md#d-034)). The mechanism is also fragile in a way the proposal does not mention: it is a no-op under `panic = "abort"`, a plausible release profile for a desktop binary. If [D-015](s13-decision-register.md#d-015) should be revisited, that is its own decision entry with its own argument, not a wrapper.

*Single-flight coalescing of `reconstruct(ts)`* misreads the workload. The proposal groups `audit_current()` with `reconstruct()` as expensive log folds; `audit_current` never reads `transaction_log` at all — it is a symmetric-difference comparison between `links_current` and a window projection of `links` ([D-030](s13-decision-register.md#d-030)). And the thundering-herd model assumes a server: this is a single process with one shared `read_conn`, so N identical reconstructions serialize on that connection rather than stampeding it. The cost is latency amplification for one user, and the caller — who owns the calling pattern — is the right place to stop firing five identical queries. Most decisively, an in-flight map keyed by `ts` is a second description of derived state, which is the failure class [D-030](s13-decision-register.md#d-030) and [D-035](s13-decision-register.md#d-035) exist to prevent. The sanctioned mechanism for bounding reconstruction cost is already specified: snapshots ([§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots)), with anchoring and retention defined. Rejected in favour of finishing that — and **that mechanism is specified and not implemented** ([D-046](s13-decision-register.md#d-046)), which this entry owes as a caveat: the argument is that snapshots are the right answer, not that the right answer is already in place. Anyone re-proposing coalescing should be told that composition is the work, not that the problem is solved.

<a id="d-041"></a>D-041 — Analytics annotations belong in a derivative table, not in `concepts.content` (0.5.4). [Doctrine VI](s0-s3-foundations.md#doctrine-vi), [Doctrine VII](s0-s3-foundations.md#doctrine-vii). **Fixed in 0.5.4; the schema gains `analytics_annotations` ([§4.5](s4-schema.md#45-analytics-annotations--the-second-derivative-table-054-d-041)) on the ladder's `v2 → v3` rung.** As shipped through 0.5.3, `Subgraph::write_back_annotations` constructed a `ConceptUpsert` per annotated node and placed the annotation value in the `content` field, so writing back a Louvain partition overwrote every annotated concept's document text with a community label. The 0.4.5 document specified the correct destination and the 0.5.x renumbering lost it along with the rest of [§5.4](s5-modules.md#54-graphsubgraphrs-and-graphalgorithmsrs--native-in-memory-analytics) — the defect and its own specification went missing in the same edit. An annotation is `{ concept_id, label, value }` and belongs in `analytics_annotations`, a derivative table with no log trigger: disposable and rebuildable by re-running the algorithm, which is [Doctrine VI](s0-s3-foundations.md#doctrine-vi)'s second category, and excluded from the ledger by exactly the reasoning [Doctrine VII](s0-s3-foundations.md#doctrine-vii) applies to embeddings.

Three things were wrong with the old destination and only the first is obvious. It destroyed user content. It routed derived data into `transaction_log` through the concept triggers, so the ledger inflated permanently with labels no reconstruction should want. And because a concept `UPDATE` must carry a strictly advancing `recorded_at` ([§4.3](s4-schema.md#43-the-transaction-log), [D-018](s13-decision-register.md#d-018)), re-running the same algorithm on an unchanged graph produced a fresh version of every annotated concept — the ledger recorded the analytics schedule as though it were history. The method's doc comment asserted the write was "a normal bitemporal write and not an edit of history," which was true of the mechanism and false of the intent: that mechanism is right for a domain fact, and a community label is not one. The deeper point is the one the 0.4.5 text made in a single clause and is worth preserving: a reconstruction that needs community labels should recompute them, because a stored label answers what some past run of some past version of the algorithm produced, which is a different question wearing the same name.

What shipped: the table and its index ([§4.5](s4-schema.md#45-analytics-annotations--the-second-derivative-table-054-d-041)); `Annotation` and `Database::write_analytics_annotations`, chunked on the low-priority tier behind a new `LowPriCommand::WriteAnalyticsChunk`; `write_back_annotations` repointed and given a `label` parameter it previously had no way to express; and a `v2 → v3` migration rung, the first time the [D-032](s13-decision-register.md#d-032) ladder has had more than the baseline. Nothing is backfilled — a label that landed in `content` is indistinguishable from the text it replaced, and recomputation is the recovery, which is what this table exists to make cheap. Four tests pin the properties that matter: content untouched, `transaction_log` unchanged across an annotation write, a rerun replacing rather than accumulating *and* not versioning the concept, and the same three through `write_back_annotations` itself. Fixing this also caught a test making [D-038](s13-decision-register.md#d-038)'s mistake — `verification_counts_every_declared_object` asserted "4 tables" as a literal and failed the moment a fifth arrived, so it now checks presence by name and derives its counts from the DDL arrays.

Rejected: keeping the shipped shape and documenting it (it silently destroys content, which no amount of documentation makes acceptable); a dedicated `annotations` column on `concepts` (a schema change to a frozen ledger table under [D-036](s13-decision-register.md#d-036), to store data the ledger should not carry); storing annotations in `properties`-style JSON on the concept row (same objection, plus it re-enters `transaction_log`).

Rejected: rewriting [Appendix A](appendices.md#appendix-a--public-api-normative) to match the code without comment (loses the record of intent and makes the missing capabilities invisible again); deleting the unimplemented entries (same, with the added cost that [§5.6](s5-modules.md#56-temporalas_ofrs--valid-time-queries-and-attribute-hydration), [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets) and the implementation plan still reference them); marking the whole appendix aspirational (it is the API contract — half of it is real and callers need to know which half).


<a id="d-060"></a>D-060 — Overlapping valid-time intervals are refused in the write actor, not by a trigger, and the two guards partition the space rather than layering (0.5.6). [Doctrine II](s0-s3-foundations.md#doctrine-ii), [Doctrine III](s0-s3-foundations.md#doctrine-iii), [§4.2](s4-schema.md#42-links-assertion-history-and-current-belief-materialization), [D-014](s13-decision-register.md#d-014), [D-059](s13-decision-register.md#d-059). Closes defect AA and, with it, AG. `trg_links_single_open` fires `WHEN NEW.valid_to = '9999-12-31T23:59:59.999999Z'`, so it guards the open sentinel and nothing else: two *closed* intervals for one `(source, target, edge_type)` that overlap in valid time were accepted without complaint, and `query_as_of_edges` at an instant inside both returned one relationship as two edges, which every weighted algorithm downstream then double-counted. A wrong answer with no error, and the property suite could not see it because its invariant is stated over open intervals only.

The check runs in the write actor — `reject_overlapping_interval`, called from `AssertEdge` and from `write_edges_atomic` inside its transaction. The plan's recommendation was to refuse in `EdgeAssertion::normalized`, and that is not implementable as stated: `normalized` is a pure function with no connection, and moving the read to the API boundary instead would leave a check-then-write race between the read and the actor's insert. Inside the actor there is one writer by construction ([D-014](s13-decision-register.md#d-014)) and, for the batch paths, one transaction, so the window does not exist rather than being narrow. The recommendation's cost argument — "one read per assertion rather than one per insert" — also did not survive contact: on this path an assertion *is* an insert, so the counts are equal, and what actually differs is the race and the reach.

The arithmetic is `Interval::overlaps`, which is why the SQL narrows to a *provable superset* (`valid_from < :new_valid_to`, since overlap requires `max(start) < min(end)`) and leaves the decision in Rust. One definition of overlap, in the function named after it — rather than one in SQL and one in Rust, kept in step by hand. That also closes AG: the function was the crate's only overlap arithmetic and had no production caller, which is the missing half of AA rather than a separate tidiness problem. The three equality columns plus the `valid_from` range are exactly the shape `idx_lc_open_interval` was added for, so the probe rides D-059's index rather than justifying one of its own.

**Two open intervals stay `SingleOpenViolation`.** They do overlap, so a naive check reports them — and reporting them here would leave that variant constructible by nothing, which is defect Q's shape reintroduced by a fix. `defer_to_single_open` returns true exactly when both intervals are open, which is exactly the trigger's `WHEN` clause; everything else is unguarded at the storage layer and belongs to this check. A batch is additionally checked against *itself* before the transaction opens, because the database cannot see rows that are not in it yet and a self-contradicting batch would otherwise commit its own overlap.

What this does not cover, and [§4.2](s4-schema.md#42-links-assertion-history-and-current-belief-materialization) now says so: raw SQL against the same file. The storage layer permits what the API refuses. ([§4.7](s4-schema.md#47-what-this-schema-does-not-enforce) collects this with the two other gaps of its kind, and [D-074](s13-decision-register.md#d-074) says why one place rather than three.) Rejected: guarding closed intervals in the trigger (correct at the storage layer, and it adds a second index probe to every insert on the path D-059 has just finished making fast, to constrain callers who were going through the actor anyway); declaring overlap legal and deduplicating in every reader (cheapest to write, and it pushes the same decision onto every reader written from now on).

<a id="d-061"></a>D-061 — Identifiers are opaque with two reserved characters, and neither offered option was the answer (0.5.6). [§4.1](s4-schema.md#41-concepts-and-per-model-embeddings), [§4.3](s4-schema.md#43-the-transaction-log), [§5.2](s5-modules.md#52-graphbuilderrs--traversal-valid-time-and-attribute-fidelity), [D-029](s13-decision-register.md#d-029). Closes defects AD and J. Three modules assumed ULIDs and nothing enforced them: the fold partition (defect W), the `|`-joined entity key in `transaction_log`, and the traversal CTE's cycle check, `INSTR(w.path, CAST(l.target_id AS BLOB)) = 0`, which is correct only because every id was assumed to be the same fixed width.

Both offered options failed on inspection. **Wiring `validate_id` in as written would have required ULIDs** — not a tightening of the contract but a different one, since every id in the suite (`a`, `SRC`, `n000`, `node_100`) and presumably in every caller's data would become invalid. The assumption was wrong, not merely unenforced. **Declaring ids fully opaque** is stated as needing only a width-independent cycle check, and that is the smaller half: with `|` legal inside a component, two genuinely different links produce one `entity_id`, so the log cannot say which relationship a row belongs to — and W's partition fix does not help, because both rows are links.

So the constraint is the delimiters and nothing else: an id may not be empty and may not contain `|` or `/`. (**`/` is free again as of 0.6.0.** It was reserved solely so the cycle check could match a delimited path element, and [D-076](s13-decision-register.md#d-076) deleted the path column outright — so only `|` remains reserved, and a read-path optimisation retired half of an identity constraint. Relaxing runs in the safe direction: ids previously refused are now accepted, so nothing stored becomes invalid.) Narrow enough to leave every existing id valid, and it converts three assumptions into one enforced property, checked in `ConceptUpsert::normalized` and `EdgeAssertion::normalized` (both endpoints). The cycle check becomes `INSTR(w.path, '/' || id || '/') = 0` over a path delimited at both ends, which matches a whole element instead of a substring — without this, visiting `abc` pruned a live branch to `b`, silently, as a smaller result rather than an error. `generate_id` remains offered rather than required, and a test asserts a generated ULID always satisfies the constraint, since otherwise the crate would hand callers ids its own write path rejects.

Defect J is closed in the same change: `validate_id` returned `DbError::NotFound(id)` for a malformed identifier, which says the opposite of what happened. A caller matching on `NotFound` to decide whether to create the thing would be sent to create it again, with the same id, forever. It now returns `DbError::InvalidId { id, reason }`. Rejected: percent-encoding the components (moves cost to every read and makes the log unreadable by eye, to buy two characters back); choosing delimiters no id would plausibly contain (the same bet made silently — "plausibly" is what an assumption is).

<a id="d-062"></a>D-062 — The clock is injectable, and flooring it is part of the `Clock` trait rather than of `SystemClock` (0.5.6). [§5.1.2](s5-modules.md#512-handle-shape-and-the-clock-contract), [D-025](s13-decision-register.md#d-025), [D-027](s13-decision-register.md#d-027). Closes defect K, open since 0.5.2. `FakeClock` was public and constructed in `tests/harness.rs` with nothing to inject it into, so the field was dead and the compiler warned about it on every build of every test binary — while `recorded_at`, the transaction-time axis, was untestable through the public API because `Database::open` hardcoded `SystemClock`. Every test that wanted to assert on transaction time drove a raw connection with hand-written literals, which tests the trigger and not the crate's own stamping.

`Database::open_with_clock(path, cadence, clock)` is the entry point. What kept the defect open for three releases is the step the obvious implementation omits: a fake starting at the epoch issues stamps below every stored `recorded_at`, so the first concept write against any non-empty file aborts on `trg_concepts_monotonic_ra`. `open_with_clock` therefore raises the injected clock to the ledger's newest stamp before the actor starts. That is expressed as `Clock::raise_floor`, a required trait method, because the trait's own contract — strictly increasing across restarts — is not a property any clock can hold alone: it depends on what the database already contains, which the clock cannot see. Every implementation needs to be told, so telling it belongs to the trait. `SystemClock::new` and `open_with_clock` now share one definition of the floor, `recorded_at_floor`, rather than the query existing twice.

`FakeClock::raise_floor` moves to one microsecond *past* the floor, not to it: `recorded_at` must be strictly increasing, and issuing the floor itself collides with the row it was read from. The determinism cost is stated rather than hidden — on a fresh database an injected fake issues exactly the stamps it was given, and on a populated one it is floored and does not. Rejected: taking the floor as a constructor argument on `FakeClock` (the caller does not know it either, and it would have to be re-read on every reopen); a defaulted no-op `raise_floor` (an implementation that silently declines to be floored is the failure mode this closes, and a default makes declining the easy path).

<a id="d-063"></a>D-063 — The `Subgraph` integer-index rewrite is **retired, not scheduled**, and D-047's deferral condition is finally met (0.5.6). [D-007](s13-decision-register.md#d-007), [D-039](s13-decision-register.md#d-039), [D-047](s13-decision-register.md#d-047), [§5.4](s5-modules.md#54-graphsubgraphrs--the-in-memory-graph). [D-047](s13-decision-register.md#d-047) deferred the rewrite "until Louvain and Dijkstra are measured on a budget-sized graph". Nothing measured them for two releases, so the condition could not be met and the rewrite could be neither scheduled nor dropped — it simply sat, which is the worst of the three states. Measured now, on the star-of-stars fixture, three hops from the root:

| | 1,001 nodes | 5,001 nodes | 10,001 nodes |
|---|---|---|---|
| `load_subgraph` (3 hops) | 4.97 ms | 27.7 ms | 62.2 ms |
| `louvain` | 1.99 ms | 13.9 ms | 28.3 ms |
| `scc` | 0.90 ms | 7.7 ms | 12.9 ms |
| `k_core` | 0.71 ms | 6.7 ms | — |
| `dijkstra` | 0.41 ms | 2.5 ms | — |
| `astar` (zero heuristic) | 0.11 ms | 0.84 ms | — |

**The load dominates any single analysis at every size measured**, and the margin does not close: at 10K nodes the most expensive algorithm is 45% of the load, and the four cheaper ones are a rounding error against it. An integer-index representation does not touch the load — that cost is the recursive walk, the hydrate round trips, and row decoding, none of which care how the in-memory adjacency is keyed. So the rewrite optimises the smaller half of a workload whose larger half it cannot reach.

The honest qualification, which is why this is a retirement rather than a refutation: sum all five algorithms and they approach the load (4.12 ms against 4.97 ms at 1K; roughly 58 ms against 62 ms at 10K). A caller who loads once and runs the whole battery has a workload where the rewrite would matter — and `Subgraph` being a reusable value is exactly what makes that pattern possible. That is a real case and it is not the common one, so the rewrite is recorded as available with a stated trigger (a profile showing algorithm time dominating load time in a caller's actual use) rather than kept as an open item with no condition.

What the measurement redirects attention to instead: `load_subgraph` is mildly superlinear — 12.5× for 10× the nodes — which is a larger and unexplained effect than anything the rewrite would have recovered. Rejected: performing the rewrite anyway (it is a large change to the representation every algorithm reads, for the half of the cost that is already small); deleting [D-047](s13-decision-register.md#d-047)'s deferral without measuring (the deferral was correct, and its condition was answerable — leaving it unanswered is what was wrong).

**Fixture named in the entry itself, and it is the matrix's `star_of_stars` ([D-088](s13-decision-register.md#d-088), noted 0.6.0).** This is the one performance entry that already said which fixture it used — "on the star-of-stars fixture, three hops from the root" — which is why its CPU finding survives [D-087](s13-decision-register.md#d-087) unchallenged: a reader can see what it is a measurement of. It is the model for the annotations added to the entries around it.

<a id="d-064"></a>D-064 — A narrowing predicate is not free if it changes the plan: the overlap guard reproduced [D-059](s13-decision-register.md#d-059)'s defect one wave after it was fixed (0.5.6). [D-056](s13-decision-register.md#d-056), [D-059](s13-decision-register.md#d-059), [D-060](s13-decision-register.md#d-060). `OVERLAP_CANDIDATES` was written with a provably safe narrowing — `AND valid_from < :new_valid_to`, sound because overlap requires `max(start) < min(end)` — on the stated reasoning that the three equalities plus a `valid_from` range are "exactly the shape `idx_lc_open_interval` was added for". They are not. The range is what let `idx_lc_traversal_cover` win:

```text
with the range:     SEARCH links_current USING COVERING INDEX
                    idx_lc_traversal_cover (source_id=? AND valid_from<?)
without it:         SEARCH links_current USING COVERING INDEX
                    idx_lc_open_interval (source_id=? AND target_id=? AND edge_type=?)
```

`idx_lc_traversal_cover` leads on `(source_id, valid_from, …)` and contains every column the query mentions, so given a `valid_from` range it wins as a covering index while binding **one** equality column — and the guard scans the source's out-degree. Identical in shape to the defect [D-059](s13-decision-register.md#d-059) diagnosed in `trg_links_single_open`, in code written one wave after that fix, by someone who had just read it.

Cost, on a 90-edge chunk into a 2,000-edge hub: **+9.8 ms**, and — the detail that identified it — *the same with and without `idx_lc_open_interval`*. An index that makes no difference is an index that is not being used. Dropping the range makes the query a three-column point lookup the intended index serves exactly, and the guard's cost falls to within measurement noise of not running it at all (18.4 ms → 8.58 ms, against 8.65 ms with the guard disabled entirely).

A second, smaller instance of [D-056](s13-decision-register.md#d-056) was found and fixed in the same investigation: the guard prepared its statement per row inside `write_edges_atomic`, which the batch path had already learned not to do for `INSERT_LINK`. Worth ~0.2 ms on the same chunk — real, and an order of magnitude below the plan defect, which is why it was not the answer.

Two things follow, and they are the reason this has an entry rather than a commit message. **A correctness test cannot see this class of defect** — the guard returned the right answer throughout, in the right transaction, with the right error type. `the_overlap_guard_seeks_on_all_three_equality_columns` now pins the plan, joining the two tests [D-042](s13-decision-register.md#d-042) and [D-059](s13-decision-register.md#d-059) left behind. And **a covering index is a trap that recurs**: it is chosen for containing the columns rather than for discriminating between rows, so the more columns an index carries the more queries it can silently capture. Both existing plan tests exist because of the same mechanism. Rejected: `INDEXED BY` to force the choice (pins one query to one index name and moves the fragility rather than removing it); dropping `idx_lc_traversal_cover` (it is load-bearing for the traversal, which is a different shape).

**Fixture: `star_of_stars`, hub arm ([D-088](s13-decision-register.md#d-088), added 0.6.0).** Measured on the same chunks-into-a-hub setup as [D-059](s13-decision-register.md#d-059), which is appropriate, because the defect is a *plan-shape* defect and a plan is a property of the query and the index rather than of the data. The +9.8 ms magnitude is a property of the hub; the wrong index would have been chosen on any shape, and [D-089](s13-decision-register.md#d-089) is what now catches that class without needing a fixture at all.

<a id="d-065"></a>D-065 — `corpus_size` stays a per-query `COUNT(*)`: defect AF is real in mechanism and under one percent in consequence (0.5.6). [D-007](s13-decision-register.md#d-007), [D-037](s13-decision-register.md#d-037), [§5.3](s5-modules.md#53-graphvector_filterrs--filtered-vector-search). The objection was that [D-007](s13-decision-register.md#d-007) argues strategy choice should be arithmetic rather than a rule of thumb, while the arithmetic's own input is O(corpus) and the thing it selects is not — the planner's input costing more than the plan. The mechanism is exactly as described. The magnitude is not:

```text
corpus_size        2,000 vectors     5.2 µs
corpus_size       20,000 vectors     8.5 µs
declared_dimension    (one PRAGMA)   5.0 µs
whole filtered search                2.5 ms
```

Ten times the corpus costs 1.6 times the time, because ~4.9 µs of it is a round trip and statement preparation rather than counting — which is why `declared_dimension`, whose work is a single `PRAGMA`, costs the same 5 µs. Extrapolated to [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets)'s stated 100K corpus: ~22 µs against a 2.5 ms search, **under 1%**.

The implementation plan proposed caching both "since neither can change without DDL". That is true of the dimension and **false of the count**, which changes on every `upsert_embeddings` — so the proposed fix would have traded a real staleness bug for less than one percent of a query, and the justification offered for it was the part that was wrong. `declared_dimension` genuinely is DDL-fixed and could be cached soundly; at 5 µs there is nothing to buy, and an empty cache is one more thing to invalidate on a migration that drops a model table ([D-036](s13-decision-register.md#d-036)). Both stay as they are, with the measurement recorded beside them so the question is closed rather than merely unanswered. Rejected: caching the dimension alone (sound, and buys 5 µs at the cost of a lifetime question about model re-registration); deriving the count from `sqlite_stat1` (requires `ANALYZE` to have run, and returns a stale figure when it has not — an approximation is fine for this input, but one whose staleness nobody controls is not).

<a id="d-066"></a>D-066 — The snapshot cadence gets its own connection, and `Drop` warns rather than asserts (0.5.6). [D-012](s13-decision-register.md#d-012), [D-026](s13-decision-register.md#d-026), [D-044](s13-decision-register.md#d-044), [D-053](s13-decision-register.md#d-053), [§5.1.2](s5-modules.md#512-handle-shape-and-the-clock-contract), [§7.3](../Macrame%20Implementation%20Plan%20v0.5.6.md). Two hardening items that both turned on the same question — what a mechanism is actually protecting — and were answered in opposite directions.

**The cadence's connection.** `run_cadence` was given `read_conn.clone()` on the reasoning that a `libsql::Connection` is an Arc-backed handle and [R15](s11-s12-milestones-and-risks.md#r15) makes every extra local connection a cost worth not paying for nothing. The cost it was not paying for was real: `reconstruct` brackets its fold with `ATTACH cold … DETACH cold`, that region is per-connection state, and nothing synchronises it — so a cadence fold and a caller's fold on one connection can interleave such that one DETACHes a handle the other is mid-fold on. Recorded in §8.5 as a hazard rather than a defect because it **did not reproduce** under 200 concurrent reconstructions: the cadence anchors at `MAX(recorded_at)` and therefore almost always takes the hot path, so the window needs a write landing between `log_head` and the fold. Narrow, and real. The cadence now opens its own `query_only` connection at `open()`. Preferred to a mutex around the region because it removes the shared state rather than ordering access to it — there is nothing left to race on and nothing to remember to hold. The R15 objection does not apply: that fault is about *concurrent* opens, and this is one more sequential open during `open()`.

**`Drop`.** [§7.3](../Macrame%20Implementation%20Plan%20v0.5.6.md) offered option B — document `close()` as mandatory and `debug_assert` in `Drop` — and it was implemented, measured, and reduced to a `warn!`. The assert fired on roughly thirty tests on its first run, and the right reading of that was not "thirty tests are wrong". What dropping actually costs is one final snapshot: every public write method awaits its responder, so by the time a caller *can* drop the handle every write it issued has committed; the cadence stops on its own, because `cadence_stop` is a `watch::Sender` whose drop signals the task; and a snapshot is derivative state under [Doctrine VI](s0-s3-foundations.md#doctrine-vi), so losing one makes the next `reconstruct` fold from an older anchor — **slower, not wrong**. Spending a test-run abort on a performance loss, in a project whose own notes say a suite that fails for reasons unrelated to the code under test trains people to ignore red, is the wrong trade. Option A ("abort the actor and log") stays rejected for the reason it was rejected twice before: `Drop` cannot await, so it cannot drain, and cleanup that cannot clean up is worse than none.

What did change is the half nobody had argued about: **`close()` propagates the writer's `Result`**. It was `let _ = handle.await`, so an actor that had panicked closed "successfully" and the caller's one chance to learn the write path had died was spent silently. A `JoinError` becomes `DbError::WriterStopped`, and it is returned *before* the final snapshot is written, because a snapshot taken after a failed writer records a state the caller has no reason to trust. Rejected: a mutex around the ATTACH region (orders a race instead of removing it, and the ordering has to be remembered at every future call site); keeping `close()`'s discarded `Result` as "shutdown is best-effort" (it is the only place the writer's exit status is observable at all).

<a id="d-067"></a>D-067 — An upgraded database is re-anchored at open; a fresh one is not (0.5.6). [D-043](s13-decision-register.md#d-043), [D-053](s13-decision-register.md#d-053), [Doctrine VI](s0-s3-foundations.md#doctrine-vi), [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots). [D-043](s13-decision-register.md#d-043) makes a `SCHEMA_VERSION` bump invalidate every snapshot on disk, and that is correct — a snapshot is a serialised `MaterializedState` and a schema change can change what one means. What was missing is the other half: **nothing wrote a replacement.** The first `reconstruct` after an upgrade skipped every file as `SnapshotIncompatible`, folded from genesis, and answered correctly at the cost the snapshot existed to avoid, with the only trace a `warn!` per skipped file. On a database with a large log that is the whole difference the feature buys.

`migrations::run` now returns a `MigrationOutcome`, and `Database::open` writes a fresh anchor when it reports an upgrade. Two gates, both learned from the first implementation failing tests that were right:

- **A fresh file is not an upgrade.** `from == 0` has no snapshots to invalidate, so there is nothing to re-anchor — and treating it as one made `open()` write a snapshot on every first open, which broke two contracts the suite already pins: an idle database is never anchored, and an `open()` that touches the disk when it was not asked to is surprising in its own right.
- **Only when the cadence is enabled.** `open_with_cadence(None)` means *this handle writes no snapshots except at `close()`*, and a one-off write at open contradicts that for a caller who chose the quiet mode precisely to control when files appear. They still get an anchor from `close()`.

Written at open rather than left to the cadence because the cadence fires on log *growth* ([D-053](s13-decision-register.md#d-053)): an upgraded database that is then read but never written would never re-anchor at all. Failure is logged rather than returned, on the same Doctrine VI reasoning as [D-066](s13-decision-register.md#d-066) — a missing anchor costs time and no information, so refusing to open a database because an optimisation could not be rebuilt trades a real capability for a performance one. Rejected: deleting incompatible snapshots at open instead (removes the misleading files and still leaves the next fold running from genesis); re-anchoring on the first `reconstruct` that skips a snapshot (puts an unbounded write on a read path, and on the read connection).

<a id="d-068"></a>D-068 — `raw()` stays public, and actor containment is documented as a convention rather than a guarantee (0.5.6). [D-014](s13-decision-register.md#d-014), [D-060](s13-decision-register.md#d-060), [§5.1](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor), [§4.2](s4-schema.md#42-links-assertion-history-and-current-belief-materialization). §5.1 says the write actor is the sole writer, and two mechanisms make that true of the handle: every write method goes through a channel, and `read_conn()` carries `PRAGMA query_only = ON`. Kept public. Making it private would not make the property true — the database file is reachable by any SQLite client on the machine — it would only remove the *supported* way to do the thing, which is how escape hatches become folklore. And the honest statement is one fact rather than two: this is the same limit [D-060](s13-decision-register.md#d-060) already records for the overlap guard, and [§4.2](s4-schema.md#42-links-assertion-history-and-current-belief-materialization) already states it there — and [§4.7](s4-schema.md#47-what-this-schema-does-not-enforce) now states it once for all three ([D-074](s13-decision-register.md#d-074)). **The storage layer permits what this API refuses.** The free functions `register_model` and `upsert_embedding` take a bare connection for the same reason and carry the same caveat, with the handle methods as the route that goes through the actor. Rejected: making it private (the property it would protect is not enforceable at this layer, so the change buys the appearance of a guarantee); returning a `query_only` connection instead (silently breaks the diagnostic uses, and a caller who needs a reader already has `read_conn()`).

<a id="d-070"></a>D-070 — `load_subgraph`'s superlinearity is the `DISTINCT` sort, and it is not removable (0.5.6). [D-007](s13-decision-register.md#d-007), [D-047](s13-decision-register.md#d-047), [D-063](s13-decision-register.md#d-063), [§5.4](s5-modules.md#54-graphsubgraphrs--the-in-memory-graph). Wave 3 measured `load_subgraph` at 12.5× for 10× the nodes (4.97 → 62.2 ms, 1K → 10K) and could not say why; it was recorded as unexplained and larger than anything the rewrite [D-063](s13-decision-register.md#d-063) retired would have recovered. Answered from the plan: `EXPLAIN` reports `USE TEMP B-TREE FOR DISTINCT`, an O(E log E) sort over the output, and n log n predicts ~13.3× against the 12.5× measured.

The `DISTINCT` is load-bearing. The cycle check stops a path revisiting a node; it does not stop two branches reaching the same node, so `walk` holds a node once per path that reaches it and the join multiplies that node's edges accordingly. Without it a caller gets an edge once per path to its source.

Two fixes were tried and neither shipped, which is the useful part of this entry:

- **Deduplicating the walk first** (`SELECT DISTINCT node_id FROM walk`, then joining) moves the sort from edges to nodes and is **36% slower** — on a hub-shaped graph `walk` has far more rows than the join emits, so the "smaller" set is the larger one.
- **Aligning `ORDER BY` with the full `DISTINCT` key** does elide the second temp b-tree; `USE TEMP B-TREE FOR ORDER BY` disappears from the plan, verified. Measured back-to-back: **85.95 ms against 86.76 ms** — no effect, because the `DISTINCT` b-tree dominates and the second pass runs over rows already nearly in order. Reverted, since it widens the ordering contract to `weight` and the timestamps in exchange for nothing measurable.

One caution the A/B produced and worth recording beside the numbers in §8.8: both arms sat near 86 ms where Wave 3 recorded 62.2 ms for the same code, and two identical runs in one session differed by 29%. **The absolute figures in this cycle's measurements carry that much noise; the ratios, taken within a single run, do not.** Rejected: materialising the walk into a temp table with a unique index (trades the sort for a write, on the read connection); dropping `DISTINCT` and deduplicating in Rust (the same O(E log E) in a different place, plus it would have to reproduce the ordering the sort provides).

**Corrected by [D-076](s13-decision-register.md#d-076) (0.6.0), and the correction is not that any of the above is wrong.** Every measurement in this entry reproduces, both rejected fixes were rejected for good reasons, and the `DISTINCT` is still load-bearing. What was wrong is the sentence this entry ends on — that the growth is *"explained, inherent to producing a deduplicated result, and left alone."* It was explained for the fixture it was measured on, and that fixture is a **tree**: `benches/budgets.rs` seeds a chain of stars, where there is exactly one path to each node, so path count equals node count and the term that actually dominates on a graph is identically 1. Measured directly: on the star fixture the walk emits 1,011 rows for 1,011 nodes, and on a 328-edge layered graph it emits **299,593** rows for 49 nodes. The leading cost was never the `DISTINCT`; it was the walk enumerating paths, and the `DISTINCT` was the visible consequence rather than the cause. This entry stands as the record of an analysis that was rigorous within a frame nobody had checked — which is the reason [T4.1](../Macrame%20Hardening%20Plan%20v0.6.0.md)'s fixture matrix exists.

**Fixture: `star_of_stars` ([D-088](s13-decision-register.md#d-088), added 0.6.0).** Recorded here explicitly because T4.1 names this entry as its worked example: with the fixture stated, it would have read *"inherent on `star_of_stars`"*, and the gap [D-076](s13-decision-register.md#d-076) later found would have been a qualifier in the entry rather than a wave. The correction below already says this in prose; the annotation makes it findable by the same rule as every other performance entry.
<a id="d-072"></a>D-072 — A `'D'` row in `transaction_log` is corruption, not a tombstone; and the fix removed a second unreachable path rather than creating one (0.5.6). [Doctrine III](s0-s3-foundations.md#doctrine-iii), [Doctrine V](s0-s3-foundations.md#doctrine-v), [D-008b](s13-decision-register.md#d-008b), [D-049](s13-decision-register.md#d-049), [D-060](s13-decision-register.md#d-060), [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots). `fold_delta` handled `operation == 'D'` by collecting a tombstone. **No trigger in the schema writes a `'D'` row and no code path in the crate can produce one**: [Doctrine V](s0-s3-foundations.md#doctrine-v) permits no physical delete outside an archive session, all three hot tables carry delete guards ([D-008b](s13-decision-register.md#d-008b) added the third), and the archive *moves* rows to the cold file rather than logging their removal — cold rows keep their original operation. The branch was not wrong; it was a claim about the ledger that is not true. Anyone reading the fold concluded that deletions are recorded and reconstructible.

That is the shape this cycle kept finding — a path assumed by one layer and enforced by none, or present and never taken — and it has now produced W, AC, AD, AI and this. The fold is the layer that can notice, so it does: a `'D'` row raises `DbError::ReplayCorrupt` naming the sequence number, the table and the entity, and saying which rule it enforces. The same call [D-060](s13-decision-register.md#d-060) made for overlapping intervals.

**The part that was not in the plan.** `Delta` carried two tombstone sets, `concepts_gone` and `edges_gone`, and *both* were populated only from the `'D'` branch. Turning that branch into an error would therefore have left `edges_gone` reachable by nothing — closing one unreachable path by opening another, in the commit whose entire subject is that pattern. So `edges_gone` went too, along with its loop in `apply_to`.

`concepts_gone` stays, and the resulting asymmetry is the interesting part rather than an oversight:

* A **concept** disappears by being *retired*, which writes a `'U'` row whose payload carries `retired = 1`. That is a genuine removal from a composed state — the snapshot holds the concept, the delta says it is gone — and `concepts_gone` is what carries it. This is the branch that was doing the work all along.
* An **edge** never disappears. Retiring one asserts a successor over the same interval key — same `source|target|type|valid_from`, later `recorded_at` — so the log row is an `'I'` under the *same* `entity_id`, and last-writer-wins in `apply_to` replaces the tuple in place. There is nothing to remove because nothing left: the interval closed. That is [Doctrine III](s0-s3-foundations.md#doctrine-iii) showing through at the fold — an assertion is superseded, never deleted.

Four tests, and the last two matter more than the first two: the `'D'` refusal for a concept and for a link, and then **controls** proving the refusal did not break what actually removes things — retirement still drops a concept from a composed fold, and a retired edge still comes back as one closed interval rather than zero or two. Without those, breaking retirement while enforcing Doctrine V would have looked like success.

Rejected: deleting the branch silently (a `'D'` row would then be ignored as an unparseable insert, which is the same silence one level down); keeping it and documenting it as forward-compatible (preserves exactly the misleading claim, and a future build that logs deletes would be refused by `migrations::run` on `user_version` long before the fold saw a row); keeping `edges_gone` for symmetry (symmetry with what — there is no operation that produces one, and the asymmetry is a fact about the doctrine worth stating rather than hiding).

<a id="d-071"></a>D-071 — The FTS5 `VACUUM` hazard does not arise, the delete guard is why, and the check that would have proved it cannot (0.5.6). [Doctrine V](s0-s3-foundations.md#doctrine-v), [Doctrine VI](s0-s3-foundations.md#doctrine-vi), [D-008](s13-decision-register.md#d-008), [D-022](s13-decision-register.md#d-022), [D-036](s13-decision-register.md#d-036), [D-051](s13-decision-register.md#d-051), [§5.9](s5-modules.md#59-vector--embeddings-the-model-registry-and-search), [Appendix C](appendices.md#appendix-c--future-considerations-deliberately-deferred). Wave 5 opened with what looked like the last silent-wrong-answer path in the crate and closed having built nothing, which is the right outcome and took two measurements to reach.

**The hazard, as flagged.** `concepts_fts` is declared `content='concepts', content_rowid='rowid'`. `concepts` has `id TEXT PRIMARY KEY`, so its rowid is *implicit*, and `VACUUM` renumbers implicit rowids. After a vacuum every `content_rowid` in the index would point at a different concept, and keyword search — and `HybridSearch` with it, since RRF fuses the keyword arm — would return the wrong concepts with no error. Nothing in the crate vacuums; nothing stops an operator.

**It does not arise, and the reason had never been written down.** `concepts` can never be deleted from: `trg_concepts_guard_delete` is *unconditional*, not marker-gated like the `links` and `transaction_log` guards, because [D-022](s13-decision-register.md#d-022) says concepts are never physically archived. Upserts go through `ON CONFLICT(id) DO UPDATE`, which preserves the rowid rather than replacing the row. So `concepts.rowid` is dense `1..n` in insertion order at all times, and `VACUUM`'s renumbering — which assigns `1..n` in rowid order — is the identity map. Measured rather than argued: 20 concepts with three updates among them, rowids identical before and after a `VACUUM`, and the index still matching all 20. `vacuum_does_not_disturb_the_fts_index` pins it.

**So the delete guard is load-bearing for the search index, not only for the ledger.** That is the finding worth carrying forward. [Appendix C](appendices.md#appendix-c--future-considerations-deliberately-deferred) designs concept archival as deferred-but-feasible and names GDPR erasure as a separate operation outside the archive path; **either one makes `concepts.rowid` sparse and makes this hazard real.** Whichever lands owes a `rebuild_fts()` as part of its work, and the test above is what will say so — it fails the moment rowids stop being dense.

**The check that was supposed to make this moot.** `rebuild_fts()` has existed since [D-051](s13-decision-register.md#d-051) as the repair with no way to ask whether it is needed; its own note concedes it is "cheaper to run than to reason about". Wave 5 set out to add `Database::verify_fts()` on FTS5's `'integrity-check'` — the engine's own operation, which is what [D-036](s13-decision-register.md#d-036) and `REBUILD_CONCEPTS_FTS` both prefer over a hand-rolled equivalent that could drift from the triggers.

**`'integrity-check'` does not answer the question.** On libSQL 0.9.30 it verifies the index's *internal* consistency, not its agreement with the content table. Measured: after `'delete-all'` the index matches zero rows where it matched ten, and both `'integrity-check'` and `'integrity-check', 0` report success. A `verify_fts()` built on it would return "healthy" for an empty index.

That is defect AC's shape — a function that looks like it checks something and does not — so **it was not shipped**. The alternative was the hand-rolled content comparison rejected earlier in the same review, and the argument against it did not improve: it would be a second implementation of the sync triggers, able to drift from them, built to guard a hazard now shown unreachable. `an_emptied_fts_index_still_passes_integrity_check` records the limitation as a **tripwire**: it asserts that `integrity-check` still passes on a stale index, so a later libSQL that cross-checks content makes the test fail and announces that the method can now be built. Under [Doctrine VI](s0-s3-foundations.md#doctrine-vi) the exposure is bounded anyway — the index is derivative, `rebuild_fts()` reconstructs it from the ledger, and no information can be lost, only search results made wrong until someone rebuilds.

Operator note, in [§5.9](s5-modules.md#59-vector--embeddings-the-model-registry-and-search) rather than an appendix because that is where the external-content declaration is explained: `VACUUM` is safe **as long as concepts are never deleted**, which the schema currently enforces. Restoring a backup that skipped the shadow tables still calls for `rebuild_fts()`, which is the case that method was written for.

Rejected: sampling N concepts and comparing index rowids (the hand-rolled second implementation [D-036](s13-decision-register.md#d-036) argues against, and it can only ever miss what it did not sample); giving `concepts` an `INTEGER PRIMARY KEY` alias so the rowid is explicit and stable (the structural fix, and a schema change to a frozen ledger table that [D-036](s13-decision-register.md#d-036) permits neither as `ADD COLUMN` nor as an index — worth revisiting only in a major-version slot, and unnecessary while the guard holds); dropping external content so FTS5 stores its own copy (removes the coupling and roughly doubles storage on `content`, the largest column in the schema, to insure against an event that cannot currently happen); rebuilding the index unconditionally at every `open()` (self-healing in appearance, an unbounded reindex at every startup in fact, and it would make any check decorative).

<a id="d-073"></a>D-073 — `load_subgraph_with` reuses `TraversalBuilder`, filters **both** the walk and the projection, and found two accounting defects on the way in (0.5.6). [D-007](s13-decision-register.md#d-007), [D-039](s13-decision-register.md#d-039), [D-047](s13-decision-register.md#d-047), [D-064](s13-decision-register.md#d-064), [§5.2](s5-modules.md#52-graphbuilderrs--traversal-valid-time-and-attribute-fidelity), [§5.4](s5-modules.md#54-graphsubgraphrs-and-graphalgorithmsrs--native-in-memory-analytics). `load_subgraph` took neither `edge_types` nor `min_weight` while `TraversalBuilder` took both — the same walk over the same table with two fewer knobs. Recorded in 0.5.6's Wave 4.5 as a feature gap, and closed here because it is not one: the byte budget bounds the **unfiltered** neighbourhood, so a caller wanting one edge type out of a hub got [`SubgraphTooLarge`](s6-s10-flows-to-dependencies.md#7-errors) for a graph whose filtered form fits easily, and filtering the returned `Subgraph` afterwards cannot help because the refusal happens during the walk. A **reachability** limit, not a convenience one.

`TraversalBuilder` is reused rather than two parameters added, so there is one filter vocabulary and one validation path — [D-039](s13-decision-register.md#d-039) already made edge types bind parameters precisely because this walk had no validation of its own. `load_subgraph` becomes a delegation with a default builder.

**The design question, which is where the two forms could quietly disagree.** `TraversalBuilder` applies its filters to the **recursive step** — which edges are *followed* — while this loader's final projection returns every edge of every node it reached. Wiring them together naively gives a caller who asked for `CITES` a graph reached via `CITES` and populated with `KNOWS` edges as well. Both halves therefore filter: naming edge types or a weight floor asks for a subgraph *of those edges*, the walk uses them to bound which nodes are reached, and the projection uses them to decide which adjacency lands in the result.

**Two defects surfaced during implementation, and neither is in the feature.**

*The byte accounting was off by one byte per edge.* The loader added `2 * edge_bytes(&edge)`, on the reasoning that `add_edge` stores the entry twice. It does — but the `in_adj` copy has `node` rewritten to the **source**, and `edge_bytes` sums `e.node.len()`, so the running total drifted from `estimated_bytes()` by `target.len() - source.len()` per edge. Enough to make the loader refuse a graph sized at exactly its own `estimated_bytes()`. Invisible to `load_subgraph_totals_agree_with_the_derivation`, which asserts refusal at *half* the budget — a threshold no one-byte-per-edge drift can reach. That test now also requires the graph to fit its own estimate, which is the assertion the [`node_bytes`](s5-modules.md#54-graphsubgraphrs-and-graphalgorithmsrs--native-in-memory-analytics) doc comment had been making in prose since 0.5.4.

*Delegating with the builder's default silently disarmed the negative-weight guard.* `TraversalBuilder` defaults `min_weight` to `0.0`, and `0.0` **excludes negative weights** — which is exactly the input [D-039](s13-decision-register.md#d-039)'s `NegativeEdgeWeight` exists to *report*, since Dijkstra and A* are unsound over them and the decision was to refuse at the boundary rather than return a shortest path that is merely a path. So the first delegation turned a typed refusal into a graph quietly missing edges, which is the failure mode this whole cycle has been closing. Caught by `a_negative_edge_weight_is_refused_at_load`, an existing test.

The fix makes the two mechanisms agree rather than overlap: `load_subgraph` passes `NEG_INFINITY`, so an edge the caller has **not** filtered reaches the guard; a caller who states a weight floor has asked to exclude what falls below it, and excluding it is not an error. `load_subgraph_with` with a default builder therefore filters negatives rather than reporting them, which is stated on the method — the alternative was to change `TraversalBuilder`'s default, which would silently alter every existing traversal.

A plan-shape test guards the new SQL, because [D-064](s13-decision-register.md#d-064) established that adding a predicate to an index-sensitive query can push the planner off the index it was written for while every returned row stays correct. Both arms are checked: the filtered walk and the unfiltered one must each still be served index-only by `idx_lc_traversal_cover`.

Rejected: adding `edge_types` and `min_weight` as two more positional parameters (a six-argument loader, and a second filter vocabulary to keep in step with the builder's); teaching `TraversalBuilder` to return a `Subgraph` directly (the tidiest end state and the largest change — the builder knows nothing of byte budgets or `NodeData`, and it would put [D-007](s13-decision-register.md#d-007)'s budget on a type whose other method has no use for one); filtering only the projection (the byte budget is enforced during the walk, so it would close the ergonomic half of the gap and leave the reachability half exactly where it was).

<a id="d-077"></a>D-077 — The latest-belief projection gets one definition, and the archive stops auditing its own rebuild (0.6.0). [Doctrine VI](s0-s3-foundations.md#doctrine-vi), [D-012](s13-decision-register.md#d-012), [D-023](s13-decision-register.md#d-023), [D-030](s13-decision-register.md#d-030), [D-035](s13-decision-register.md#d-035), [§5.7](s5-modules.md#57-temporalarchivers--cold-storage), [§5.8](s5-modules.md#58-integrity--audit-and-rebuild). `archive()` calls `rebuild_within` **inside its own write transaction**, and `rebuild_within` ended by calling `audit_current` on itself. **The order of the two changes is the entire argument, and it is not the order the plan proposed.** T0.2 proposed making the post-rebuild audit opt-in on the grounds that "the archive already knows the projection is correct because it just derived it from the definition". That was not true when it was written. The projection existed **twice** — byte-identical, in `rebuild.rs` and `audit.rs` — so there was no *the* definition, and the post-rebuild audit was not tautological at all: it was a runtime check that the two copies still agreed, which is a real check, paid on every archive forever. Deleting it against two copies would have removed the only thing keeping them honest. So the projection is extracted to one `LATEST_BELIEF_PROJECTION` **first**; only then is the audit tautological by construction, and only then is skipping it a saving rather than a silent loss of coverage. The first draft of this entry quoted "56–61%" from a single run, which is [D-070](s13-decision-register.md#d-070)'s session-noise caution being ignored one entry after it was cited. <a id="d-078"></a>D-078 — [§4.7](s4-schema.md#47-what-this-schema-does-not-enforce) claimed a gap the storage layer does not have: NaN weights are refused by `NOT NULL` (0.6.0). [D-039](s13-decision-register.md#d-039), [D-074](s13-decision-register.md#d-074), [§4.7](s4-schema.md#47-what-this-schema-does-not-enforce), [§5.4](s5-modules.md#54-graphsubgraphrs-and-graphalgorithmsrs--native-in-memory-analytics). [D-074](s13-decision-register.md#d-074) gathered three invariants enforced *above* the storage layer and listed the third as *"edge weights are non-negative **and not NaN**"*, permitted by "the schema and the write API". The NaN half is false. SQLite stores a NaN double as NULL, so `weight REAL NOT NULL` rejects it before any code of ours is involved.

Measured on libSQL 0.9.30 through all three doors, because the hardening plan's probe ran on SQLite 3.50.4 via `node:sqlite` and this project does not carry another engine's numbers: `assert_edge(weight = f64::NAN)`, a raw `INSERT` binding `f64::NAN`, and a raw `INSERT` computing `0.0/0.0` inside the engine — which never crosses the binding layer at all, and so could plausibly have behaved differently. All three fail with `NOT NULL constraint failed: links.weight`, and nothing lands.

So NaN is not a weaker instance of §4.7's property; it is the **opposite** of it. §4.7 exists to say where the schema is silent, and here the schema is strict — the section claimed a hole in its own subject matter. Row 3 now reads "non-negative" and the NaN correction is stated beside it rather than quietly dropped, since a reader who relied on the old row would have written a NaN guard they did not need.

**The tripwire runs in the failing direction, and that is the point.** The other three cases in `storage_boundary_tests.rs` assert that the storage layer *accepts* what the API refuses, so they fail if a gap is ever closed. This one asserts the storage layer *refuses*, so it fails if the gap is ever opened — if a future libSQL stores NaN as a real double, the inserts start succeeding, the test breaks, and §4.7's row has to be corrected back. A claim that the schema enforces something needs a tripwire exactly as much as a claim that it does not; the failure mode here would otherwise be a shortest path computed over NaN, where every comparison is false and the answer is silently arbitrary.

`load_subgraph`'s `weight.is_nan()` arm is therefore unreachable on any file this schema created, by any SQLite client, and it **stays** — with a comment saying so. Removing it would trade a comparison per edge for a dependency on an engine behaviour this crate does not control, and the failure it prevents is unbounded. Rejected: deleting the arm as dead code (correct today, and it is dead only because of an engine property nothing in this crate enforces); leaving §4.7 as written (it overstates the ledger's weakness, and a document that is wrong in the *safe* direction still teaches a reader something false about where the checks are); folding this into [T2.1](../Macrame%20Hardening%20Plan%20v0.6.0.md)'s `CHECK (weight >= 0.0)` decision (that constraint is about negative weights and is still open — bundling a correction with an undecided change is how corrections wait).

<a id="d-079"></a>D-079 — The write actor counts its own holds, behind a `metrics` feature (0.6.0). [D-042](s13-decision-register.md#d-042), [D-055](s13-decision-register.md#d-055), [D-058](s13-decision-register.md#d-058), [D-059](s13-decision-register.md#d-059), [§5.1](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor), [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets). Everything this crate knew about its own latency lived in `benches/`, which is a statement about one laptop and one synthetic fixture. [D-059](s13-decision-register.md#d-059) had already established that the 3 ms bound does **not** hold on a large database, by a factor of 15, and it took a benchmark rewrite to notice — because nothing in a running system was counting. `Database::metrics()` now returns queue depth on both channels, a per-command-kind hold histogram, a count of holds over [`CHUNK_BUDGET`](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor), and the longest hold since open with the command that caused it.

**The unit measured is the actor turn, not the SQL.** The instrumentation brackets the whole `execute` call rather than the statements inside it, because the actor is single-threaded and the SQLite write lock is not preemptible: an interactive assertion arriving mid-turn waits for the turn, whatever the turn spent its time on. Timing the SQL alone would have reported a bound that held while callers waited — which is the same error [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets) made when it stated the budget as a row count with a duration attached ([D-058](s13-decision-register.md#d-058)).

**The three contractual exemptions are exempt from the violation count, not from measurement.** `write_bulk_atomic`, `archive` and `rebuild_current` are uncapped by decision (D-012, D-014, D-023), so counting their holds as budget violations would make the violation count noise on any database that archives. Their durations are still recorded — a 40 ms archive is precisely what T1.1 exists to shrink and cannot be shrunk if it is not counted.

**Two implementation facts worth recording, because both were wrong first and both were caught by a test rather than by review.**

The first: `turns` was counted at the top of the loop, where the queue-depth sample is taken. That sample must happen *before* `select!` blocks — it is "what was queued when I went looking", and taking it afterwards measures what arrived during the turn instead. But the same increment made `turns` count loop *iterations*, so an idle actor had already counted a command that had not arrived, and the total disagreed with the sum of its own per-kind breakdown by exactly one, forever. The two are now separate fields: `depth_samples` is iterations, `turns` is the sum of the per-kind counters, and the snapshot exposes both so the difference reads as a fact rather than as drift.

The second is sharper. The longest hold and the kind that caused it are packed into **one** `AtomicU64`, so a reader cannot see a duration from one turn beside a kind from another — a rare wrong answer to exactly the question the field exists to answer. The first packing put the kind in the high bits. The update is a `fetch_max` on the packed word, so whichever field sits high is the one being compared: the "longest hold" became the hold with the largest *enum index*, and a 3 ms `write_concepts_chunk` outranked a 10 ms `rebuild_current` because its variant is declared later. Nothing in the arithmetic was wrong, and the unit test passed — its fixture's slowest hold was also its highest-indexed kind. Only the integration test, running real commands whose costs and declaration order disagree, exposed it. The packing is now duration-high, kind-low, and there is a unit test whose two orderings deliberately conflict.

**The feature is off by default and the loop has one shape either way.** With `metrics` off, `HoldTimer::start` reads no clock and `ActorMetrics` is a zero-sized type whose methods are empty, so the actor compiles to what it compiled to before. That is arranged as two impls of one type rather than `#[cfg]` inside the loop body, which matters more than the nanoseconds: a conditional in the loop is how the instrumented and uninstrumented paths drift until only one of them is the one that runs.

This is a precondition for the rest of Tier 1, not a convenience. T1.1 and T1.2 are both "make the tail bounded", and neither can be validated anywhere but a bench without something that measures the tail. Rejected: on by default (the crate's contract is a latency bound, and a default that instruments the path the bound is about should be the operator's choice); `tracing` spans instead of counters (spans answer "what happened in this request" and this answers "is the bound holding across all of them" in fixed memory, with no allocation on the actor's path — they are different questions and `tracing` is already a dependency for the first); one counter set per channel rather than per kind (priority is a property of scheduling, kind is a property of cost, and the question being asked is which *command* is expensive); locking the actor to produce a consistent snapshot (the observer would become a source of the latency it is measuring, so `snapshot()` is explicitly not torn-read-free and says so).

<a id="d-080"></a>D-080 — The archive can be windowed, the sessions are separate actor turns, and an empty session no longer rebuilds (0.6.0). [D-011](s13-decision-register.md#d-011), [D-012](s13-decision-register.md#d-012), [D-058](s13-decision-register.md#d-058), [D-077](s13-decision-register.md#d-077), [D-079](s13-decision-register.md#d-079), [§5.1](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor), [§5.7](s5-modules.md#57-temporalarchivers--cold-storage), [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets). `archive(cutoff)` was the least bounded of the three operations exempt from [`CHUNK_BUDGET`](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor), and uniquely so: `write_bulk_atomic` and `rebuild_current` are sized by something the caller can see, while the archive's hold is a function of *how long since the last archive ran*. `archive_windowed(cutoff, window)` runs the same work as N sessions, each with its own marker, horizon row and rebuild, returning one `ArchiveReport` per session.

**D-012 is satisfied per session, which is what it asks for.** The requirement is that copy-then-delete never be split — a crash between the phases duplicates or loses rows. N small sessions satisfy that exactly as one large one does. What windowing adds is the obligation that a partial run leave a coherent intermediate state, and it does: each session commits a valid horizon, so a failure at window *k* leaves the database archived to boundary *k−1* and nothing in between. The **sequence** is not atomic and does not claim to be; re-running with the same cutoff completes the job.

**The loop lives on the handle, not in the actor's `Archive` arm, and this is the whole decision.** Putting it inside the actor would produce N small transactions inside **one** hold — smaller transactions, and identical latency, because the actor is single-threaded and nothing else writes until its turn returns however many `COMMIT`s that turn contains. Sending N commands is what returns the actor to its `select!` between sessions, which is where a high-priority assertion gets to jump the queue. This is the same reasoning that puts [D-011](s13-decision-register.md#d-011)'s chunking on the handle, and it is the trap T1.2 names for `CREATE TABLE … AS SELECT`. `actor_metrics_tests` pins it by asserting that the number of `Archive` *turns* equals the number of sessions reported — the one fact about windowing that cannot be seen from outside the actor.

**An archive session that deletes no links no longer re-projects `links_current`.** `links_current` is a function of `links`; if the `DELETE` removed nothing, the projection cannot have drifted. This was harmless while `archive()` was called once against a whole backlog, because that one session always had work to do. It stops being harmless the moment the caller windows: [D-077](s13-decision-register.md#d-077) established that `rebuild_within` costs O(*surviving* `links`) regardless of how much the session archived, so without this a run of twenty windows over a quiet stretch of history pays twenty full reprojections to delete nothing — and windowing makes the archive several times slower in total than not windowing. Archiving the transaction log deliberately does not trigger a rebuild either; it cannot change `links`.

**Measured, and the result is a trade rather than an improvement.** Fixtures of superseded history over four hours of transaction time, driven by a `FakeClock` so the windows bound something real, with the hold read from the actor's own per-kind high-water mark ([D-079](s13-decision-register.md#d-079)) rather than from the caller's side of the channel:

| fixture | window | sessions | longest hold | total |
|---|---|---|---|---|
| 8,000 keys | one session | 1 | 3,326 ms | 3,326 ms |
| 8,000 keys | 1 h | 9 | **768 ms** | 4,160 ms |
| 2,000 keys | one session | 1 | 260 ms | 260 ms |
| 2,000 keys | 1 h | 9 | **117 ms** | 671 ms |

At 8,000 keys the hold falls 4.3× for total wall time that is flat within this cycle's noise — two runs put the nine-session total at 3,362 ms and 4,160 ms against single-session figures of 3,730 ms and 3,326 ms, and the intermediate windows were repeatedly *faster* than the single session. At 2,000 keys the same change costs 2.6× the total work to halve the hold. The reason the trade inverts is that the archive's dominant terms are superlinear in the surviving table — `LINKS_ARCHIVABLE`'s correlated `EXISTS` and the rebuild both — so at large sizes each session leaves a smaller table for the next and the savings offset the fixed per-session cost, while at small sizes there is nothing to offset it. **Windowing pays when the backlog is large, which is when the unwindowed hold is a problem in the first place.** `archive()` is therefore kept rather than deprecated, and the numbers are published beside both.

A window is **refused** rather than clamped when it would need more than `MAX_ARCHIVE_SESSIONS` (4,096) sessions, or when it is zero. Rounding a one-second window up to something workable would archive over boundaries the caller did not choose and give them no way to see that it happened. The session count is derived from the oldest `recorded_at` actually present rather than from a fixed epoch, so a database opened yesterday is not asked to archive 1970, and the last boundary is `cutoff` itself rather than `start + n·window`, which would overshoot and archive rows the caller excluded.

Rejected: making `archive()` window by default (the trade inverts with size, and a default that is 2.6× slower on small databases to improve a latency nobody was suffering is the wrong way round); windowing by row count instead of by transaction time (the count is not known without a scan, and the cutoff is a *time* on both axes — a row-count window would have to be translated back into one anyway); returning an aggregate `ArchiveReport` instead of a `Vec` (it would hide which session failed, and on the error path the per-session results are the only record of what did commit); a background task that windows continuously (that is a policy, and this crate's position is that scheduling belongs to the caller — [D-053](s13-decision-register.md#d-053) is the one exception and it is opt-out).

<a id="d-081"></a>D-081 — `write_bulk_atomic` stays uncapped and stops being unpredictable; its cost is a function of batch **shape**, not size (0.6.0). [D-011](s13-decision-register.md#d-011), [D-014](s13-decision-register.md#d-014), [D-060](s13-decision-register.md#d-060), [D-079](s13-decision-register.md#d-079), [§5.1](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor), [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets). [D-014](s13-decision-register.md#d-014) is right that the batch is one act under one stamp and capping it breaks the guarantee the method exists to provide. But "uncapped and undocumented at the call site" is not the same as "uncapped by decision", and the only statement of the cost anywhere was the word *uncapped* in a table. `write_bulk_atomic` now warns through `tracing` when the predicted hold exceeds `BULK_ATOMIC_WARN_HOLD` (250 ms — fifteen frames at 60 Hz, deliberately far above [`CHUNK_BUDGET`](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor), since this path is exempt from that bound by contract and a warning that fires on correct behaviour gets filtered out), and `estimated_bulk_hold` is public so a caller can ask before committing to a batch size.

**T1.3's prescribed model — "rows × measured per-row cost" — is wrong twice, and measuring it is what showed both.** First, the cost is not linear: `write_edges_atomic` opens with `reject_overlaps_within`, which compares **every pair** in the batch before a row is written ([D-060](s13-decision-register.md#d-060)'s within-batch guard). Second, and this is the one that matters, the quadratic term's constant is set by the batch's *shape*. The pairwise loop begins with an early `continue` on mismatched `(source_id, target_id, edge_type)`; pairs sharing all three fall through to `Interval::new` and `overlaps`, which is **sixteen times** dearer per pair.

Measured on libSQL 0.9.30, best of three, hold read from the actor's own per-kind high-water mark ([D-079](s13-decision-register.md#d-079)):

| rows | fan-out to distinct targets | 20,000 corrections to one relationship |
|---|---|---|
| 2,000 | 148 ms | 310 ms |
| 5,000 | 414 ms | 1,386 ms |
| 10,000 | 1,013 ms | 4,884 ms |
| 20,000 | **2,618 ms** | **18,057 ms** |

Two batches of the same length, seven times apart — and a size-only model errs toward the *under*-prediction, which is the only direction that matters for a warning. So `estimated_bulk_hold` counts the matching pairs rather than guessing them, with one `HashMap` pass over the batch:

```text
hold ≈ 73 µs · rows  +  5.5 ns · mismatched pairs  +  86 ns · matching pairs
```

Within 1.03–1.11× of measurement across 500–20,000 rows in both shapes; it over-predicts by 3× below ~500 rows, where fixed costs dominate, which is harmless because nothing that small can approach the threshold. `examples/bulk_atomic_diag.rs` prints predicted against measured so the model's drift is visible rather than assumed, and a unit test pins both measured figures — a coefficient edited without re-measuring fails it.

**The warning is emitted on the caller's task, before the command is sent.** In the actor the only context left is "a large batch"; here the log line carries the caller's own `tracing` span and names the call site that chose the size. The message states the predicted hold, says the operation is atomic by contract and cannot be chunked, and names [`Database::bulk_import`](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor) as the alternative for callers who need the latency bound and not the atomicity ([D-011](s13-decision-register.md#d-011)).

**A defect in [D-079](s13-decision-register.md#d-079)'s instrumentation, found by this item's own diagnostic.** The hold was timed around the whole `execute` call from the actor loop, so it was recorded *after* each arm sent on its `oneshot`. Those are two tasks: a caller that awaits its own write and immediately reads `Database::metrics()` can be scheduled first and see a turn count that does not include the write it just did. `bulk_atomic_diag` reported a 20,000-row batch as a **0 ms** hold, every time. Not a ledger correctness problem, and invisible to a dashboard sampling every few seconds — which is worse, because the instrumentation would have been believed while being wrong precisely when someone tried to verify it. The timing now lives in a `Turn` type whose `answer` method records and *then* sends, in that order; what falls outside the measurement is the `oneshot::send` itself, a few nanoseconds against a turn measured in microseconds at best.

Rejected: capping the batch (breaks [D-014](s13-decision-register.md#d-014) — the entire contract of the method); returning the estimate as an error above a threshold (a caller who genuinely needs 20,000 rows in one act is not making a mistake, and refusing them leaves no supported way to do the thing); stating the ceiling as prose in rustdoc without a function (prose cannot be consulted at run time by a caller sizing a batch, which is exactly when the answer is needed); a size-only estimate (7× wrong between two shapes, in the under-predicting direction); making `reject_overlaps_within` sub-quadratic by grouping first (defensible and a larger change than this item — the guard would still be O(n log n) with the same expensive comparison, and it belongs with a decision about D-060's within-batch semantics rather than smuggled into a documentation fix).

<a id="d-082"></a>D-082 — `links_current` can be rebuilt beside itself in chunks, and the swap costs an index build rather than nothing (0.6.0). [D-011](s13-decision-register.md#d-011), [D-023](s13-decision-register.md#d-023), [D-035](s13-decision-register.md#d-035), [D-042](s13-decision-register.md#d-042), [D-077](s13-decision-register.md#d-077), [D-079](s13-decision-register.md#d-079), [D-080](s13-decision-register.md#d-080), [§4.2](s4-schema.md), [§5.8](s5-modules.md#58-integrity--audit-and-rebuild). `rebuild_current` is one `BEGIN IMMEDIATE … COMMIT` holding the write lock for its whole duration — 353 ms for 40,000 rows in `links` — and [D-023](s13-decision-register.md#d-023) is why it cannot simply be split: the window between the `DELETE` and the `INSERT` is the entire of current belief, so a reader landing in it sees a graph with no edges and no error. `rebuild_current_chunked` builds the replacement in a shadow table instead. The live table stays live and trigger-maintained throughout; the only moment anything is unavailable is the swap.

**Four mechanical facts, re-probed on libSQL 0.9.30 rather than carried over.** The plan states three of them from a `node:sqlite` probe, and [D-078](s13-decision-register.md#d-078) is the precedent for not taking another engine's semantics on trust. All three hold here: `ALTER TABLE … RENAME` reparses the whole schema, so the rename fails with `error in trigger trg_links_current_sync: no such table: main.links_current` while the triggers exist; `DROP TRIGGER` → `DROP TABLE` → `RENAME` → recreate works; DDL is transactional. `PRAGMA legacy_alter_table=ON` also works and is **not** used — it disables the reference fixups the modern rename exists to perform.

**The fourth is the one the plan does not name, and it is silent.** The plan's step 2 says to build the shadow with `CREATE TABLE … AS SELECT`, and reasons only about that statement's *duration*. It copies rows and **nothing else**: no primary key, no `CHECK` constraints. The swap then succeeds, the row count is right, and the next `INSERT INTO links` dies inside `trg_links_current_sync` with `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint` — because the conflict target no longer exists. Probed: the projection had stopped being maintained and the only symptom appeared on an unrelated write. The shadow is created from [`CREATE_LINKS_CURRENT_TABLE`](s4-schema.md) with the name substituted, so it cannot drift from the declared table, and `shadow_rebuild_tests` writes *after* every swap rather than only counting rows.

**The swap is not microseconds, and the reason is structural.** Index names are global and SQLite has no `ALTER INDEX … RENAME`, so the shadow cannot carry `idx_lc_traversal_cover` while the live table still holds that name — and building it under a temporary name would leave `links_current` permanently indexed under names absent from `CREATE_INDICES`, so the next migration would create a **second** copy of each. `DROP TABLE` frees the names and they are reusable in the same transaction (probed), so the swap is where the three indexes get built. What the chunking moves off the lock is the *projection* — the window function over all of `links`, the O(E log E) term. That is a smaller claim than the shadow idea's usual promise and it is the true one.

**Measured** (best of three by longest hold, read from the actor's per-kind high-water mark, [D-079](s13-decision-register.md#d-079)):

| `links` | `links_current` | `rebuild_current` | turns | chunked, longest turn | chunked, total |
|---|---|---|---|---|---|
| 4,000 | 1,000 | 26.0 ms | 7 | **11.1 ms** | 20.4 ms |
| 16,000 | 4,000 | 110.6 ms | 19 | **16.6 ms** | 65.6 ms |
| 40,000 | 10,000 | 353.5 ms | 43 | **46.8 ms** | 152.6 ms |

The hold falls 7.6× at the largest size and the advantage grows with the table, which is the shape the item needed. The result that was not expected is the last column: the chunked path is also **2.3× cheaper in total**, where [D-080](s13-decision-register.md#d-080)'s windowing cost more. The cause is the same fact that forces the index build into the swap — the shadow is filled while *unindexed*, so it pays one bulk index build at the end instead of maintaining three indexes per row, and that more than covers the extra turns and the second table. Note also what still does not hold: 46.8 ms is fifteen times [`CHUNK_BUDGET`](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor), so `ShadowRebuild` is deliberately **not** exempt from the violation count. Its fill chunks are meant to fit and its swap is not going to; exempting the kind would hide the first fact to excuse the second.

**Both paths are kept, and they differ in contract, not only in speed.** `rebuild_current` is one act, audits itself, and can run inside a caller's existing transaction — which is what `archive()` needs, since a nested transaction would simply fail. `rebuild_current_chunked` does none of those and cannot be used there. It also does not audit: the whole argument is that expensive work happens off the lock, and `audit_current` is two `EXCEPT` passes over the projection, the exact cost [D-077](s13-decision-register.md#d-077) removed from the archive for the same reason. A caller who wants the check has `audit_current` on the read connection, where it costs nobody the write lock.

**An archive during the build abandons the rebuild rather than swapping in a stale table.** The catch-up pass finds work by `recorded_at >= build_start`, which cannot see a *deletion* — a deleted row has no `recorded_at` left to be found by — so an interleaved [`archive`](s5-modules.md#57-temporalarchivers--cold-storage) would let the shadow resurrect archived history. The actor keeps an archive counter (in `ActorShared`, deliberately outside `ActorMetrics` because it is not a metric and must exist in every build, not only under the `metrics` feature); `Begin` reports it, `Swap` compares, and a mismatch drops the shadow and returns the new `DbError::RebuildInterrupted`. That variant is distinct from `RebuildFailed` and the distinction is the point: `RebuildFailed` means the repair ran and did not repair, which is a reason to distrust the ledger; this means the repair **did not run**, `links_current` is untouched, and the action is to retry. Verifying instead would have cost O(E log E) under the lock, which is what this exists to remove.

The epoch travels out to the caller and back through `ShadowStep::Swap` rather than being remembered by the actor, because the actor is stateless per command by construction and one remembered slot would be silently shared by two concurrent rebuilds. `shadow_step` is public for the same reason `raw()` is: the looping `rebuild_current_chunked` offers no seam, and a caller pacing a rebuild against a frame budget needs one — with the obligation, stated at the method, that mishandling the epoch defeats the interlock.

Rejected: `CREATE TABLE … AS SELECT` for the shadow (drops the schema, silently — above); temporary index names on the shadow (leaves the live table indexed under names `CREATE_INDICES` does not declare, so the next migration doubles them); `PRAGMA legacy_alter_table=ON` (works, and disables the fixups the rename exists for); chunking by row count rather than by `source_id` (the window function partitions by a key led by `source_id`, so a chunk that split a source would rank a partial partition and project the wrong row — the source is the smallest safe unit, and a single very-high-degree hub is therefore one chunk however long it takes, which is bounded by the graph and not by any constant); replacing `rebuild_current` with this (different contract — not atomic as one act, not usable inside a transaction, not self-verifying, and it can decline); auditing the shadow inside the swap (the cost the design exists to remove).

<a id="d-083"></a>D-083 — `links.weight` is constrained by the schema in v7, and the constraint needed two clauses nobody predicted (0.6.0). [Doctrine III](s0-s3-foundations.md#doctrine-iii), [D-032](s13-decision-register.md#d-032), [D-036](s13-decision-register.md#d-036), [D-039](s13-decision-register.md#d-039), [D-059](s13-decision-register.md#d-059), [D-060](s13-decision-register.md#d-060), [D-074](s13-decision-register.md#d-074), [D-078](s13-decision-register.md#d-078), [§4.7](s4-schema.md#47-what-this-schema-does-not-enforce), [§5.4](s5-modules.md#54-graphsubgraphrs-and-graphalgorithmsrs--native-in-memory-analytics). [§4.7](s4-schema.md#47-what-this-schema-does-not-enforce) listed three invariants enforced above the storage layer and called the third — non-negative edge weights — the one genuinely open. It was also the asymmetric one: rows 1 and 2 describe a writer going around the API, while for row 3 the *supported* path accepted the value, so a file this crate wrote by itself could hold a row it declined to read back. Schema v7 closes it with a table-level `CHECK` on `links`; the cold schema gains the same one.

**The constraint shipped is `CHECK (weight >= 0.0 AND weight < 9e999 AND typeof(weight) = 'real')`. Only the first clause is the one T2.1 asked for.** The item offers "three corrections to the obvious form" and none of them is either of the other two clauses — both came out of probing what the first still admits, and both are worse than the negative weight the item was written for.

`typeof(weight) = 'real'` closes text. `REAL` in SQLite is an **affinity**, not a type: values that can be converted are, and values that cannot are stored as they arrived. `'abc'` cannot become a number, so it is stored as TEXT — and in SQLite's type ordering every text value sorts above every numeric one, so `'abc' >= 0.0` is *true* and the first clause passes it. What follows is not a wrong answer: reading a text `weight` as `f64` reaches `unreachable!("invalid value type")` inside libsql 0.9.30 and **panics**, in whatever unrelated query first touches the row, arbitrarily far from the write that planted it. The clause costs one function call per insert and refuses nothing legitimate — `3`, `'5'` and `1.0` all arrive as REAL through affinity conversion and pass.

`weight < 9e999` closes infinity, and the route to it is the part worth recording, because **two successive predictions about it were wrong and a test settled it.** T2.1 predicted `CHECK (weight >= 0.0)` would admit `+∞` — correct, confirmed on libSQL — and argued from there that the loader guard must therefore stay. But the guard is `weight < 0.0 || weight.is_nan()`, so it does not catch `+∞` either; nothing in the crate did. The second reading, written into the DDL rustdoc as a correction to the plan, was that this is harmless: IEEE infinity propagates through addition and stays totally ordered under comparison, so Dijkstra still terminates and still reports the edge as effectively unusable — an odd answer rather than an unsound one. That was wrong too, and the full suite said so within minutes: **an infinite weight makes the transaction log unreplayable.** The log trigger serialises the row to JSON, JSON has no representation for infinity, and the payload round-trips into `ReplayCorrupt { reason: "number out of range" }` — every later `reconstruct()` fails, including the one `close()` performs. Under Doctrine III the log is the source of truth, so a value that cannot survive it is corrupt rather than eccentric. `9e999` is the idiom because SQLite has no `isinf`: the literal overflows to `+∞` on parse and `inf < inf` is false.

**The loader guard stays, for a reason that is neither the plan's nor the second one.** T2.1 kept it on the `+∞` argument, which turns out to be the constraint's job. It stays because a `CHECK` on `links` does not reach `links_current` — derivative and deliberately unconstrained — nor cold files created before this rung. Those are the paths on which `NegativeEdgeWeight` remains reachable, and `graph_tests` now plants its fixture in `links_current` for exactly that reason: the old fixture wrote to `links` and stopped passing the moment the constraint landed, which is the tripwire working rather than a test to be patched around.

**Doctrine III is not violated, and the case where it would be is refused.** SQLite has no `ADD CONSTRAINT`, so the rung is a full rebuild of `links` — the largest table — inside one transaction: create, copy verbatim, drop, rename, recreate triggers. No clamping, no rounding, no dropping. A database already holding a weight the new constraint rejects therefore **cannot be migrated**, and the rung refuses *before* touching anything, with a count and an example row, rather than failing halfway through a copy with a bare `CHECK constraint failed`. Such rows are reachable — until v7 `assert_edge(weight = -1.0)` was accepted, which *was* the gap — and what those assertions were meant to say is not a decision a migration can take on the operator's behalf.

Two mechanical notes on the rung. `DROP TABLE links` comes **before** the rename, so the schema reparse the rename triggers (SQLite ≥ 3.25) does not meet trigger bodies naming a table that no longer exists — the same trap [D-082](s13-decision-register.md#d-082) documents from the other direction. And the v7 shape is **pinned as literal text** rather than reusing `ddl::CREATE_LINKS_TABLE`, unlike every other rung on this ladder: those create an index or a derivative table, where getting today's definition is the point, whereas a table rebuild that reads the current constant would silently take a v6 database straight to the v8 shape the day `links` changes again, and stamp it v7. A migration rung is a statement about the past; pinning the text is what makes it one.

**Taken now rather than after 1.0, and that is the whole scheduling argument.** [D-032](s13-decision-register.md#d-032) makes this a baseline re-issue today, which is cheap. [D-036](s13-decision-register.md#d-036) freezes the ledger tables at 1.0, after which the same change is an unmigration. The cost is stated rather than buried: O(rows) in time and roughly 2× `links` in peak disk, on the only rung in this ladder that rewrites a ledger table.

**T2.3 is folded in here rather than given its own decision, because it is the same question answered the other way.** That item asks that [D-060](s13-decision-register.md#d-060) — the overlap guard staying in the write actor — be revisited and *confirmed*, since §4.7 read as though it were unsettled. **Confirmed.** The actor now performs exactly the probe a trigger would, on an index built for it ([D-059](s13-decision-register.md#d-059)), with the statement prepared once ([D-064](s13-decision-register.md#d-064)); moving it into `trg_links_single_open` would add a second index probe to every insert on the path just made fast, to constrain writers who bypassed the actor — and a writer who can bypass a channel can bypass a `PRAGMA`. §4.7 now says "settled" where it said "open". The contrast with row 3 is the useful part: a `CHECK` was affordable precisely because the engine enforces it against the raw connection too, so it does not share row 1's "constrains only the people already behaving" problem, and it costs a comparison rather than an index probe.

Rejected: `CHECK (weight >= 0.0)` alone as specified (admits text, which panics on read, and infinity, which corrupts the log — only probing showed it); adding `AND weight IS NOT NULL` (`REAL NOT NULL` covers it, including NaN — [D-078](s13-decision-register.md#d-078)); deleting the loader guard now that the schema checks (it does not cover `links_current` or pre-v7 cold files); putting the same `CHECK` on `links_current` (it is derivative, rebuilt from `links` by trigger and by `rebuild_current`, so it would constrain the same data twice — and it would make `NegativeEdgeWeight` unreachable and untestable); clamping or dropping offending rows during migration (an edit to an assertion, which is the one thing this ledger does not do); deferring to 1.0 (the migration only gets more expensive, and D-036 makes it impossible).

<a id="d-084"></a>D-084 — `rowid_pk` on `concepts` is deferred to the release that implements erasure, with the trigger condition written down (0.6.0). [Doctrine V](s0-s3-foundations.md#doctrine-v), [D-036](s13-decision-register.md#d-036), [D-051](s13-decision-register.md#d-051), [D-071](s13-decision-register.md#d-071), [D-083](s13-decision-register.md#d-083), [§4.6](s4-schema.md), [§5.9](s5-modules.md#59-vector--search). T2.2 proposes adding `rowid_pk INTEGER PRIMARY KEY` to `concepts` so that FTS5's `content_rowid` can point at a column `VACUUM` cannot renumber. The technical claim is sound and is **not** the reason this is deferred, so both halves are recorded here rather than left as an unexamined omission.

Sound: an `INTEGER PRIMARY KEY` *is* the rowid, so `VACUUM` cannot move it, and `content_rowid='rowid_pk'` would make [D-071](s13-decision-register.md#d-071)'s dense-rowid argument unnecessary rather than merely true-for-now. Lookup by `id` costs the same either way — a `TEXT PRIMARY KEY` on a rowid table is already a unique index plus rowid indirection.

Deferred because it **does not unblock what it is for**. Erasure also needs the FTS delete trigger issuing FTS5's `'delete'` command with `OLD` values, which [§4.6](s4-schema.md) already names as the missing third trigger, and without that a deleted concept stays searchable. Taking `rowid_pk` alone buys nothing today and costs something: `AUTOINCREMENT`, which is what would guarantee non-reuse, writes a `sqlite_sequence` row on every concept insert, and non-reuse only matters once deletion exists. So the ordering is not "cheap thing first" but "the thing that is only correct as part of a set".

**Scheduled, with a condition rather than a version.** The first rung of whichever release implements concept archival or erasure carries: `rowid_pk`, the FTS delete trigger, and a `rebuild_fts()` call. [D-083](s13-decision-register.md#d-083) is the precedent for why they travel together — SQLite has no `ADD CONSTRAINT` and no cheap `ALTER` on a table like this, so each separate visit to `concepts` is another full rebuild, and three changes in one rung cost one rebuild instead of three.

The counter-argument, stated because it is real: D-083 argues a schema change to a ledger table should be taken *now*, pre-1.0, while [D-032](s13-decision-register.md#d-032) makes it a cheap baseline re-issue and before [D-036](s13-decision-register.md#d-036) freezes it. That applies here too, and if erasure lands after 1.0 this becomes expensive for exactly the reason D-083 gives. The difference is that D-083's constraint was independently correct — it closes a live panic and a live corruption path regardless of what ships next — whereas `rowid_pk` is inert until its companions exist. Adding an inert column to beat a deadline is how a schema accumulates fields nobody can explain. If 1.0 approaches with erasure still unscheduled, this decision should be revisited on the deadline argument alone, and that revisit is the obligation this entry exists to create.

Rejected: taking `rowid_pk` alone now (inert, and pays a hot-path `sqlite_sequence` write for a hazard [D-071](s13-decision-register.md#d-071) measured as unreachable); `AUTOINCREMENT` without deletion (buys non-reuse nothing yet consumes); leaving it unrecorded until erasure is designed (an omission with no trigger condition is indistinguishable from an oversight, which is the failure mode this register exists to prevent).

<a id="d-085"></a>D-085 — A historical traversal must state which text it wants, and the shared hydrate chunk gets one definition (0.6.0). [Doctrine II](s0-s3-foundations.md#doctrine-ii), [D-026](s13-decision-register.md#d-026), [D-063](s13-decision-register.md#d-063), [§5.2](s5-modules.md#52-graphbuilderrs--traversal), [§7.5](s6-s10-flows-to-dependencies.md). `TraversalBuilder` returned the past's topology wearing the present's titles and reported that through `tracing::warn!`. A log line is not a boundary: it is invisible in any application that has not configured a subscriber, which is most of them at first run. This was the last silent-wrong-answer path the 0.5.6 cycle documented and did not close.

**Why it could only ever have been a warning before, which the item does not say.** `hydrate_attributes` takes the mode as a parameter and receives a `ts`, and a `ts` is just an instant — nothing in the call distinguishes "as of last Tuesday" from "as of now". So the warning fired on **every** `AttributeMode::Current` hydrate, overwhelmingly the ordinary live case where it is exactly right. Loud where it did not matter and, being a log line, silent where it did. No amount of upgrading `warn!` to an error at that layer would have worked; the information needed to raise one was never there.

So the fix is a representation change first. `TraversalBuilder::as_of(ts)` now exists, which makes "a query about the past" *expressible*; and `attribute_mode` became `Option<AttributeMode>`, where `None` means **defaulted** rather than `Current`. Those two carry exactly the information the decision needs. `execute` returns the new `DbError::AttributeModeUnstated` for the one combination that is a question — `as_of` set, mode never stated — and does what it is told for every other. The error text names both resolutions, because "you must choose" without saying between what is a worse boundary than a warning.

**The fast, mixed answer stays available.** Past topology with live text is a legitimate query — a caller rendering a historical diagram with today's labels wants precisely it — and the objection was always to receiving it without asking, never to asking for it. `.attribute_mode(AttributeMode::Current)` says so and is honoured.

**No existing caller changes.** A traversal with no `as_of` is a query about now, where `Current` and `AtTime` agree about which text to return, so the default stands. That is what keeps this from being a breaking change for everyone in order to fix one combination — the whole suite compiled and passed unaltered.

The test that pins it renames a concept *after* the instant being asked about, so the two modes genuinely disagree. Without that the fixture returns the same string under every mode and the question is invisible — which is precisely how this survived to 0.6.0. Writing it also surfaced Doctrine II inside the fixture: the topology filter is **valid** time while `AtTime` hydration is **transaction** time, and one `as_of` parameter feeds both, so the first version of the test failed by keying the rename on the wrong axis.

**T3.1 folded in.** `HYDRATE_CHUNK` was defined twice — `graph::subgraph` and `temporal::as_of`, both `400`, with the reasoning at one and `// See as_of::HYDRATE_CHUNK` at the other. It now lives in `util::limits` beside the `SQLITE_MAX_VARIABLE_NUMBER` it exists to stay under. The cross-reference comment was itself the evidence: the duplication was known and being managed by convention, and a shared constant is what replaces a convention. The margin check moved from a `#[test]` to a `const` block on clippy's prompting, which is strictly better — both sides are constants, and the failure it guards is someone tuning the value upward, plausibly in a release build without running the suite. `wave1_regression_tests` now derives its straddling fixture size from the constant rather than hardcoding 450, which would have silently stopped straddling anything the moment the constant moved.

Rejected: keeping the `warn!` alongside the error (it fires on the live path, where there is nothing to warn about); flipping the default to `AtTime` (correct at every instant, and it makes every live traversal read `transaction_log` instead of `concepts` — a performance regression on the common path to fix the rare one); comparing `ts` against the wall clock to detect a historical query (no API change needed, and it makes a correctness boundary depend on scheduling and on how stale the caller's `now` is); making `as_of` a required argument of `execute` (breaks every caller to reach the same place).

<a id="d-086"></a>D-086 — Pipelining the bulk paths was implemented, measured, and removed; the deduplication stayed (0.6.0). [D-011](s13-decision-register.md#d-011), [D-058](s13-decision-register.md#d-058), [D-079](s13-decision-register.md#d-079), [§5.1](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor). T3.4 observes that `bulk_import` and its three siblings `await` each chunk before sending the next, so the actor finishes a chunk and idles for a channel round trip before the following one arrives — ~11,000 such gaps on a 1M-edge import, with the 64-slot low-priority queue never more than one deep. It proposes sending *k* chunks ahead and estimates *k* = 2–4 captures most of the win.

**Every observation in that item is true and the conclusion does not follow.** The gaps are real and there are that many of them. They are also **four orders of magnitude smaller than the work they interrupt**: a tokio mpsc hop is sub-microsecond, and a chunk of [`chunk_rows::EDGES`](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor) takes 13–21 ms. The item sizes the win as though the round trip were comparable to the chunk cost.

Implemented and swept at depths 1, 2, 4, 8 and 16 over 20,000 and 100,000 edges, best of three, with the per-kind hold read from the actor's own counters ([D-079](s13-decision-register.md#d-079)):

| edges | depth 1 | depth 2 | depth 4 | depth 8 | depth 16 |
|---|---|---|---|---|---|
| 20,000 | 1,557 ms | 1,573 ms | 1,548 ms | 1,578 ms | 1,578 ms |
| 100,000 | 8,030 ms | 8,037 ms | 8,017 ms | 8,007 ms | 8,041 ms |

Ten cells, all within 1% of sequential, in both directions. The longest hold stayed at 13.8 ms and 21.0 ms throughout, which is the control the sweep exists to check: pipelining changes *when* chunks are sent and never how large they are, so a moving hold would have meant the change did something it should not have.

**It was not free to keep.** With chunks in flight, a failure at chunk *i* no longer leaves a **prefix** committed — chunks *i+1 … i+k−1* were already sent and commit anyway. [D-011](s13-decision-register.md#d-011) promises "a failure partway leaves earlier chunks committed", and a caller recovering from a partial import would no longer be able to assume "everything before the failure, nothing after". Paying for that with a weaker recovery story in exchange for nothing measurable is the wrong trade, so the pipelining came out.

**What stayed is the part that was worth doing anyway.** The four bulk paths had four copies of the same send-and-await loop; they now share `low_chunked`, which is sequential and stops sending at the first error, so what commits is exactly the prefix before the failure. `examples/pipeline_diag.rs` is kept deliberately — the item's reasoning is entirely plausible and will be re-proposed by the next reader of that loop, and the sweep is cheaper to re-run than the argument is to re-have.

Worth noting what this does *not* say. The measurement is against an **embedded, local** libSQL, where the channel hop and the storage are both in-process. A network-backed or replicated deployment would have a round trip that is not sub-microsecond, and there the item's reasoning would hold. That is a different engine profile, not a different chunk size, and it is the condition under which this decision should be revisited.

Rejected: keeping the pipelining at depth 4 because it is harmless (it is not — it weakens D-011's recovery guarantee, and a mechanism with no measured benefit is a mechanism that will not be maintained); keeping it at depth 1 (the machinery would be dead weight around a constant that makes it a no-op); leaving the four duplicate loops in place because the pipelining was rejected (the duplication was a real defect independent of the item that exposed it).

**Fixture: `chain` — the spine, without spurs ([D-088](s13-decision-register.md#d-088), added 0.6.0).** `examples/pipeline_diag.rs` imports `c{i} -> c{i+1}` for 20,000 and 100,000 edges. Shape matters less here than in any other entry annotated in this pass, because the question is *when chunks are sent* rather than what is in them, and the control (the longest hold, which stayed flat at 13.8 ms and 21.0 ms) is what confirms that. It is stated anyway, and the one thing it changes is worth naming: a chain has out-degree 1, so the single-open probe ([D-059](s13-decision-register.md#d-059)) is at its cheapest here and the per-chunk cost is a floor rather than a typical figure.
<a id="d-087"></a>D-087 — `Subgraph` interning passes its own gate and is still deferred, on a cost the plan does not price; the measurement found a cheaper adjacent win (0.6.0). [D-007](s13-decision-register.md#d-007), [D-047](s13-decision-register.md#d-047), [D-063](s13-decision-register.md#d-063), [D-073](s13-decision-register.md#d-073), [§5.4](s5-modules.md#54-graphsubgraphrs-and-graphalgorithmsrs--native-in-memory-analytics). [D-063](s13-decision-register.md#d-063) retired the integer-index rewrite on **CPU** grounds, and that measurement is sound: load dominates every algorithm at every size tested. T3.3 observes the **memory** argument was never made, and sets an explicit gate — measure *edges per budget*, not milliseconds, and skip if the budget is not what actually stops real callers.

**The gate is passed.** Measured by the loader's own accounting (`examples/budget_density_diag.rs`), an edge costs two adjacency entries because `add_edge` stores a full `EdgeRef` in `out_adj` and a clone in `in_adj`, each carrying an owned id and two owned 27-byte timestamps:

| id length | bytes/edge now | interned | edges per MiB now | interned | ratio |
|---|---|---|---|---|---|
| 8 | 342 | 48 | 3,066 | 21,845 | **7.1×** |
| 26 (ULID) | 378 | 48 | 2,774 | 21,845 | **7.9×** |
| 64 | 454 | 48 | 2,309 | 21,845 | **9.5×** |

`size_of::<EdgeRef>()` alone is 104 bytes — four `String` headers and an `f64` — before a single byte of payload. Interned to `{u32, u32, f64, u32, u32}` it is 24 with no heap payload at all. This is a **reachability** improvement, the category [D-073](s13-decision-register.md#d-073) used, and it needs no schema change.

**Deferred anyway, on a cost T3.3 does not price.** `Subgraph`, `EdgeRef` and `NodeData` are public types with public fields, read directly by every algorithm and constructed directly by tests and callers. Interning is not an internal representation change; it is a breaking change to the crate's main read-side data structure, and 0.6.0 is a hardening cycle whose other items are deliberately additive or invisible. Scheduled for 0.7.0 with the API break named, rather than smuggled into a release that promised not to move anything.

**The measurement also found something cheaper, which is the part worth acting on first.** The same sweep asked where the budget actually goes, at 20 edges per node:

| content bytes/concept | node bytes | edge bytes | edges' share |
|---|---|---|---|
| 0 | 37,800 | 1,368,000 | 97% |
| 200 | 77,800 | 1,368,000 | 95% |
| 2,000 | 437,800 | 1,368,000 | 76% |
| 20,000 | 4,037,800 | 1,368,000 | 25% |

So interning wins big exactly when concepts are small, and is swamped when they are large. And `load_subgraph_with` **always** hydrates `content` — its rustdoc says so plainly, "`attribute_mode` is ignored" — while **no graph algorithm reads it**: `dijkstra`, `astar`, `louvain`, `k_core`, `scc` and `modularity` touch topology and weights only. A caller running Louvain over a corpus of 20 KB documents is spending three quarters of the byte budget on document bodies that the algorithm will not look at.

That is a smaller change than interning, in the opposite regime, and the two are complementary rather than alternatives: dropping `content` helps when nodes dominate, interning helps when edges do. Recorded here rather than acted on because it is a new finding rather than a plan item, and because `Subgraph` carrying live concept text is a documented property that some caller may be relying on — the fix is a load option, not a silent change of what the type contains.

Rejected: doing the interning now (a public API break in a hardening release); keying it on `rowid_pk` as an earlier proposal did (sparse and unbounded, so it still needs a map rather than a vector — and it would drag in [D-084](s13-decision-register.md#d-084)'s deferred schema change); re-litigating [D-063](s13-decision-register.md#d-063) (its CPU finding is not disputed and this does not rest on it); dropping `content` from `Subgraph` unconditionally as part of this decision (it is what the type has always carried, and changing that quietly is the failure mode this register exists to prevent).

**Fixture: none — measured on `Subgraph`'s own byte accounting ([D-088](s13-decision-register.md#d-088), added 0.6.0).** `examples/budget_density_diag.rs` computes bytes per edge from `size_of::<EdgeRef>()` and the loader's own formula, and builds its node-share table by hand at a fixed 20 edges per node. No database and no graph shape is involved, which is why the conclusion generalises where a timing would not — the arithmetic is the same on every shape, and only the *edges-per-node* ratio that decides whether it matters is shape-dependent. `dense_small` is where it matters most and `chain` where it matters least.
<a id="d-088"></a>D-088 — The fixture matrix, and the shape a figure was taken on becomes part of the figure (0.6.0). [D-047](s13-decision-register.md#d-047), [D-059](s13-decision-register.md#d-059), [D-063](s13-decision-register.md#d-063), [D-070](s13-decision-register.md#d-070), [D-076](s13-decision-register.md#d-076), [§8](s6-s10-flows-to-dependencies.md#8-testing-strategy), [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets). T4.1 is the plan's own "most important item", on the grounds that one fixture shape produced [D-070](s13-decision-register.md#d-070)'s wrong conclusion, T0.1's invisibility, and [D-059](s13-decision-register.md#d-059)'s still-open note that the chunk constants are empty-database figures needing "a realistic fixture, which requires deciding what 'realistic' means." Four shapes now exist in `tests/fixtures.rs`, each named for the cost it is the worst case for: `star_of_stars` (hub out-degree; the existing one), `clustered` (path enumeration, Louvain), `chain` (recursion depth, snapshot fold length), `dense_small` (the `DISTINCT` sort, the byte budget). `benches/budgets.rs` no longer carries its own copy of the star — `seed_edges` delegates to `Shape::StarOfStars`, so the shape every pre-0.6.0 §9 figure was taken on is now a named member of the matrix rather than an anonymous local function.

**The headline number, which is the item's whole case.** `load_subgraph` at *comparable coverage* — each shape at the depth it needs to reach 90% of itself, so the rows are the same size of problem:

| shape | depth | nodes | load |
|---|---|---|---|
| `star_of_stars` | 2 | 600 | **3.06 ms** |
| `chain` | 485 | 541 | 23.2 ms |
| `clustered` | 89 | 541 | 235 ms |
| `dense_small` | 1 | 300 | 259 ms |

§9's `load_subgraph` budget is a measurement of the first row. The spread across shapes at comparable size is **77×**, and none of it was visible before.

**Coverage, not depth, and this correction is the part T4.1 does not contain.** The obvious way to build the table is to fix the depth, and the first version did. At a fixed depth of 3 the four shapes reach **600, 25, 6 and 300** nodes — so that table compares a 600-node problem against a 6-node one and reports the difference as a property of the shape. That is [D-070](s13-decision-register.md#d-070)'s error committed inside the file written to prevent it: a frame nobody checked. `depth_to_cover` exists so a shape-crossing measurement has to say which variable it holds fixed. Depth is the right control for "what does one more hop cost"; coverage is the right control for "what does this shape cost at comparable size", and the two answer different questions.

**A second correction, to my own first draft.** `Facts` initially called its path count "the CTE's row count". It is not: T0.1 replaced `UNION ALL` + a `path` column with a plain `UNION`, which dedupes on `(node_id, depth)` and bounds the walk at `reached × (depth+1)`. The number is retained and renamed `simple_paths`, with the caveat stated on the type, because it remains the metric that separates a tree from a graph — and because it is the cost that *returns* the instant path semantics are reintroduced, which T0.1's own rustdoc argues is a live risk since the two forms have equal reachability and every test passes under either. Reported beside `union_bound`, their ratio is what T0.1 bought: **22,127× on `dense_small`** (26,552,696 simple paths against a bound of 1,200) and **0.25× on `star_of_stars`** — the only fixture that existed when T0.1 was written.

**`clustered` had to be rebuilt once, and the reason is the finding in miniature.** The first version linked each community as `i -> j, i < j`, which reads as dense and is a **DAG**: path length is bounded by community size and the walk stays near-linear. Measured at 9×, it would have shipped as a weaker `star_of_stars` under a name promising a different question. Both directions make each community strongly connected — what Louvain and `scc` are actually looking for — and take the same walk to 47×. `fixture_matrix_tests` pins that, along with the other property each shape was chosen for, and `the_matrix_discriminates` asserts the four *differ* from each other, because four fixtures that behave alike are one fixture.

**The rule this exists to enforce**: a performance decision entry names the shape it was measured on. [D-070](s13-decision-register.md#d-070)'s would have read "inherent on `star_of_stars`", and the gap would have been a sentence in the entry rather than a wave.

Rejected: putting the fixtures in `src` behind a feature (dev-only code in the shipped library, and a `fixtures` feature in `[[bench]] required-features` makes a plain `cargo bench` skip the benchmarks silently — the path-include follows `tests/harness.rs`, whose cost is one empty test binary); scaling `dense_small` with the bench scale factor (edge count is `n(n-1)`, so it is minutes of fixture construction at any interesting node count, and the shape's point is density at a *small* node count — capped at 300 and pinned as a stated property); changing `star_of_stars` while moving it (every pre-0.6.0 figure is on that arithmetic and altering it would orphan the record); deriving `Facts::reached` from the path enumeration in the depth sweep (`O(simple_paths)`, which is 26.5 million at depth 3 on `dense_small` and unbounded above it — `reach_by_depth` is one BFS).

**The rule was applied prospectively, and that was half the item (added later in 0.6.0).** The matrix and the rule landed together and only the *new* entries named their fixture, which left nine older performance decisions reading as though their figures were general — exactly the condition this entry exists to end, one level up. They are annotated now: [D-047](s13-decision-register.md#d-047), [D-055](s13-decision-register.md#d-055), [D-059](s13-decision-register.md#d-059), [D-063](s13-decision-register.md#d-063), [D-064](s13-decision-register.md#d-064), [D-070](s13-decision-register.md#d-070), [D-076](s13-decision-register.md#d-076), [D-086](s13-decision-register.md#d-086), [D-087](s13-decision-register.md#d-087). Three things came out of doing it that arguing about it would not have produced. [D-063](s13-decision-register.md#d-063) **already named its fixture** ("on the star-of-stars fixture, three hops from the root"), which is why its CPU finding has survived unchallenged where [D-070](s13-decision-register.md#d-070)'s did not. [D-055](s13-decision-register.md#d-055) is the largest single instance: all twelve §9 budget rows, the project's public statement of what it costs, on one shape. And [D-087](s13-decision-register.md#d-087) needed an **opt-out** rather than a shape — it was measured on `Subgraph`'s own byte accounting with no database at all, which is why the rule now admits `**Fixture: none — …**` as an answer that still requires a sentence.

`every_performance_decision_names_its_fixture` in `tests/fixture_matrix_tests.rs` keeps the annotations from rotting, and caught [D-086](s13-decision-register.md#d-086) — written in this same cycle and already unannotated — on its first run. Its limitation is stated in the test rather than hidden: the list of performance entries is hand-maintained, so a *newly added* one is not detected. What is enforced is that an existing annotation cannot quietly disappear and cannot name a shape the matrix lacks, since the accepted names come from `Shape::name` rather than a second list. The first version matched the bare word and accepted "chain" out of "snapshot chain"; it matches backticked names only, because a tripwire that fires on prose is one that gets disabled.
<a id="d-089"></a>D-089 — Plan-pinning becomes a registry keyed by index, which found two indexes with no reader (0.6.0). [D-042](s13-decision-register.md#d-042), [D-059](s13-decision-register.md#d-059), [D-064](s13-decision-register.md#d-064), [§4.4](s4-schema.md#44-indices), [§8](s6-s10-flows-to-dependencies.md#8-testing-strategy). T4.2 observes that [D-042](s13-decision-register.md#d-042), [D-059](s13-decision-register.md#d-059) and [D-064](s13-decision-register.md#d-064) are one bug three times — *a covering index captures a query because it contains the columns, not because it discriminates* — each found by measurement after it shipped, each answered with one more reactive `EXPLAIN` test. It proposes the rule: every query with an index dependency ships with a plan assertion.

**Implemented in the other direction, and that is what made it find something.** `tests/index_plan_tests.rs` is keyed by *index*, not by query: every entry in `ddl::CREATE_INDICES` must name the query that justifies it, and `every_index_is_justified` fails if an index is added without one. The query-keyed form catches a query that leaves its index — which is what the three reactive tests do, and they are kept. It cannot catch an index that **no query ever seeks on**, because there is no query to write an assertion against. That is pure cost: an index write on every insert into its table, forever, read by nothing.

**Two of the six are exactly that.**

- `idx_annotations_label` — nothing in the crate selects from `analytics_annotations` at all. It is written by `write_analytics_annotations` and read only by callers, through their own connection.
- `idx_lc_tgt_active (target_id, valid_to)` — no query in the crate seeks on `target_id` as a leading column. Every `links_current` predicate either leads on `source_id` (the walk) or binds all three key columns (the two guards), and `Subgraph::in_adj` is built in Rust from the forward rows the walk already returned.

Verified rather than inferred: `examples/index_coverage_probe.rs` confirms both indexes *would* be chosen by a query of the obvious shape, so this is "nothing runs that query", not "the planner declines the index". The cost is not hypothetical — [D-059](s13-decision-register.md#d-059)'s own note weighs "a fourth index write per assertion" as a price worth arguing about, and `idx_lc_tgt_active` is one of those four on the crate's hottest write path.

**Recorded and scheduled rather than dropped.** Removing an index is a schema change needing a `DROP INDEX` rung, in a release whose other items are additive or invisible — the same reason [D-084](s13-decision-register.md#d-084) and [D-087](s13-decision-register.md#d-087) were deferred. `the_unread_indices_are_the_two_already_known` pins the set, so a third joining them is a red test rather than a line of DDL nobody revisits. Scheduled for 0.7.0 alongside the other schema work.

The registry reproduces private query constants, which is the hazard `migration_tests` already documented for trigger bodies. `every_reproduced_query_still_exists_in_its_source` bounds it by `include_str!`ing the module each query came from and matching a fragment, whitespace-normalised because the sources are CRLF — compile-time, no widened API surface, and red when the original moves.

Rejected: making the fold and archive SQL constants `pub` so the test could explain the real string (widens the public surface to serve a test, when `include_str!` gets the same guarantee); dropping the two indexes in this release (a schema rung, and [D-036](s13-decision-register.md#d-036)'s freeze deserves the same care an addition gets); leaving them undocumented because they might be useful to a future query (an index whose justification is a query nobody has written is the definition of the cost this entry names).

<a id="d-090"></a>D-090 — The bench control row is enforced by the group constructor rather than by a convention (0.6.0). [D-047](s13-decision-register.md#d-047), [D-055](s13-decision-register.md#d-055), [D-070](s13-decision-register.md#d-070), [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets). [D-070](s13-decision-register.md#d-070) measured ~29% session-to-session noise in this project's absolute timings and recorded the consequence as a caveat. A caveat is only as good as the next reader's memory of it, and the failure is silent: a 20% regression and a 20% quiet machine print identically. T4.3 proposes a fixed trivial operation as row zero of every bench group.

Taken, with one change of form. T4.3 says "add a control row to every group", and a rule of that shape is followed until the next group is added in a hurry — so the control lives in the **constructor**: `controlled_group` is the only way to obtain a `BenchmarkGroup` in `budgets.rs`, and it has already added the row before it returns. `tests/bench_control_tests.rs` keeps the back door shut with three assertions, the third of which matters more than it looks: the control must have exactly one spelling, or two criterion series appear and a baseline comparison silently compares a group against a control it did not have last time.

The control is a `SELECT 1` round trip on a process-wide in-memory connection, not a CPU loop: the noise being corrected for is thermal state, the scheduler *and* libSQL's own overhead, and a hashing loop tracks the first of those and none of the rest.

**Measured, on the first run that used it.** Two back-to-back `traversal` runs on a quiet machine:

| | run 1 | run 2 | absolute | as a ratio to control |
|---|---|---|---|---|
| `control/select_1` | 1.639 µs | 1.589 µs | −3.0% | — |
| `three_hop_warm` | 1.704 ms | 1.635 ms | −4.0% | **−1.0%** |
| `as_of_edges` | 720.3 µs | 700.0 µs | −2.8% | **−0.2%** |

The control absorbs most of the drift, which is the claim. This is a quiet pair of runs rather than the cross-session case [D-070](s13-decision-register.md#d-070) measured at 29%, so it demonstrates the mechanism rather than bounding it.

What this does not do is normalise the numbers automatically — criterion measures each row independently and the division is still the reader's. The value is that the divisor is now *present in the same run*, which is what makes the ratio computable at all; converting the caveat into an enforced row was the item's stated goal and is what was taken.

Rejected: a pure-CPU control (misses IO and engine overhead, which is where this project's noise mostly lives); one control per file rather than per group (criterion groups can run in any order and separately via a filter, so a per-file control is not in the same measurement window as most of what it would normalise); post-processing `target/criterion` into a ratio table (a second tool to maintain, and the numbers it would consume are already printed).

<a id="d-091"></a>D-091 — `diagnostic_conn()` is a boundary where `read_conn()` is a guardrail, and `raw()` becomes undiscoverable rather than unavailable (0.6.0). [D-019](s13-decision-register.md#d-019), [D-050](s13-decision-register.md#d-050), [D-068](s13-decision-register.md#d-068), [D-069](s13-decision-register.md#d-069), [§4.7](s4-schema.md#47-what-this-schema-does-not-enforce), [§5.1](s5-modules.md#51-connectionrs--the-handle-the-pragmas-and-the-write-actor). T5.1 begins by pointing out that a read-only diagnostic connection **already exists** — `read_conn()` carries `PRAGMA query_only = ON` — and that the real question is therefore only what to do about `raw()`. It then makes the sharper point: `query_only` is per-connection and reversible by its holder in one statement, so it is a guardrail and not a capability boundary, and `read_conn()` hands back a *shared* `&Connection`, so it does not serve a caller who wants their own.

**Both halves of that were measured rather than accepted** (`examples/readonly_open_probe.rs`, libSQL 0.9.30, against a live WAL database with the actor running):

| | `read_conn()` | `diagnostic_conn()` |
|---|---|---|
| `SELECT`, `EXPLAIN QUERY PLAN` | allowed | allowed |
| `INSERT` | refused | refused |
| `PRAGMA query_only = OFF` | allowed | allowed |
| `INSERT` after that | **allowed** | **refused** |

The last row is the entire difference and the reason the new method exists. Rows two and three would look identical for a second `query_only` connection, so `tests/diagnostic_conn_tests.rs` asserts the pair in **both** directions: turning the pragma off must restore writes on the reader (or §4.7 invariant 2 is describing something else) and must not on the diagnostic connection.

**One finding the item does not anticipate, and it runs the other way.** `CREATE TEMP TABLE` **succeeds** on a `SQLITE_OPEN_READ_ONLY` connection and is refused by `read_conn()` — temp tables live in a separate writable temporary database, whereas `query_only` refuses them outright. That is precisely the mechanism [D-050](s13-decision-register.md#d-050) measured when it removed `TwoPhaseTempTable` for returning `SQLITE_READONLY (8)` on the read connection. So the stronger boundary is not uniformly stronger, and one of D-050's two reasons for removing that strategy no longer applies to every connection this crate can offer. Recorded, not acted on: D-050 had a second reason (`vector_top_k` refuses a fourth argument and there is no allow-list to push into) and that one is untouched.

**`raw()` is `#[doc(hidden)]`, and the `raw-access` feature T5.1 also offers was rejected on a specific cost.** A feature is the stronger declaration — it appears in the consumer's `Cargo.toml`, where a reviewer sees it. But Cargo features are additive and cannot be *required* by a test target except through `required-features`, which makes a plain `cargo test` **skip** that binary silently. The binaries that call `raw()` are `storage_boundary_tests` and `wave1_regression_tests`: the §4.7 tripwires, whose whole job is to fail when a documented gap moves. Gating them would mean the ordinary `cargo test` stopped running the tests that enforce the section this item is about, in order to make a declaration about a hatch — the same "suite quietly does less than it appears to" failure the project already names for R15 reporting. So the hatch stays reachable and stops being discoverable, and the legitimate-use list in its rustdoc shrinks from three items to one: *provoking a guard*. [D-068](s13-decision-register.md#d-068) is unchanged; removing `raw()` would still buy the appearance of a guarantee, since the file is reachable by any SQLite client on the machine.

A missing file gets its own error variant rather than `NotFound`, which renders "node {0} not found" — [D-069](s13-decision-register.md#d-069) is this project's record of what an error naming the wrong subject costs, and a database file is not a node. `SQLITE_OPEN_READ_ONLY` drops `SQLITE_OPEN_CREATE` with it, so a missing path is `SQLITE_CANTOPEN` rather than a fresh empty database — the right behaviour and an opaque thing to receive. The test for it asserts the **rendering and not the branch**, said plainly in the test rather than glossed: deleting the file underneath an open `Database` fails with OS error 32 on Windows (verified) and `close()` consumes the handle, so no in-process sequence reaches that branch.

Rejected: the `raw-access` feature (above); making `raw()` private ([D-068](s13-decision-register.md#d-068), unchanged); returning a `&Connection` from `diagnostic_conn` and caching one on the handle (the point is that the caller gets *their own*, so a long reporting query does not compete with every traversal in the process); reusing `NotFound` for the missing file; closing §4.7 invariant 2 on the strength of this (it closes one of three holes — the free `register_model` / `upsert_embedding` still take a bare connection, and the file is still reachable by any client).

<a id="d-092"></a>D-092 — R15's load-bearing claim is defended by a soak with a positive control, and the snapshot chain gets a cross-check that reports rather than repairs (0.6.0). [Doctrine VI](s0-s3-foundations.md#doctrine-vi), [D-030](s13-decision-register.md#d-030), [D-043](s13-decision-register.md#d-043), [D-049](s13-decision-register.md#d-049), [D-053](s13-decision-register.md#d-053), [D-071](s13-decision-register.md#d-071), [D-079](s13-decision-register.md#d-079), [R15](s11-s12-milestones-and-risks.md#r15), [§5.5](s5-modules.md#55-temporalreplayrs--reconstruction-and-snapshots).

**T5.2 — the soak.** R15's mitigation rests on *"production exposure is nil by construction — an application opens one `Database` and holds it for its lifetime"*, and nothing tested it. The plan already sharpens the claim (`open_inner` opens three connections, four with the cadence, so the honest statement is **one process, one file, a bounded set of connections opened once and never churned**) and already requires a **control arm**, without which a clean result cannot be told apart from a harness that provoked nothing.

*The instrument had to be a subprocess runner, and that is the part worth recording.* The fault is a process-level access violation: not a panic, not a SQLite error, nothing to catch and nothing to assert on. A `#[test]` that provoked it would take its whole binary down and be reported — as the plan itself documents — as *fewer passing tests and no failures*. So `examples/r15_soak.rs` re-executes itself with `--child` and tallies exit codes, `-1073741819` being `0xC0000005`.

| arm | shape | result |
|---|---|---|
| `claim` | one long-lived `Database`, cadence on, 16 concurrent readers running `load_subgraph` + `reconstruct`, actor saturated | **0 / 10** at 15 s, **0 / 6** at 60 s |
| `control` | the same, plus a task opening 48 databases concurrently in the same process | **2 / 10** at 15 s |

About 8.7 minutes of continuous load in the claimed-safe shape with no fault, in a session where the control faulted twice — both within the first three seconds, which is when the open storm ramps. **The claim is defended and can now be cited**, in its sharpened form. It is a rate and not a proof, and the trigger is still concurrent *open*.

The upstream report is still not filed. The reproduction is written; filing it needs credentials this project's tooling does not hold, so it stays an open item rather than a completed one.

**T5.3 — the snapshot chain.** `write_final` calls `reconstruct`, which composes onto the previous snapshot whenever one is usable, so snapshot *n* descends from snapshot *n−1* and nothing in the chain ever folds the whole log. An error at any link is copied forward indefinitely and every read agrees with it, because every read descends from it. `verify_snapshot_chain` folds from genesis — by withholding the snapshot directory, so `snapshot_anchor` finds nothing and the second computation is genuinely independent — and compares.

*It reports and does not repair, and that is a decision rather than caution.* Under [Doctrine VI](s0-s3-foundations.md#doctrine-vi) a snapshot is derivative and disposable, so the repair is *delete the snapshot directory*: one line, available to the caller, correct without this function's help, and pinned by `deleting_the_snapshots_restores_agreement`. What the caller cannot get for themselves is the knowledge that the chain diverged, and rewriting the file would destroy the only evidence that composition has a defect. A divergence is a wrong **cache**, not a corrupt ledger, and the report says so.

*Not scheduled by this crate.* A genesis fold is exactly the cost snapshots exist to avoid, on a log large enough for snapshots to matter — the only case where this is worth running. Putting it in the cadence would hand every application that bill at a moment nobody chose, on a connection shared with nothing. The plan calls it a scheduling problem and the schedule is the caller's.

*The load-bearing test is the tampered one.* A checker only ever seen to pass is the exact shape this project keeps finding defects in — [D-030](s13-decision-register.md#d-030)'s `audit_current` reduced to a constant zero and certified any corruption as clean; [D-071](s13-decision-register.md#d-071)'s FTS `'integrity-check'` reports healthy on an emptied index. So `a_tampered_snapshot_is_caught` writes a **plausible** wrong snapshot — correctly serialised, correctly named, correctly anchored, with one title altered, one concept removed and one edge dropped — and requires the report to name all three. Not a corrupt file, which zstd or bincode would notice; the kind nothing does.

Two comparison details that would otherwise be silent bugs: `seq_anchor` is reported and **never compared**, because the composed answer legitimately anchors at the snapshot it started from plus its delta while the fold anchors at the newest row it saw; and edges are compared as a **set**, because `MaterializedState::edges` is a `Vec` with no declared order and a reordering is not a divergence — a false positive here is worse than useless, since the whole meaning of a report is "go and find the bug".

Rejected: running the cross-check on the cadence (above); repairing on divergence (destroys the evidence, and the caller already has a correct one-line repair); comparing `MaterializedState` with `PartialEq` (would report anchor and ordering differences as divergences); returning a bool (a divergence needs the disagreeing rows to be actionable); an unbounded report (a chain that went wrong early disagrees about every row — capped at `ChainCheck::SAMPLE_LIMIT` with a `truncated` flag, pinned by `the_report_is_bounded`).
