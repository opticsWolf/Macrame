## §13 Decision Register

Each entry records the decision, its rationale, and — where an alternative was seriously considered — the disqualifying flaw.

<a id="d-001"></a>D-001 — libSQL as dependency, not fork (0.1.0). [Doctrine I](s0-s3-foundations.md#doctrine-i). Forking inherits a C codebase and an upstream merge burden; the project has two engineers. Every capability we need — WAL, JSON1, window functions, ATTACH, user_version, F32\BLOB, DiskANN — is in the public, stable surface.

<a id="d-002"></a>D-002 — transaction_log replaces CDC (0.2.0). [Doctrine IV](s0-s3-foundations.md#doctrine-iv). The WAL and replication frame log are engine-owned: truncated, compacted, checkpointed at the engine's discretion. A ledger built on them inherits their lifecycle. An ordinary table with an ordinary index has a retention policy we own. Rejected: CDC consumption — the frames can vanish beneath us.

<a id="d-003"></a>D-003 — 5-column bitemporal PK on links (0.2.0). The 4-column key (source, target, type, valid_from) cannot express re-assertion after mistaken retirement without mutating history. Adding recorded_at makes every assertion a distinct row. [Doctrine III](s0-s3-foundations.md#doctrine-iii).

<a id="d-004"></a>D-004 — links_current materialization (0.2.0). Latest-belief resolution via window function inside every traversal hop would tax every query forever. A trigger-maintained materialization moves the cost to write time (one upsert per assertion) and makes traversals index-simple. The WHERE excluded.recorded_at > links_current.recorded_at clause makes out-of-order inserts unable to roll belief backward. Cost: a second structure — auditable and rebuildable ([Doctrine VI](s0-s3-foundations.md#doctrine-vi), [§5.8](s5-modules.md#58-integrity--audit-and-rebuild)).

<a id="d-005"></a>D-005 — Per-model embedding tables (0.2.0). A shared F32_BLOB(768) column would hold mixed dimensions during a model migration; per-model tables make migration additive. [Doctrine VII](s0-s3-foundations.md#doctrine-vii).

<a id="d-006"></a>D-006 — AttributeMode with log hydration (0.3.0-A). The honest price of [§4.4](s4-schema.md#44-asymmetric-versioning-deliberately)'s asymmetry: Current / AtTime / Omit, with a runtime warning when Current meets as_of. Rejected: a concepts_current twin — a permanent join tax on every hop.

<a id="d-007"></a>D-007 — Byte-budget cost model for vector-filter strategies (0.3.0-A). Strategy selection by estimated bytes touched, not by rule of thumb; estimates logged so tuning is empirical.

<a id="d-008"></a>D-008 (revised 0.5.3) — Archive guard via main.sqlite_master probe. SQLite forbids a trigger in main from referencing objects in another database, temp.sqlite_master included; the restriction is enforced by the trigger compiler at CREATE TRIGGER time, so the original 0.4.0 design fails during migration and never reaches runtime. The guard instead probes main.sqlite_master for a marker table macrame_archive_session, created as the first statement and dropped as the last statement of the single archive transaction ([D-012](s13-decision-register.md#d-012)). Connection-locality — the property the temp probe was reaching for — is preserved by two independent mechanisms: uncommitted DDL is visible only to the writing connection, so no other connection ever sees the marker; and the archive transaction holds the write lock for its duration, so no other connection can reach the guard at all. The marker cannot outlive the transaction: commit drops it, rollback discards it, and there is no crash path that leaves the guards disarmed — which is structurally stronger than the temp marker, which would have persisted on the Write Actor's connection had the archive code ever failed to drop it. One behavioural shift: an ad-hoc DELETE issued during an archive transaction receives SQLITE_BUSY (lock contention) rather than ArchiveViolation (trigger abort). The outcome is identical — the delete is blocked — and the busy error is arguably the more informative of the two. Note also that BEFORE DELETE is a row trigger: a DELETE against an empty guarded table fires nothing and succeeds trivially, which is harmless because it removes nothing. Rejected: temp.sqlite_master probe (engine restriction, unimplementable); a persistent marker in main created and dropped in separate transactions (opens a window in which ad-hoc deletes from any connection are permitted — a [Doctrine V](s0-s3-foundations.md#doctrine-v) violation).

<a id="d-008a"></a>D-008a — Concepts carry an unconditional delete guard (0.5.3). Because concepts are never physically archived ([D-022](s13-decision-register.md#d-022)), there is no session in which deleting a concept row is legal. trg_concepts_guard_delete therefore has no WHEN clause and no marker probe: it aborts every physical delete unconditionally. Physical concept removal for legal compliance remains out of scope and outside the archive path ([Appendix C](appendices.md#appendix-c--future-considerations-deliberately-deferred)).

<a id="d-008b"></a>D-008b — transaction_log carries a delete guard (0.5.3). The archive path removes superseded log rows ([§5.7](s5-modules.md#57-temporalarchivers--cold-storage), Archive scope), so transaction_log is a hot table from which the archive session deletes — and [Doctrine V](s0-s3-foundations.md#doctrine-v) requires that every such table refuse deletes outside the session. The 0.4.0–0.5.2 DDL guarded concepts and links but left transaction_log unprotected, meaning the ledger itself was the one hot table an ad-hoc DELETE could truncate. It now carries the same marker-probing guard as links.

<a id="d-009"></a>D-009 — Reject the Mutex-wrapped shared write connection (0.4.5). A mutex serializes acquisition but not occupancy: a 50K-row transaction holds the file lock end-to-end, and the UI queues behind the whole job. The lock is held at the file-system level for the duration of a transaction; only bounded transactions plus controlled succession can cure it. Rejected: tokio::sync::Mutex, read-write lock variants (same occupancy problem).

<a id="d-010"></a>D-010 — Two-tier biased channel over a generic priority queue (0.4.5). Two mpsc arms and biased select! give strict preemptive ordering at every transaction boundary with zero allocation and no dependency; a third tier is one arm away. Rejected: heap-based scheduler, per-command priority fields — machinery for a problem two tiers solve.

<a id="d-011"></a>D-011 — Cooperative chunking at 500–1,000 rows (0.4.5). The priority queue cannot preempt a running transaction; bounding chunk duration to 2–3 ms bounds UI latency to the same. Rejected: unbounded bulk commands (starvation), time-based slicing mid-statement (impossible — the lock is per-transaction).

<a id="d-012"></a>D-012 — Archive stays a single atomic transaction (0.4.5). Copy-then-delete must be atomic, or a crash between phases duplicates or loses rows; archive is therefore the one scheduled lock hold that exceeds a chunk, and it runs at idle ([R7](s11-s12-milestones-and-risks.md#r7)). Rejected: chunked archive with cross-chunk verification — not crash-safe.

<a id="d-013"></a>D-013 — rebuild_current on the high-priority tier (0.4.5). Drift repair is a corrective act triggered by audit; it must not queue behind analytics. It is a single millisecond-scale transaction, so the preemption is cheap.

<a id="d-014"></a>D-014 — Chunked writes are not transaction-time atomic; the atomic variant is explicit (0.4.5). Each chunk is a distinct learning event with its own recorded_at; reconstruct mid-write sees a prefix. Callers needing all-or-nothing visibility pay one stall, knowingly, via write_analytics_results_atomic. [Doctrine VIII](s0-s3-foundations.md#doctrine-viii) applied to the write path: fidelity is a parameter.

<a id="d-015"></a>D-015 — No automatic writer restart (0.4.5). A dead writer means a bug; a respawn would mask it and re-enter on a connection whose last-transaction state the caller cannot reason about. Containment (typed errors) plus reopen is the policy; tracing reports the death. Restart remains available as a recorded deferral ([Appendix C](appendices.md#appendix-c--future-considerations-deliberately-deferred)).

<a id="d-016"></a>D-016 — Withdraw transaction() from the public surface (0.4.5). A caller-held closure can hold the write lock for arbitrary time — the exact starvation 0.4.5 removes. Every normative operation in [Appendix A](appendices.md#appendix-a--public-api-normative) is expressed through typed methods; the BEGIN IMMEDIATE … COMMIT shape survives as the actor-internal unit of work.

<a id="d-017"></a>D-017 — Unify all identifiers to snake_case (0.5.0). The prior document mixed snake_case declarations with flatcase usage in primary keys, triggers, and prose — residue of multiple editing passes. One convention, declared in [§4](s4-schema.md#4-schema)'s preamble, enforced by review. Rejected: flatcase (loses word boundaries); quoting all identifiers (verbose, fragile, non-idiomatic).

<a id="d-018"></a>D-018 — recorded_at monotonicity trigger on concepts (0.5.0). [Doctrine II](s0-s3-foundations.md#doctrine-ii) requires the two clocks to be independent, but nothing in the 0.4.5 schema enforced this for concept updates. A BEFORE UPDATE trigger rejecting non-advancing stamps closes the gap at the engine level. This is a constraint, not a default. Rejected: application-level validation only (breakable by the next endpoint, script, or migration tool).

<a id="d-019"></a>D-019 — PRAGMA query_only = ON on read connections (0.5.0). The write-serialization guarantee was enforced by Rust ownership. query_only converts the ownership invariant into a runtime enforcement at the engine level. Cost: one pragma per connection open. Rejected: relying on ownership alone (defense in depth is cheap and permanent).

<a id="d-020"></a>D-020 — Rename "checkpoint" to "snapshot" for the application-level concept (0.5.0). SQLite uses "checkpoint" for WAL-to-main-file truncation. Two different operations sharing a name is a persistent source of confusion. The rename is cosmetic but permanent. Rejected: coexistence with disambiguation comments (comments rot; naming doesn't).

<a id="d-021"></a>D-021 — Explicit PRAGMA recursive_triggers = OFF (0.5.0). SQLite defaults recursive triggers to OFF, which is correct here. But relying on a default for a correctness property is fragile. Stating the pragma makes the dependency visible. Cost: one line in configure().

<a id="d-022"></a>D-022 — Concepts are never physically archived (0.5.1). The archive path targets only links (closed intervals) and transaction_log (superseded rows). Concepts remain in the hot database permanently, managed by retired (soft-delete) and valid_to (temporal expiry). Three structural reasons: (1) FK constraints on embeddings*.concept_id would be violated or require CASCADE, destroying embeddings; (2) F32_BLOB and DiskANN indexes are libSQL-specific and do not exist on the ATTACHed cold database; (3) concepts are entities, not intervals — they have no "closed" state analogous to a retired edge. The trg_concepts_guard_delete trigger remains as a safety net. Rejected: physical concept archival with embedding extraction (structurally infeasible without a custom serialization layer that [Doctrine I](s0-s3-foundations.md#doctrine-i) forbids); ON DELETE CASCADE on embeddings (silently destroys [Doctrine VII](s0-s3-foundations.md#doctrine-vii) artifacts).

<a id="d-023"></a>D-023 — rebuild_current() stays atomic; sizing note added (0.5.1). A chunked rebuild would create a window where links_current is partially populated, and concurrent traversals would silently omit edges — a correctness failure worse than a latency stall. The rebuild is therefore a single atomic transaction, and the lock-hold cost is documented ([§5.8](s5-modules.md#58-integrity--audit-and-rebuild)): ~500 ms at 100K edges, ~5 s at 1M, ~50 s at 10M. Operational guidance: run at startup or idle; in normal operation (triggers functioning), drift should be zero and rebuild should never be needed. The high-priority status is retained because it governs ordering (fix before the next analytics chunk), not urgency (fix before the user's next click). Rejected: chunked rebuild with a "rebuilding" flag blocking traversals (adds a second consistency mode to an already complex temporal model; the flag itself becomes a failure mode if the rebuild crashes mid-chunk).

<a id="d-024"></a>D-024 — seq_id is strictly monotonic, not gap-free (0.5.1). SQLite AUTOINCREMENT guarantees monotonicity and non-reuse, but a rolled-back transaction still increments sqlite_sequence, leaving a gap. **(Mechanism corrected in 0.5.4 — see [D-049](s13-decision-register.md#d-049). Measured against libSQL 0.9.30, a rollback also undoes the `sqlite_sequence` write, so the number is reused and no gap appears. Gaps are real all the same: the archive path deletes superseded rows from `transaction_log`, scattered through the sequence. The rule below stands; the reason given for it did not.)** The prior document's "strict, gap-free total order" claim was incorrect. All replay and delta-fold logic uses inequality comparisons (seq_id > :anchor), which skip gaps correctly. The prose is corrected and a gap-tolerance test is added ([§8](s6-s10-flows-to-dependencies.md#8-testing-strategy)). Rejected: application-level gap detection and backfill (adds complexity for a property the logic does not require; the inequality comparisons are already correct).

<a id="d-025"></a>D-025 — SystemClock monotonicity floor (0.5.1). SystemClock::now() returns max(wall_clock, last_issued + 1μs). On construction, it queries MAX(recorded_at) from the database and floors the interior state, so that a restart after an NTP backward correction cannot issue a timestamp older than the newest row. This guarantees that trg_concepts_monotonic_ra never rejects a legitimate update due to clock drift. FakeClock is monotonic by construction. Rejected: relying on the OS clock alone (NTP corrections can move the wall clock backwards; the monotonicity trigger would reject legitimate updates); disabling the trigger for the first update after restart (creates a [Doctrine II](s0-s3-foundations.md#doctrine-ii) violation window).

<a id="d-026"></a>D-026 — Cold-database read path via per-query ATTACH (0.5.2). When reconstruct(ts) targets a ts older than the hot log's horizon, the replay module ATTACHes the archive database on read_conn, folds a UNION ALL of main.transaction_log and cold.transaction_log with the identical window-function query, then DETACHes. ATTACH/DETACH bracket exactly one fold and never persist, so no file handle is held between calls and a moved cold file cannot leave a stale handle. The hot entry wins for entities present in both files because its seq_id is greater — the same last-writer-wins rule as snapshot composition. If the cold file is absent, the module returns a typed ReplayCorrupt rather than a wrong answer ([R14](s11-s12-milestones-and-risks.md#r14)). Rejected: a persistent ATTACH at open() (holds a file handle for the process lifetime and fails hard if the archive is moved); merging cold rows into the hot log before folding (defeats the purpose of archiving and re-inflates the hot file).

<a id="d-027"></a>D-027 — Strict SystemClock timestamp parsing with graceful fallback (0.5.2). SystemClock::new() parses MAX(recorded_at) with a strict in-crate parser for the exact format the crate produces (YYYY-MM-DDTHH:MM:SS.ffffffZ, plus second-precision backward compatibility), rejecting offsets and missing Z. On parse failure it falls back to SystemTime::now() with a tracing::warn! — never a startup panic; the monotonicity trigger ([§4.3](s4-schema.md#43-the-transaction-log)) prevents a corrupt stored timestamp from propagating into new writes. SQLite's lexicographic MAX() is safe because [§4.1](s4-schema.md#41-concepts-and-per-model-embeddings) mandates a single fixed UTC Z format. (Corrected in 0.5.4: as written in 0.5.2 this was not true. [§4.1](s4-schema.md#41-concepts-and-per-model-embeddings) mandated a Z suffix but no fixed width, and mixed-precision values do not order lexicographically — see [D-029](s13-decision-register.md#d-029). The claim holds only under the canonical form 0.5.4 introduces.) Rejected: chrono/time dependency (one call site does not justify the dependency); panicking on parse failure (a corrupt row must not make the database unopenable); accepting arbitrary ISO-8601 (this is a crate-internal format; strictness catches corruption early).

<a id="d-028"></a>D-028 — Timeout is not cancellation on the write path (0.5.2). A HighPriCommand awaiting its oneshot responder waits in Rust, not in SQLite, so busy_timeout does not bound it; during an in-flight rebuild_current() or archive() transaction the caller stalls for that transaction's duration while WAL readers remain unaffected. Every write method's rustdoc states this and shows the tokio::time::timeout pattern. Dropping the responder does not cancel the command — it remains queued and commits when the actor yields; for a ledger, an asserted fact is asserted whether or not anyone is still listening. True abandonment is an application-layer CancellationToken checked before send. Rejected: crate-level command cancellation (would require the actor to dequeue and discard, adding a failure mode — a "cancelled" command that actually ran — for a property the ledger does not want); making busy_timeout the documented bound (it does not apply to channel waits and would mislead callers).

<a id="d-029"></a>D-029 — Canonical timestamp form: fixed width, not merely a Z suffix (0.5.4). [Doctrine II](s0-s3-foundations.md#doctrine-ii). Every temporal column is exactly 27 characters, YYYY-MM-DDTHH:MM:SS.ffffffZ, enforced by a table-level CHECK (GLOB) on concepts, links, links_current, and transaction_log. The prior rule — "ISO-8601 text with an explicit Z suffix, because they must sort lexicographically" — named the right requirement and specified an insufficient mechanism. Two values that differ only in precision do not order lexicographically: '2026-01-01T00:00:00Z' <= '2026-01-01T00:00:00.000000Z' is FALSE, since 'Z' (0x5A) sorts after '.' (0x2E). Every comparison in the system is lexicographic — SQL valid-time predicates, the traversal CTE's join condition, MAX(recorded_at) in SystemClock::new(), Rust str ordering in Interval — so the defect's blast radius is the whole temporal surface, and its failure mode is silence: a traversal whose edges all fail the predicate returns the anchor node alone, with no error to attribute it to. This manifested as a real test failure (a 3-node traversal returning 1) once the schema first installed successfully. The sentinel widens to 9999-12-31T23:59:59.999999Z for the same reason: an exempt value is a carve-out that reintroduces the bug, and the all-nines form is also the maximum representable instant, which is what [valid_from, valid_to) requires. Enforcement is at the storage layer because the failure is silent — a convention cannot be violated loudly, a CHECK can. util::timestamp::normalize() widens the legacy second-precision form at the boundary; offsets, missing Z, and other precisions are typed errors. Rejected: normalizing only in Rust (leaves every raw SQL path, migration, and external tool free to write mixed precision — and the crate's own test suite was exactly such a path); comparing via SQLite datetime() (reintroduces the ambiguous type [§4.1](s4-schema.md#41-concepts-and-per-model-embeddings) exists to avoid, and defeats index use); keeping the second-precision sentinel as a special case (the carve-out above).

<a id="d-030"></a>D-030 — audit_current() counts the symmetric difference (0.5.4). [Doctrine VI](s0-s3-foundations.md#doctrine-vi). The 0.4.5–0.5.3 query chained four compound-SELECT arms flatly: A EXCEPT B UNION B EXCEPT A. SQLite gives EXCEPT and UNION equal precedence and evaluates them left-associatively, so this parses as (((A EXCEPT B) UNION B) EXCEPT A), which reduces to a constant zero — the audit reported "no drift" for every possible state of the database, including a links_current deliberately corrupted by the test suite. An integrity check that cannot fail is worse than no integrity check, because it is trusted. Parentheses do not fix it: SQLite rejects a parenthesised compound-SELECT operand outright. The corrected query names both sides as CTEs and computes each direction inside its own scalar subquery, summing the two — the grouping is then structural rather than syntactic, so no future edit can silently regroup it. Both directions are required: a row links_current lacks is a missed materialization, a row it holds that the projection does not is a stale or spurious one, and either alone is drift. Rejected: a one-sided EXCEPT (misses missed-materialization drift entirely); COUNT(*) equality between the two relations (equal cardinality with different contents reports clean).

<a id="d-031"></a>D-031 — format_iso8601_utc and parse_iso8601_utc are real implementations (0.5.4). The 0.5.2 skeleton stubbed both: the formatter hard-coded a literal date and derived only the time-of-day from the SystemTime, so every stamp the crate produced claimed the same calendar day regardless of the clock; the parser validated the Z suffix and then returned SystemTime::now() unconditionally, so SystemClock's monotonicity floor ([D-025](s13-decision-register.md#d-025)) was seeded with wall-clock time rather than with MAX(recorded_at) and the restart-after-NTP-correction guarantee did not hold. Both are now implemented over Hinnant's civil-calendar algorithm in util::timestamp — around sixty lines, no chrono dependency, consistent with [D-027](s13-decision-register.md#d-027)'s rejection. The parser validates the calendar as well as the shape, so 2026-02-30T00:00:00.000000Z is rejected rather than accepted as a timestamp no round-trip can reproduce; :60 is rejected because SystemTime counts SI seconds and has no slot for a leap second, and aliasing it to :59 would break the strictly-increasing clock contract. Rejected: leaving the stubs pending a chrono dependency (the monotonicity floor is a doctrinal guarantee, not a nicety).

<a id="d-032"></a>D-032 — Legacy-free schema baseline at user_version = 2 (0.5.4). Macrame is pre-1.0 and declares no on-disk compatibility: there is no migration path into the canonical form, only a baseline that applies to an empty database. The baseline is numbered 2 rather than 1 because builds before 0.5.4 stamped user_version = 1 over the pre-canonical schema — no CHECK constraints, second-precision timestamps, the narrow sentinel. Had the canonical baseline reused the number 1, such a file would open silently and every guarantee [D-029](s13-decision-register.md#d-029) buys would be void on it while user_version insisted all was well; reserving 1 as a value the ladder refuses by name is what makes "no legacy support" an enforced property rather than a README sentence. migrations::run() reads user_version before writing anything and refuses three cases with a typed DbError::Migration: a version greater than this build's (operating on a schema you do not understand is how a ledger loses history); a version with no rung leading out of it, which is exactly the pre-0.5.4 v1; and an unstamped database that already holds objects, since user_version defaults to 0 and an unrelated SQLite file is otherwise indistinguishable from a fresh one. Each rung runs in one BEGIN IMMEDIATE transaction with the version stamp inside it, so "the schema exists" and "the schema is declared to exist" are the same commit and a crash mid-step leaves a database still honestly at its old version. A post-condition check counts the objects sqlite_master actually holds against what the DDL arrays declare, because CREATE … IF NOT EXISTS hides precisely the failure that matters: an object that exists with a different definition is silently kept. Rejected: retrofitting the canonical form by table rebuild (correct engineering for a released system, unjustifiable ceremony for a pre-1.0 crate with no deployed data — and the rebuild's two traps, sqlite_sequence continuity under AUTOINCREMENT and the [D-008](s13-decision-register.md#d-008) delete guards, are failure modes bought for nothing); accepting v1 databases unchanged (silently voids [D-029](s13-decision-register.md#d-029)); a no-op version guard without a ladder (the mechanism is needed the first time the schema moves, and building it against a single known rung is cheaper than retrofitting it under pressure).

<a id="d-033"></a>D-033 — One classification boundary for engine error text (0.5.4). SQLite reports a RAISE(ABORT) as a generic constraint failure carrying the message, so the message text is the only thing distinguishing "you violated the single-open-interval rule" from "the disk is full". error::abort_kind() is the sole place in the crate that matches on engine error text; classify() turns an AbortKind plus a WriteOp into the typed error [§7](s6-s10-flows-to-dependencies.md#7-errors) specifies, and archive::classify_archive_violation delegates to it rather than carrying a second copy of the needle. The needles themselves are the schema::ddl::ABORT_* constants spliced into the trigger DDL by concat!, so the guard and its classifier are the same string by construction, with a unit test asserting each constant appears in some trigger. Scattered string matching fails silently in the worst direction: an upstream wording change degrades an unknown number of typed errors into opaque Engine errors that no caller can match on, and nothing announces it. Concentrated, a change breaks one function and the tests covering it. classify() takes a connection because RecordedAtRegression reports the value it clashed with and the trigger does not put it in the message — one extra query on an error path buys an error a caller can act on. Rejected: matching at each call site (the failure above); parsing SQLite extended result codes instead (a RAISE(ABORT) carries SQLITE_CONSTRAINT_TRIGGER for every guard, so the code cannot tell them apart).

<a id="d-034"></a>D-034 — Write commands carry typed payloads, not SQL strings (0.5.4). The 0.4.5 skeleton declared WriteBulkAtomic { rows: Vec<String> } and the chunked background commands as Vec<String>. Whatever those strings were meant to be, the only thing an actor can do with a Vec<String> is execute it, which makes the write channel an arbitrary-SQL channel: it bypasses edge-type validation, timestamp canonicalisation ([D-029](s13-decision-register.md#d-029)), and every typed error [§7](s6-s10-flows-to-dependencies.md#7-errors) defines, and it means the sole write connection will execute whatever any caller in the process hands it. The commands now carry EdgeAssertion and ConceptUpsert values, validated and canonicalised at the public boundary before they cross the channel, so a malformed edge type or a second-precision timestamp is a typed error at the call site rather than an engine CHECK failure surfacing from the far side of an actor with no context attached. HighPriCommand::execute and LowPriCommand::execute are exhaustive matches with no wildcard arm — the pre-0.5.4 `_ => LoopCtl::Continue` dropped the responder for four of six high-priority and all three low-priority commands, and a dropped responder is indistinguishable from a hung database from the caller's side. Exhaustiveness makes that a compile error rather than a runtime silence; Database::high()/low() additionally map a send failure to WriterUnavailable and a dropped responder to WriterDroppedResponder, so the actor going away is a typed error rather than a wait that never ends. Rejected: keeping Vec<String> with a validation pass over the strings (validating SQL by inspecting it is the problem, not the solution); a WriterUnavailable stopgap for unimplemented arms (correct while arms are missing, but all nine are now implemented and exhaustiveness is the stronger guarantee).

<a id="d-035"></a>D-035 — Archive re-derives links_current instead of describing the deletion's shadow (0.5.4). [Doctrine II](s0-s3-foundations.md#doctrine-ii), [Doctrine VI](s0-s3-foundations.md#doctrine-vi). archive() deletes from links under LINKS_ARCHIVABLE and must leave links_current equal to the latest-belief projection of what remains. As written in 0.5.2 it did so with a hand-written compensating statement, DELETE FROM links_current WHERE valid_to <> sentinel AND valid_to <= :cutoff — a predicate over *valid* time standing in for one that also requires recorded_at < :cutoff. The two are not the same set. An interval closed at the cutoff but recorded at or after it fails LINKS_ARCHIVABLE and survives in links, while the compensation deletes it from links_current: permanent drift, produced by the archive path itself, that no later audit can explain and only a rebuild can clear. The compensation is now integrity::rebuild::rebuild_within(&tx), executed inside the archive transaction, so the materialization is re-derived from the definition rather than from a second description of it. A description of a set can drift from the set; a derivation cannot. The same commit made rebuild_current() transactional in its own right — it had been a bare DELETE followed by an INSERT, and the window between them is the whole of current belief, so a failure across it (or a concurrent reader landing in it) sees a graph with no edges and no error, contradicting [D-023](s13-decision-register.md#d-023)'s atomicity claim in the code that claimed it. Found by property test, not by inspection: the defect requires a cutoff that separates an interval's valid time from its transaction time, and every seeded test in the suite used a cutoff comfortably after both. Rejected: adding recorded_at < :cutoff to the compensating DELETE (restores agreement today and reinstates the same failure mode — two predicates that must be kept identical by hand); auditing after the archive and rebuilding only on drift (the archive transaction has already committed by then, so the window is real, and a repair conditional on a check is only as good as the check).

<a id="d-036"></a>D-036 — 1.0 on-disk compatibility contract: core-frozen, periphery-rebuildable (0.5.4). Macrame 1.0 commits to strict on-disk backward compatibility for the normative ledger tables (concepts, links, transaction_log). Post-1.0 schema changes to these are restricted to additive operations: ALTER TABLE ADD COLUMN and new indexes. Changing a primary key, dropping a column, or altering bitemporal semantics is forbidden and requires a major version with an explicit ETL migration path. Bitemporal data is the hardest data to migrate: a changed links PK cannot be repaired by CREATE TABLE AS SELECT, because doing so means replaying history, re-resolving conflicting assertions, and recomputing transaction-time boundaries — an operation that rewrites the past, which [Doctrine III](s0-s3-foundations.md#doctrine-iii) forbids. Freezing the core also plays to SQLite's shape: ADD COLUMN is exact and cheap, while a table rebuild requires a temp table, drops and recreates every trigger attached to the original, and invalidates the WAL. Conversely, derivative tables — links_current ([Doctrine VI](s0-s3-foundations.md#doctrine-vi)) and the per-model embedding tables ([Doctrine VII](s0-s3-foundations.md#doctrine-vii)) — carry no schema-stability guarantee at all. A minor version needing a different materialization drops the table, recreates it from the DDL, and calls integrity::rebuild::rebuild_within() inside the same migration step transaction; a model change adds a new embeddings table and leaves the old one for the previous model. The bifurcation is exactly [Doctrine VI](s0-s3-foundations.md#doctrine-vi)'s "source-of-truth or rebuildable, there is no third category," applied to time rather than to structure.

Two mechanical premises were verified rather than assumed, both in tests/compat_contract_tests.rs. First, the additive escape hatch preserves [D-029](s13-decision-register.md#d-029): SQLite has no "add table constraint", so the table-level canonical_ts_check! covering today's columns cannot be extended, and an additive temporal column would have no canonical-form guard unless ADD COLUMN accepts a *column-level* CHECK. It does, and enforces it, and the ALTER leaves all nine triggers intact — so the rule is that any post-1.0 temporal column must carry its own inline CHECK, and the contract would otherwise have silently readmitted the mixed-precision ordering defect on a schema nobody is permitted to rebuild. Second, the periphery is genuinely disposable: dropping links_current entirely, recreating it from DDL, and rebuilding from links reproduces it byte for byte, which is the executable form of the claim that no information lives solely in the materialization. The frozen shapes themselves are pinned by PRAGMA table_info assertions — a change detector before 1.0, a release blocker after it.

Rejected: full on-disk compatibility including derivative tables (buys nothing — the tables are reconstructible by definition — and forfeits the ability to ever change the materialization strategy); no compatibility commitment at 1.0 (a ledger whose central promise is that the past is never rewritten cannot also reserve the right to rewrite the format the past is stored in — [D-032](s13-decision-register.md#d-032)'s legacy-free stance is correct precisely because it is pre-1.0, and it expires at 1.0); a single ladder arm per release with an `unreachable!()` default (the ladder must remain a loop that composes steps, and a panic on an unrecognised user_version turns an unfamiliar file into a crash instead of the typed DbError::Migration refusal [D-032](s13-decision-register.md#d-032) requires).

<a id="d-037"></a>D-037 — F32_BLOB dimension enforcement is carried by the vector index, not by the column type (0.5.4). [Doctrine VII](s0-s3-foundations.md#doctrine-vii). **This entry corrects [§4.1](s4-schema.md#41-concepts-and-per-model-embeddings), which was wrong.** The pre-0.5.4 text stated that libSQL rejects a wrong-dimension vector at insert time, and drew the conclusion that the crate-level check in embedding.rs "exists for error quality" while "the engine-level check exists for correctness". Measured against libSQL 0.9.30: a two-float blob inserted into a column declared F32_BLOB(4) is **accepted** when the table carries no vector index, and rejected — with the row not landing — once a libsql_vector_idx index exists, reporting "vector index(insert): dimensions are different: 2 != 4". Enforcement is therefore a property of the DiskANN index, not of the declared column type. Two consequences follow and both are now structural. First, register_model() creates the table and its index in one transaction and there is no supported way to have one without the other, because a per-model table without its index is a table with no dimension enforcement at all — which also means dropping the index to accelerate a bulk load silently disarms the only storage-layer check, and it must not be offered as an option. Second, the crate-level check is not merely cosmetic, so it had better be real: search_vector() previously called EmbeddingCodec::encode(query_vec, query_vec.len(), model), comparing the vector's length against itself, which made the check true by construction and DimMismatch unreachable through the search path. It now resolves the dimension by reading F32_BLOB(n) back out of PRAGMA table_info for the model's table. That is deliberate: the declared dimension in the schema is the single copy, so the Rust-side check and the engine-side one cannot disagree, and the crate holds no registry of its own to fall out of date — the same reasoning [D-035](s13-decision-register.md#d-035) applied to the archive's compensating delete. Both halves of the asymmetry are pinned by tests, including the negative one on an unindexed table; if libSQL ever begins enforcing the column type itself, that test fails and this entry should be revisited rather than quietly outgrown. Rejected: a macrame-maintained model registry table (a second description of a fact the schema already states, which is the drift [D-035](s13-decision-register.md#d-035) exists to prevent); trusting the declared type without the index (measured false); accepting the caller's asserted dimension (that is precisely the tautology being removed).

<a id="d-038"></a>D-038 — Migration verification checks for required objects by name, not by counting sqlite_master (0.5.4). The 0.5.4 verify() compared the number of tables, triggers and indices against expected totals and refused to open the database on any mismatch. The intent was sound — catch a CREATE … IF NOT EXISTS that no-ops instead of creating — but a total is the wrong instrument, because it treats every *extra* object as corruption. Three legitimate sources of extras now exist: a registered embedding model adds embeddings_<model> ([D-037](s13-decision-register.md#d-037)), libSQL's vector index adds libsql_vector_meta_shadow plus a shadow table and shadow index per model, and [D-036](s13-decision-register.md#d-036) explicitly permits post-1.0 migrations to add indexes. Under the counting check, registering a single model made a healthy database fail verification on its next open, with a message blaming the schema version. Verification now asserts the presence of each required object by name and reports exactly which are missing. The names are parsed out of the CREATE_TRIGGERS and CREATE_INDICES arrays rather than kept in a parallel list, so adding a trigger extends what verify() requires with nothing else to remember. Rejected: raising the expected counts (restores the bug the moment a second model is registered); excluding embeddings_% and %_shadow from the count (an allowlist of everything that may exist, maintained by hand, versus a checklist of what must exist — the latter is what the check is actually for); dropping verification (it is the only guard against IF NOT EXISTS silently no-opping).


<a id="d-039"></a>D-039 — Native graph analytics, dropping petgraph (0.5.4). [Doctrine I](s0-s3-foundations.md#doctrine-i). The in-memory analytics surface is exactly five algorithms — Dijkstra, A*, SCC, k-core, Louvain — over an adjacency list, and it is now owned in-crate. petgraph is rejected because the translation cost it was supposed to save was already being paid: SubgraphLoader built a HashMap<String, NodeIndex> by hand on the way in and mapped NodeIndex back to ULIDs on the way out, so the dependency bought a graph representation the crate immediately wrapped. Only four items of its surface were used (DiGraph, NodeIndex, algo::dijkstra, algo::tarjan_scc), Louvain was never among them, and a k-core and an A* over ULID keys had to be written regardless. Rejected: petgraph (a dependency whose entire used surface is smaller than the adapter around it); graaf (maturity risk for a pre-1.0 project); keeping petgraph solely for its track record (addressed below).

Three things this decision is honest about. First, what was replaced was not working code. `louvain_communities` assigned every node its own index and returned — the all-singletons partition, labelled "basic community detection" — so the fact it was named after an algorithm it did not implement is what made the gap invisible. Second, the guideline's proposed acceptance test for Louvain, that modularity be non-decreasing against the singleton partition, is satisfied by construction by exactly that stub; [§8](s6-s10-flows-to-dependencies.md#8-testing-strategy)'s oracle for Louvain is therefore an upper bound (modularity must not exceed the enumerated optimum over all set partitions) rather than a lower one. Third, replacing a well-used library forfeits its track record, and the substitute for that is differential testing rather than assurance: every algorithm is checked against an independent brute-force definition — exhaustive simple-path enumeration for Dijkstra and A*, an O(V³) reachability closure for SCC, recompute-from-scratch peeling for k-core, and enumeration of every set partition via restricted growth strings for Louvain. The oracles were confirmed to have teeth by mutation: `scc` with its second pass walking out_edges instead of in_edges — Kosaraju minus the transpose — is caught and shrunk to a two-node counterexample, which is kept in tests/graph_property_tests.proptest-regressions with a note recording that the defect never shipped.

Determinism is a property of the data structures, not of a sort applied at the end. Subgraph uses BTreeMap, the algorithms return BTreeMap/BTreeSet rather than the hashed equivalents, and every tie is broken explicitly — equal-distance heap entries by node id, equal-gain Louvain moves by the lower community index. Any one of the three left as a HashMap reintroduces per-process variation, and in Louvain's case a different partition run to run: Rust's default hasher is seeded per process, so a caller iterating a HashSet result to write it back emits rows in a different order every run. Distances additionally need a total order that f64 does not have; OrdF64 wraps total_cmp so a NaN weight cannot corrupt the heap's invariant silently.

Two defects in adjacent code were found while doing this and are fixed here. TraversalBuilder spliced edge types into the CTE as quoted literals via format!("'{t}'"), and validate_edge_type — whose own doc comment cited the CTE as its justification — runs only from EdgeAssertion::normalized on the write path, so a traversal never passed through it. Edge types are now bind parameters: unlike a table name, an edge type is a value, and values can be parameters, so the question is removed rather than answered (contrast [D-037](s13-decision-register.md#d-037), where a model name is an identifier and validation was the only option). And TraversalBuilder stored attribute_mode, exposed a builder method for it, and never read it — build_sql always emitted the Current join — so a caller asking for AtTime received live attributes with no indication the mode had been ignored, which is the silent wrong answer [Doctrine II](s0-s3-foundations.md#doctrine-ii) exists to prevent. Hydration now runs as a second step through the already-correct hydrate_attributes.

Two further gaps are recorded rather than closed. DbError::SubgraphTooLarge existed in the error enum but was constructed nowhere, so [D-007](s13-decision-register.md#d-007)'s byte budget was declared and unenforced; load_subgraph now measures during the load and both halves are tested. And links.weight is a bare REAL NOT NULL with no CHECK, while Dijkstra and A* are only correct for non-negative weights — a negative weight would yield a shortest path that is merely a path. Adding a CHECK constraint is a schema change against the [D-036](s13-decision-register.md#d-036) freeze and is not taken unilaterally; load_subgraph refuses such an edge with a typed NegativeEdgeWeight instead, which puts the failure at the boundary. Whether the constraint should also exist in the schema is open.

<a id="d-049"></a>D-049 — Snapshot composition is implemented; the anchored fold is the first code [D-024](s13-decision-register.md#d-024) has ever bound (0.5.4). Closes [D-046](s13-decision-register.md#d-046). `reconstruct(ts)` now selects the newest snapshot at or before `ts`, folds the hot log above its anchor with `seq_id > :anchor AND recorded_at <= :ts`, and merges under last-writer-wins by `seq_id` — the same rule `trg_links_current_sync`'s upsert applies and the same rule the cold fold applies. `Database::reconstruct(ts)` wires the archive path and the snapshot directory from the handle, so composition is the default rather than something a caller opts into by remembering two arguments.

**Absence and deletion are different facts, and composition is where the difference starts to matter.** The pre-0.5.4 fold treated a winning `'D'` row as `continue` and a `retired = 1` concept as "do not insert". Folding from nothing that is right — both end as absence. Composed onto a snapshot they are opposites: the entity is *in* the base, and skipping the row leaves it standing as though nothing had happened. Tombstones are therefore collected and applied, and the full fold runs the same code against an empty base, so there is one path rather than two that must agree.

The acceptance gate is a property test: for a generated history with a snapshot taken mid-way, composed and full-fold results must agree at every transaction-time instant in the delta. That is [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots)'s "three paths, one rule, verified by the property suite" made executable — the claim had been in the document since 0.4.5 with nothing behind it.

**Two things this exposed, both worth recording.** First, the property test *passed under mutation* on its first run: dropping the tombstone changed nothing, because the generator had no operation that produced one. `Op::RetireConcept` was added and the mutation then failed, shrinking to a two-operation history ending in the retirement. A gate for the exact defect the design is about, satisfied by construction because the generator could not reach the case, is the same failure as [D-030](s13-decision-register.md#d-030)'s audit and the pre-[D-039](s13-decision-register.md#d-039) Louvain oracle — the third time this cycle a test has needed mutation to show it was asserting nothing.

Second, **[D-024](s13-decision-register.md#d-024)'s stated mechanism is wrong and is corrected below.** It attributes `seq_id` gaps to rolled-back transactions. Measured against libSQL 0.9.30: `sqlite_sequence` is written inside the transaction, so a rollback undoes it and the number is reused — `INSERT`, `BEGIN … INSERT … ROLLBACK`, `INSERT` yields ids `1, 2`, not `1, 3`. Gaps in the hot log are real regardless, because the archive path deletes superseded rows from `transaction_log` ([§5.7](s5-modules.md#57-temporalarchivers--cold-storage)) and those are scattered through the sequence rather than forming a prefix. So [D-024](s13-decision-register.md#d-024)'s rule is right and its reason was not; the gap-tolerance test builds the state the real mechanism produces, by deleting a log row inside a session marker, and fails under `seq_id = :anchor + 1`.

**Composition is disabled once an archive database exists, and that is a correctness requirement rather than caution.** Because archived rows are scattered, a row above the anchor and at or before `ts` can be gone from the hot log while a newer row for the same entity — recorded *after* `ts`, and so invisible to this fold — is what displaced it. The delta would miss it, the snapshot would answer with the older value, and the result would be wrong with nothing to indicate it. The full fold is slower and right. Composing across the archive boundary needs the cold log in the delta, which is a larger change and stays open. Note the same reasoning applies to `hot_log_covers`, which decides the cold path on `MIN(recorded_at)` — that is also not a sound completeness test after a scattered archive, and is recorded as open rather than fixed here.

Anchor selection loads candidates newest-first and stops at the first whose timestamp is at or before `ts`, so `reconstruct(now)` reads exactly one file. `SnapshotIncompatible` ([D-043](s13-decision-register.md#d-043)) is skipped rather than raised: an incompatible snapshot is the ordinary consequence of an upgrade, and being able to carry on without it is the entire reason that variant is distinct from corruption.

Still open, and not closed by this entry: **there is no snapshot cadence.** [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots) specifies a read-side maintenance task writing an anchor every 10,000 log entries; only `close()` writes one. The effect is that a cleanly-shut-down application composes from its shutdown anchor — the common case, and the one that matters most — while a long-running session accumulates an unbounded delta. The cadence is a spawned task whose lifecycle is a decision (owner, stop signal, what `close()` does with it), and it is left as one. Rejected: composing across the archive boundary now (needs the cold log in the anchored fold and a coverage test that is sound after scattered deletion — both larger than this); putting the anchor timestamp in the snapshot header to avoid loading candidates (worth it only if the newest-first scan ever reads more than one file, which `reconstruct(now)` does not); keeping `Database::reconstruct` off the surface (the free function's `None` for the snapshot directory is a correct answer that quietly folds the whole log, and a fast path nobody takes is not a fast path).

<a id="d-048"></a>D-048 — The vector write path goes through the Write Actor; `register_model` goes with it (0.5.4). [Doctrine VII](s0-s3-foundations.md#doctrine-vii), [D-011](s13-decision-register.md#d-011), [D-019](s13-decision-register.md#d-019). Phase 3 was delivered, tested and **unreachable**: `upsert_embedding` and `register_model` both take a `&libsql::Connection`, `Database::read_conn()` carries `PRAGMA query_only = ON`, and the write connection is moved into the actor at `open()` and cannot be named. An application could search vectors it had no way to store. Fifteen passing tests said otherwise because every one of them opened its own connection and reached around the actor — the same shape as [D-041](s13-decision-register.md#d-041)'s annotations and the pre-[D-039](s13-decision-register.md#d-039) Louvain, a capability that is green and absent at the same time, and the third instance this cycle of a test suite certifying its own workaround.

`Database::upsert_embeddings(model, rows)` chunks at `CHUNK_ROWS` onto the low-priority tier behind `LowPriCommand::UpsertEmbeddingChunk`. Low, not high: embedding is bulk derived work, and a 50,000-vector backfill must yield to an interactive assertion at every chunk boundary ([§5.1.5](s5-modules.md#515-cooperative-chunking--the-golden-rule)). Atomic per chunk and not across chunks, following `bulk_import` — and the trade is safer here than there, because an embedding is derived ([Doctrine VII](s0-s3-foundations.md#doctrine-vii)), so a partially written batch is recoverable by re-embedding, whereas a partially written history is not recoverable at all. The declared dimension is resolved **once per chunk**, not once per row: `declared_dimension` is a `PRAGMA table_info` round trip, and it cannot change inside a chunk, because the chunk holds the write lock and only `register_model` creates the table that declares it. No clock reading is taken, because an embedding carries no timestamp on either axis; the ledger already records when the content changed.

**`register_model` moved behind the actor too, and that was a deferred decision rather than an obvious one.** It issues DDL, which everywhere else in this crate is the migration runner's exclusive business ([D-032](s13-decision-register.md#d-032)), and the case for leaving it on a caller-supplied connection was that DDL is setup rather than steady-state work. That case does not survive the gap above: with the write connection actor-owned, "a caller-supplied write connection" is not a thing an application has, so leaving `register_model` outside would have made the write path reachable in principle and not in fact. The exception is bounded — a model's table is created once, by an explicit call, in one transaction ([D-037](s13-decision-register.md#d-037) requires the table and its DiskANN index be created together or dimension enforcement does not exist). It sits on the *high*-priority tier despite being setup, because every embedding write for a model blocks on it and queueing it behind a bulk job would stall the thing it gates.

Five tests, and the constraint on the first is what it *uses* rather than what it asserts: it touches `Database` and nothing else on the write side, so if the only route to a stored vector is again a connection the caller had to build, it stops compiling. The others pin that re-embedding replaces rather than versions and never reaches `transaction_log`; that a bad vector rolls back its whole chunk rather than leaving a prefix; that an unregistered model is a typed `ModelNotRegistered` rather than an engine complaint about a missing table; and that a backfill larger than one chunk lands completely.

Rejected: the high-priority tier for embedding writes (a backfill would preempt the user, which is the starvation [D-009](s13-decision-register.md#d-009) removed); one transaction for the whole batch (unbounded lock hold, and [Doctrine VII](s0-s3-foundations.md#doctrine-vii) makes the atomicity it buys unnecessary); resolving the dimension per row (one `PRAGMA` round trip per vector); keeping a `HashMap<model, dim>` on the handle to avoid the per-chunk read (a second description of a fact the schema already states, which is [D-037](s13-decision-register.md#d-037)'s rejected alternative and [D-035](s13-decision-register.md#d-035)'s defect); leaving `register_model` on a raw connection (per above — it makes the path reachable only for a caller who cannot exist).

<a id="d-047"></a>D-047 — The byte budget is enforced incrementally; the integer-index rewrite of `Subgraph` is deferred until something measures it (0.5.4). [Doctrine VI](s0-s3-foundations.md#doctrine-vi), [D-007](s13-decision-register.md#d-007).

**The defect.** `load_subgraph` called `graph.estimated_bytes()` inside the row loop, and that function is O(V + E) — it walks every node and both adjacency maps. Loading was therefore O(E²), measured on the reference machine at 500 edges in 26 ms, 1,000 in 76 ms, 2,000 in 231 ms: time tripling for each doubling of the input. The irony is exact. The byte budget exists to bound what a hub node in a dense neighbourhood can do to a load, and the budget *check* was the part that did not scale — a graph well inside its budget could take seconds to refuse or accept. Nothing caught it because the one large-graph test (20,000 nodes, SCC depth) builds its `Subgraph` in memory and never goes through the loader; every test that does go through the loader uses a handful of edges.

The fix is a running total carried through the load, and `estimated_bytes()` stays a derivation over the whole graph so a caller can still ask. Two accounts of one quantity is the drift [D-035](s13-decision-register.md#d-035) is about, so they are not two accounts: `node_bytes` and `edge_bytes` are the single definition of the estimate, `estimated_bytes()` sums them over a graph, and the loader adds them as it inserts. `hydrate` now also refuses *inside* its loop rather than after it — checking once at the end allocates the whole oversized result before declining to return it, which is the failure the budget exists to prevent rather than to report. Two tests: one asserting the loader's running total and the derivation give the same number (budget set one byte under the derived total, so an undercount — counting an edge once when `add_edge` stores it twice — fails), and one asserting the growth rate. The second is a ratio and not a duration, because absolute timings are a property of the machine and the growth rate is a property of the algorithm. Its sizes are 8× apart because at 4× the quadratic term does not yet dominate: mutation-tested, the per-row check gives 21.3× against a linear 8.0×, and the bound sits at 16×. A 4× spread measured 8× against an expectation of 4× and no CI-safe bound would have caught it.

**The rewrite is deferred.** The same review proposed carrying five of `petgraph`'s internal design choices into `Subgraph`: integer node/edge indices, topology separated from payloads, explicit directional adjacency, borrowing iterators, and deterministic insertion ordering. Two of the five are already implemented — `out_adj` and `in_adj` have been maintained as a pair since [D-039](s13-decision-register.md#d-039), and `out_edges`/`in_edges` already return borrowed slices, which are *more* capable than the proposed iterators, since `degree()` is `.len()` in O(1) and `k_core` calls it in a loop. Two are real: algorithms key `BTreeMap`s by 26-byte ULID, so every relaxation is a logarithmic number of string comparisons (comparisons, not hashes — `BTreeMap` does not hash), and `add_edge` clones the `EdgeRef` for the reverse direction, so every edge's three strings exist twice.

They are deferred rather than taken because **nobody has measured the algorithms**. The load path dominated everything until this entry fixed it, [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets)'s budgets are documented and not implemented as gates, and the case for a rewrite that touches every algorithm and the public `Subgraph` API should rest on a number rather than on an appeal to a well-engineered crate's internals. The condition for revisiting is a benchmark of Louvain and Dijkstra on a budget-sized loaded graph.

**And the rewrite has a cost the proposal does not price.** Determinism is currently structural: `BTreeMap` in, `BTreeMap`/`BTreeSet` out, explicit tie-breaks. Integer indices assigned in insertion order make it *procedural* — a property of the loader's `ORDER BY` and its `ids.sort()` continuing to be right. Both are right today. But substituting a description of a property for a derivation of it is this project's recurring defect ([D-030](s13-decision-register.md#d-030)'s audit, [D-035](s13-decision-register.md#d-035)'s compensating delete, the Louvain stub), and this instance fails silently in the worst way: a reordered `ORDER BY` would not error, Louvain would return a different partition, and [§8](s6-s10-flows-to-dependencies.md#8-testing-strategy)'s oracle would still pass, because an upper bound on modularity does not detect a *different* valid answer. If the rewrite happens it needs a test that loads one graph under two different SQL orderings and asserts identical index assignment — not a comment saying to sort. Relatedly, the proposal's "sort by ULID **or `recorded_at`**" is not a free choice: `recorded_at` is not a total order over nodes and its ties are unspecified.

Three smaller defects in the proposed blueprint, recorded so a later implementation does not inherit them: its `NodeData` drops `embedding_model`, which the current struct carries and the loader populates; its `ulid_to_idx` stores every id a second time, partly cancelling the memory win that justifies it; and it does not deliver its own second point, because `out_adj: Vec<Vec<EdgeId>>` indexing into `edges: Vec<EdgeData>` still pulls three `String`s into cache to read a `weight` — the separation that pays puts the weight beside the topology, which is what `petgraph` actually does, since for `petgraph` the edge payload *is* the weight.

Rejected: caching the running total as a field on `Subgraph` (the struct's fields are public and tests build graphs by mutating them directly, so a cached field would be silently wrong for any graph not built by the loader — a stale description of state, which is the thing being avoided); keeping the per-row `estimated_bytes()` and raising the default budget (treats a complexity class as a tuning parameter); taking the integer-index rewrite now on the strength of the argument (the argument is sound and the measurement does not exist, and this document's standard since [D-037](s13-decision-register.md#d-037) is that a claim about performance carries a number).

<a id="d-046"></a>D-046 — Snapshot composition is specified and not implemented; [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots), [§4.3](s4-schema.md#43-the-transaction-log) and [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets) are corrected to say so (0.5.4). **CLOSED by [D-049](s13-decision-register.md#d-049) later in the same cycle — the inventory below describes the state this entry was written against, and is kept because the six claims it lists are why the work was scoped the way it was.** Snapshots are written — `close()` calls `write_final`, the file lands atomically, retention runs — and they are read by nothing. `load_snapshot` has no caller in `src/` outside its own module: `reconstruct` folds the hot log, or hot and cold together ([D-026](s13-decision-register.md#d-026)), and never consults a snapshot at any `ts`. Six claims in the document depended on the composition that does not exist, and each is now marked rather than left standing:

1. **The anchored fold does not exist.** `HOT_FOLD` and `COLD_FOLD` filter on `recorded_at <= ?1` alone; there is no `seq_id > :anchor` term anywhere. [§4.3](s4-schema.md#43-the-transaction-log)'s index rationale distinguishes "the unanchored cold-start fold" from "the anchored fold", and only the first is real. This also makes [D-024](s13-decision-register.md#d-024)'s guarantee — that all replay logic uses inequality comparisons and never successor arithmetic — vacuously true rather than satisfied: there is no anchor to compare against, so the discipline is untested at the moment a maintainer first writes one.
2. **The composition and merge rule is unexercised.** [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots)'s "for each entity the fold's row wins; for entities absent from the fold, the snapshot's row stands" never runs.
3. **"Three paths, one rule, verified to agree by the property suite" was false on both halves.** Two paths exist (the `links_current` upsert and the cold fold); the third does not, and no test compares them.
4. **There is no 10,000-entry cadence and no maintenance task.** [§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots) describes "a lightweight maintenance task [that] watches `seq_id` through `read_conn`"; nothing of the kind is spawned. `write_final` on clean shutdown is the only path that writes a snapshot, so an application that crashes, or one that simply runs for a long time, accumulates no anchors at all.
5. **Retention is five newest, flat.** The "plus one daily for thirty days" tier is not implemented.
6. **[§9](s6-s10-flows-to-dependencies.md#9-performance-budgets)'s "with snapshot, ≤ 200 ms at 1M entries" is unreachable**, and the row above it ("snapshot composition expected at this scale") describes an expectation nothing meets.

The consequence is not incorrectness — `reconstruct` returns the right answer — but unboundedness: it costs what the entire log costs, at every `ts`, forever, and the mechanism specified to bound that is the one missing. The gap is recorded here rather than closed because closing it is a real piece of work with a decision inside it (below), and because a document that describes writing-without-reading as a working cache is the same failure [D-037](s13-decision-register.md#d-037) and [D-040](s13-decision-register.md#d-040) corrected elsewhere: prose asserting a capability the code does not have, in a section a reader has no reason to doubt.

What closing it requires: an anchor-selecting read that picks the newest snapshot at-or-before `ts` and is robust to `SnapshotIncompatible` ([D-043](s13-decision-register.md#d-043)) by discarding and falling back to the full fold; an anchored fold variant carrying `seq_id > :anchor`, which is where [D-024](s13-decision-register.md#d-024)'s inequality discipline finally has something to be true about; a merge with the last-writer-wins rule; a property test asserting anchored-plus-snapshot equals full-fold at arbitrary `ts` over generated histories, which is the "three paths, one rule" claim made executable; and a decision on the cadence — the specified maintenance task watching `seq_id` on the read side is one option, and writing an anchor from the actor at a chunk boundary is another that costs the write path something and cannot miss. The read-side watcher is the specified design and should be honoured absent a reason not to.

<a id="d-042"></a>D-042 — A covering index for the traversal CTE, with the column order measured rather than reasoned (0.5.4). [§5.2](s5-modules.md#52-graphbuilderrs--traversal-valid-time-and-attribute-fidelity)'s recursive step ran on `idx_lc_src_active (source_id, valid_to)`, which pushes the seek and the open-interval bound into the index and leaves `valid_from`, `weight` and `edge_type` to be evaluated against a base-table row fetched for every candidate edge at every hop — random IO proportional to degree, not to result size. `idx_lc_traversal_cover (source_id, valid_from, valid_to, weight, edge_type, target_id)` carries everything the walk reads, so `EXPLAIN QUERY PLAN` reports `SEARCH l USING COVERING INDEX … (source_id=? AND valid_from<?)` and the base table is not touched until the terminal join to `concepts`. It subsumes `idx_lc_src_active` — same seek column, strictly more payload — which the `v3 → v4` rung therefore drops rather than keeping alongside; two index writes per assertion on a table that already takes three is a real cost for no read.

**The column order was where the reasoning went wrong, twice, and both errors are worth recording.** The review that prompted this proposed `(source_id, edge_type, valid_from, …)`. Measured against that proposal *with `idx_lc_src_active` still present*, the unfiltered traversal — the default, since `edge_types` is empty unless a caller sets it — declined the new index entirely and kept the old plan, which looked like a decisive argument that `edge_type` must come last. Measured again with the subsumed index dropped, both orders are covering, and the first conclusion was an artifact of the planner having a narrower alternative to prefer. The order still matters, for a smaller and different reason: with `edge_type` ahead of the range columns the unfiltered seek degrades to `(source_id=?)` and the valid-time window becomes a filter across that whole source's slice, while the shipped order constrains `valid_from` in the seek. The test asserts the seek text and not merely the word `COVERING`, because asserting `COVERING` alone passes under both orders — confirmed by mutation, which is also how the original claim was found to be overstated. A plan-shape assertion is the only honest form here: [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets)'s latency budgets are documented and not implemented as gates, so "this protects the budget" is an argument from a number nobody is measuring, whereas the plan is a fact the test can hold. Rejected: `(source_id, edge_type, …)` as proposed (weaker seek on the default query); adding the index while keeping `idx_lc_src_active` (pays for a read nobody gets); leaving it alone pending benchmarks (the benchmarks do not exist, and the plan shape is evidence that does).

<a id="d-043"></a>D-043 — The snapshot file is a versioned container, and an incompatible one is refused rather than parsed (0.5.4). Snapshots were bare `zstd(bincode(MaterializedState))`. `bincode` is not self-describing, so a file written against a different shape of `MaterializedState` does not reliably fail to load — it loads into wrong values, and the newest snapshot is the first thing a restart reaches for, so those values arrive labelled as the most recent state anyone believed. The `PayloadVersion` discipline the log has carried since 0.2.0 ([§4.3](s4-schema.md#43-the-transaction-log)) simply had no counterpart here. Files now open with a ten-byte header — magic `MACR`, a `u16` container format version, and the `u32` `user_version` this build understands — written uncompressed and checked before anything is decompressed, so the decision to reject costs nothing and commits to nothing. The failure is `DbError::SnapshotIncompatible`, deliberately not `ReplayCorrupt`: corruption is a fault to report, an incompatible snapshot is the ordinary consequence of an upgrade, and the two want opposite responses — the second should discard the file and fold from the log, which is a path that already exists. Headerless files from 0.5.4 and earlier are caught by the same check, since their first bytes are zstd's own magic. The container version is bumped when `MaterializedState` changes shape, independently of the schema version, because the two can move apart. Rejected: relying on `bincode` to fail on mismatch (it does not, which is the defect); a `serde` self-describing format such as JSON or MessagePack (pays a permanent size and speed cost on every snapshot to detect a condition a ten-byte header detects for free); versioning by filename (the name already encodes the anchor, and a name is not carried by the bytes if the file is moved).

<a id="d-044"></a>D-044 — A leaked `cold` attachment heals on the way in; the `Drop` guard that suggests itself does not work (0.5.4). Both ATTACH sites ([§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots), [§5.7](s5-modules.md#57-temporalarchivers--cold-storage)) pair with an unconditional DETACH on every `Result` path, which leaves exactly one hole: a panic unwinding between the two skips the DETACH regardless of which exit the `Result` would have taken, and a leaked handle then makes every later `reconstruct` *and* every later `archive` fail with "database cold is already in use" — permanent poisoning of the connection from one transient fault. The reflex fix is an RAII guard whose `Drop` issues the DETACH. **It does not work here:** `libsql::Connection::execute` is `async` and `Drop` cannot await, so such a guard constructs a future, discards it, and leaves the handle attached while presenting as cleanup — strictly worse than the honest single exit path, because it stops anyone looking. `Handle::block_on` inside `Drop` deadlocks on a current-thread runtime, and spawning a detach task races the next ATTACH. Recovery on the way *in* needs no destructor: `detach_stale_cold` issues a best-effort DETACH before each ATTACH, which in normal operation fails harmlessly with "no such database" and after a leak turns permanent poisoning into one failed statement nobody sees. It also works regardless of how the handle leaked, which a guard scoped to one function does not. The hole is currently hypothetical — neither span contains an `unwrap`, an `expect`, or an index — and the fix is taken anyway because it is two lines and the failure it prevents is unrecoverable without reopening the database. Verified by mutation: with the pre-ATTACH detach removed, the test reproduces the poisoning exactly. Rejected: an RAII `Drop` guard (does not execute the statement, per above); `catch_unwind` around the fold (addressed in [D-045](s13-decision-register.md#d-045)); accepting the hole because it is unreached today (the cost of prevention is two lines).

<a id="d-045"></a>D-045 — Actor `catch_unwind` and single-flight read coalescing are both declined (0.5.4). Recorded because both were proposed with sound general reasoning and both are wrong for this system, and an unrecorded rejection gets re-proposed.

*Wrapping the actor's `execute` in `catch_unwind` so a panicking chunk does not kill the writer* contradicts [D-015](s13-decision-register.md#d-015) without engaging it. [D-015](s13-decision-register.md#d-015) declines automatic writer recovery on the grounds that a dead writer means a bug that should surface in a crash report, and that resuming on a connection whose last-transaction state the caller cannot reason about is worse than stopping; catching the unwind and continuing the loop *is* that resumption, and the panic would have dropped a `Transaction` rather than rolling it back explicitly, which is precisely the unknown state [D-015](s13-decision-register.md#d-015) names. The behaviour the proposal treats as the defect — every later call returning `WriterUnavailable` — is the designed containment, and it already works: the panic unwinds the spawned task, the receivers drop, sends fail, and `Database::high`/`low` map that to the typed error ([§7](s6-s10-flows-to-dependencies.md#7-errors), [D-034](s13-decision-register.md#d-034)). The mechanism is also fragile in a way the proposal does not mention: it is a no-op under `panic = "abort"`, a plausible release profile for a desktop binary. If [D-015](s13-decision-register.md#d-015) should be revisited, that is its own decision entry with its own argument, not a wrapper.

*Single-flight coalescing of `reconstruct(ts)`* misreads the workload. The proposal groups `audit_current()` with `reconstruct()` as expensive log folds; `audit_current` never reads `transaction_log` at all — it is a symmetric-difference comparison between `links_current` and a window projection of `links` ([D-030](s13-decision-register.md#d-030)). And the thundering-herd model assumes a server: this is a single process with one shared `read_conn`, so N identical reconstructions serialize on that connection rather than stampeding it. The cost is latency amplification for one user, and the caller — who owns the calling pattern — is the right place to stop firing five identical queries. Most decisively, an in-flight map keyed by `ts` is a second description of derived state, which is the failure class [D-030](s13-decision-register.md#d-030) and [D-035](s13-decision-register.md#d-035) exist to prevent. The sanctioned mechanism for bounding reconstruction cost is already specified: snapshots ([§5.5](s5-modules.md#55-temporalreplayrs-and-temporalsnapshotrs--reconstruction-and-snapshots)), with anchoring and retention defined. Rejected in favour of finishing that — and **that mechanism is specified and not implemented** ([D-046](s13-decision-register.md#d-046)), which this entry owes as a caveat: the argument is that snapshots are the right answer, not that the right answer is already in place. Anyone re-proposing coalescing should be told that composition is the work, not that the problem is solved.

<a id="d-041"></a>D-041 — Analytics annotations belong in a derivative table, not in `concepts.content` (0.5.4). [Doctrine VI](s0-s3-foundations.md#doctrine-vi), [Doctrine VII](s0-s3-foundations.md#doctrine-vii). **Fixed in 0.5.4; the schema gains `analytics_annotations` ([§4.5](s4-schema.md#45-analytics-annotations--the-second-derivative-table-054-d-041)) on the ladder's `v2 → v3` rung.** As shipped through 0.5.3, `Subgraph::write_back_annotations` constructed a `ConceptUpsert` per annotated node and placed the annotation value in the `content` field, so writing back a Louvain partition overwrote every annotated concept's document text with a community label. The 0.4.5 document specified the correct destination and the 0.5.x renumbering lost it along with the rest of [§5.4](s5-modules.md#54-graphsubgraphrs-and-graphalgorithmsrs--native-in-memory-analytics) — the defect and its own specification went missing in the same edit. An annotation is `{ concept_id, label, value }` and belongs in `analytics_annotations`, a derivative table with no log trigger: disposable and rebuildable by re-running the algorithm, which is [Doctrine VI](s0-s3-foundations.md#doctrine-vi)'s second category, and excluded from the ledger by exactly the reasoning [Doctrine VII](s0-s3-foundations.md#doctrine-vii) applies to embeddings.

Three things were wrong with the old destination and only the first is obvious. It destroyed user content. It routed derived data into `transaction_log` through the concept triggers, so the ledger inflated permanently with labels no reconstruction should want. And because a concept `UPDATE` must carry a strictly advancing `recorded_at` ([§4.3](s4-schema.md#43-the-transaction-log), [D-018](s13-decision-register.md#d-018)), re-running the same algorithm on an unchanged graph produced a fresh version of every annotated concept — the ledger recorded the analytics schedule as though it were history. The method's doc comment asserted the write was "a normal bitemporal write and not an edit of history," which was true of the mechanism and false of the intent: that mechanism is right for a domain fact, and a community label is not one. The deeper point is the one the 0.4.5 text made in a single clause and is worth preserving: a reconstruction that needs community labels should recompute them, because a stored label answers what some past run of some past version of the algorithm produced, which is a different question wearing the same name.

What shipped: the table and its index ([§4.5](s4-schema.md#45-analytics-annotations--the-second-derivative-table-054-d-041)); `Annotation` and `Database::write_analytics_annotations`, chunked on the low-priority tier behind a new `LowPriCommand::WriteAnalyticsChunk`; `write_back_annotations` repointed and given a `label` parameter it previously had no way to express; and a `v2 → v3` migration rung, the first time the [D-032](s13-decision-register.md#d-032) ladder has had more than the baseline. Nothing is backfilled — a label that landed in `content` is indistinguishable from the text it replaced, and recomputation is the recovery, which is what this table exists to make cheap. Four tests pin the properties that matter: content untouched, `transaction_log` unchanged across an annotation write, a rerun replacing rather than accumulating *and* not versioning the concept, and the same three through `write_back_annotations` itself. Fixing this also caught a test making [D-038](s13-decision-register.md#d-038)'s mistake — `verification_counts_every_declared_object` asserted "4 tables" as a literal and failed the moment a fifth arrived, so it now checks presence by name and derives its counts from the DDL arrays.

Rejected: keeping the shipped shape and documenting it (it silently destroys content, which no amount of documentation makes acceptable); a dedicated `annotations` column on `concepts` (a schema change to a frozen ledger table under [D-036](s13-decision-register.md#d-036), to store data the ledger should not carry); storing annotations in `properties`-style JSON on the concept row (same objection, plus it re-enters `transaction_log`).

<a id="d-040"></a>D-040 — [Appendix A](appendices.md#appendix-a--public-api-normative) is rewritten against the implementation, and the divergences are recorded rather than erased (0.5.4). [Appendix A](appendices.md#appendix-a--public-api-normative) is one of the two normative surfaces, and it had drifted from the crate in roughly half its entries: the edge and concept builders hang off value types rather than the handle, traversal and reconstruction are free functions over a connection rather than handle methods, `MaterializedState` exposes fields rather than the query methods the text promised, and three entries — `db.set_embedding`, `db.hybrid_search`, and an atomic annotation write — name operations that do not exist in any form. A normative surface that does not describe the surface is worse than no appendix, because it is cited: [§5.6](s5-modules.md#56-temporalas_ofrs--valid-time-queries-and-attribute-hydration) and [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets) both budget for a hybrid search that is one pure fusion function, and Phase 3 of the implementation plan was marked delivered against a vector API whose write half cannot be reached from `Database` at all. The appendix is therefore split — A.1 states what the crate exposes, A.2 tabulates every promise the sketch made that it does not keep — rather than silently rewritten to match the code. Erasing the divergence would destroy the only record that these were once intended, which is exactly the information needed to decide whether each is a gap to close or a decision to ratify; the two that are gaps (the vector write path, hybrid search) are named as such and carry their closing conditions. This is the same treatment [D-037](s13-decision-register.md#d-037) gave a false claim in [§4.1](s4-schema.md#41-concepts-and-per-model-embeddings) and [D-030](s13-decision-register.md#d-030) gave an integrity check that could not fail: a document that was wrong is corrected in place with the correction visible, not overwritten. Rejected: rewriting [Appendix A](appendices.md#appendix-a--public-api-normative) to match the code without comment (loses the record of intent and makes the missing capabilities invisible again); deleting the unimplemented entries (same, with the added cost that [§5.6](s5-modules.md#56-temporalas_ofrs--valid-time-queries-and-attribute-hydration), [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets) and the implementation plan still reference them); marking the whole appendix aspirational (it is the API contract — half of it is real and callers need to know which half).
