## §11 Milestones

| Phase | Deliverable | Exit gate |
|---|---|---|
| M1 — Schema + integrity | DDL, migrations, triggers, audit_current, rebuild_current | Drift-audit property test passes on random streams |
| M2 — Temporal core | as_of, reconstruct, snapshots, cold-DB fold, AttributeMode | Monday/Wednesday/Friday scenario; reconstruct(now) == live property; cold-DB roundtrip |
| M3 — Graph + vectors | CTE builder, DiskANN search, hybrid RRF, native `Subgraph` ([D-039](s13-decision-register.md#d-039) — this said "petgraph bridge" until 0.5.4) | Golden-string CTE tests; dimension-rejection tests |
| M4 — Write Actor | Actor loop, priority channels, chunking, containment | Priority-interleaving concurrency test; prefix-visibility test |
| M5 — Archive + hardening | Archive session, cold storage, fuzz suite, benchmark **baselines** | [§9](s6-s10-flows-to-dependencies.md#9-performance-budgets) budgets **measured, not gated** ([D-055](s13-decision-register.md#d-055)); archive roundtrip verified |

**The M5 gate said "all §9 budgets met" through 0.6.0, and that was never a gate anyone could pass or fail ([D-055](s13-decision-register.md#d-055)).** Absolute durations on arbitrary hardware are the wrong shape for a CI check: the same code passes on a quiet machine and fails on a loaded one, and [D-070](s13-decision-register.md#d-070) measured ~29% session-to-session noise in this project's own timings. What §9 has instead is criterion baselines, which compare a run against *the previous run on the same machine*, plus the control row [D-090](s13-decision-register.md#d-090) adds to every group so a shifted baseline is distinguishable from a shifted machine. The gate is therefore worded as what it is: the budgets are measured and their drift is visible, and nothing red-lights a build on an absolute millisecond count.

**Status against these gates — 0.8.0 shipped, 0.9.0 in progress (restated 2026-08-07).** **M1–M5 are all delivered.**

The previous version of this paragraph was headed *(0.5.4)* and said M3 was delivered "except hybrid RRF, which is one pure fusion function with no FTS5 table behind it". **That stopped being true at 0.5.5b**, when `concepts_fts` arrived as an FTS5 external-content index on the `v4 → v5` rung ([D-051](s13-decision-register.md#d-051)) — so the keyword arm has existed for three releases and this paragraph went on denying it. It also said M5's benchmark gates "do not exist"; they exist as criterion baselines with the [D-090](s13-decision-register.md#d-090) control row, and M5's gate was rewritten to **measured, not gated** by [D-055](s13-decision-register.md#d-055) precisely because an absolute-millisecond gate is not a gate anyone can pass or fail. Both halves of the correction stand and neither is undone by this restatement.

**Nothing could have caught it.** `doc_sync_tests` pins the error enum and [Appendix A](appendices.md#appendix-a--public-api-normative)'s method list; `doc_link_tests` checks that anchors resolve, and every anchor here resolved throughout. A milestone table nobody updates is worse than no milestone table, because it is read as current. So this paragraph now carries a date, and A5 adds the tripwire for the specific case that produced it — a decision naming a release that has since shipped, with no delivery marker.

Two things beyond the original five, recorded here so the table is not read as the whole scope: the Python bindings shipped at 0.7.0 ([§14](s14-python-bindings.md#14-python-bindings)), and [R15](s11-s12-milestones-and-risks.md#r15) remains open and upstream — probed against `libsql 0.10.0-pre.4` on 2026-08-02 and still reproducing ([D-111](s13-decision-register.md#d-111)).

The first code written is the drift-audit property test, the Monday/Wednesday/Friday attribute-fidelity test, and the priority-interleaving concurrency test, because together they pin the three invariants every later change must preserve: that belief is honest, that fidelity is declared, and that the user is never made to wait for a background job.

| <a id="r15"></a>R15 | libSQL access violation when local databases are opened concurrently in one process (0.5.4) | Low in production, High in test | Low, after mitigation | Found while building the property suite: an intermittent STATUS_ACCESS_VIOLATION (0xc0000005), reproduced with no Macrame types in the loop — open, migrate, drop, repeat. Below the [Doctrine I](s0-s3-foundations.md#doctrine-i) line, so carried as a risk rather than fixed. **Not fixed upstream:** the dependency was moved 0.6.0 → 0.9.30, the latest stable release, three minor versions on; the crate compiled unchanged and the fault rate did not move. **The first diagnosis was wrong and is corrected here.** It was recorded as scaling with the sheer number of databases, on a volume sweep (0/8 at ~64 and ~128, 1/8 at ~384) that in hindsight varied concurrency alongside volume. The dominant factor is concurrency: one binary in isolation faulted 2/40 with libtest's default thread pool and 0/40 with `--test-threads=1`, and the full suite went from 1/20 to 0/30 on that change alone. Volume is at most secondary. The old reading also mispredicted the blast radius — the fault is not confined to the property harness; replay_snapshot, write_path and temporal binaries have each died mid-run. Mitigated in two places, both self-documenting: `RUST_TEST_THREADS = "1"` in .cargo/config.toml (which `[env]` does not force, so the fault stays reproducible on demand), and the `property-tests` feature gate over the three generated-history binaries, which are the residue that serialising does not fix — doctrine_property_tests still faults because a property case needs a database of its own. **Re-measured 2026-07-30 (0.5.6 Wave 5), and the mitigation figures below do not hold: serialising reduces a rate, it does not remove the fault.** Ten consecutive `cargo test --no-fail-fast` runs on the shipped `RUST_TEST_THREADS = "1"` faulted **5/10**, against the 0/30 recorded here at 0.5.4, on the same dependency version — either the rate rose with the suite (171 → 221 tests) or the original 0/30 was a lucky streak. Two further findings sharpen the diagnosis rather than restate it. **Every faulting binary is clean in isolation:** the four that died during those runs (storage_boundary, vector_filter, replay_snapshot, write_path) are 0/15 each when run alone — 60 isolated runs, no fault — so the trigger is neither the binary nor thread concurrency *within* one, which is already serialised in both cases. And the correlate looks like database open/drop **churn** rather than load on an open database: doctrine_property_tests, which opens one per generated case, faulted 3/4 alone and integrity_property_tests 1/4, where a 20-test binary is 0/15. The soak that would settle it, and the consequences for the load-bearing claim below, are specified in T5.2 of the v0.6.0 hardening plan. Not masked by the gate: proptest replays every previously found failure from .proptest-regressions before generating a new case, so defects already caught stay caught, and the gated binaries run as their own step. Production exposure is nil by construction — an application opens one Database and holds it for its lifetime — and remains the load-bearing claim: if this is ever observed with a single long-lived Database, this row is wrong and the risk is severe. **That claim also needs sharpening before it can be defended**, because it is not what the crate does: `open_inner` opens three connections, four since Wave 4.1 gave the cadence its own. What a soak can actually test is *one process, one file, a bounded set of connections opened once and never churned* — and given the churn correlate above, that is the statement to defend rather than one about `Database` handles. **Soaked 2026-07-31 (0.6.0, T5.2, [D-092](s13-decision-register.md#d-092)), and the sharpened claim is now defended rather than asserted.** `examples/r15_soak.rs` runs two arms as *subprocesses* and reads their exit codes, because the fault kills the process and there is nothing to assert on from inside it. **claim** — one long-lived `Database` (all four connections, cadence on), 16 concurrent reader tasks running `load_subgraph` and `reconstruct`, and the write actor kept saturated: **0 faults in 10 runs of 15 s and 0 in 6 runs of 60 s**, about 8.7 minutes of continuous load. **control** — the same, plus a task opening 48 databases concurrently in the same process: **2 faults in 10 runs**, both within the first 3 s. The control is what makes the claim arm mean anything; without it a clean result would be indistinguishable from a harness that provoked nothing. So the row's load-bearing claim should now read **one process, one file, a bounded set of connections opened once and never churned**, and in that shape R15 did not reproduce. It is still a rate rather than a proof, and the trigger is still concurrent *open*. **Reported upstream against 0.9.30 on 2026-07-31** by the maintainer, from the reproduction in `libsql-issue.md`. **Reproduced through the Python binding, 2026-07-31 (0.7.0, [D-095](s13-decision-register.md#d-095), [§14.7](s14-python-bindings.md#147-r15-through-the-boundary)).** There was a plausible argument that the binding would *reduce* exposure — one shared tokio runtime, entry serialised by the GIL — and it is refuted: `tests_py/probes/r15_concurrent_open.py` opens 48 databases from 48 Python threads released together on a barrier and faults **2 in 12 runs**, the same rate as the Rust control arm at the same width. The reason is the binding's central feature: `block_on` releases the GIL, so the threads are genuinely concurrent inside `open`, which is what the fault counts. **The boundary is transparent to R15.** Two consequences, now measured rather than transferred: the Python suite runs single-process (`pytest-xdist` opens a database per worker, which is exactly this shape), and the application guidance is unchanged — a bounded set of handles opened once, not one per request. The reporting hazard carries across intact, so a gate on either suite must key on the summary line being present rather than on the exit code. **Mitigation list extended 2026-08-02 (0.8.0, [D-110](s13-decision-register.md#d-110)), after this row's cost was paid in the open:** `main` went red on two consecutive documentation-only commits (runs `30706318073`, `30706474231`) at the quarantined property step. Two causes, and the interesting one is not the rate. The retry budget of three was calibrated on the main suite — where `RUST_TEST_THREADS = "1"` applies — and applied unchanged to the step that exists because serialising does not help it; against the 9-in-15 measured for `doctrine_property_tests` at 0.7.0, three attempts go red about 22% of the time, which is the 2-in-9 observed. The deeper fault is that a retry loop **cannot classify**: three failures and a genuine defect print the same four lines. `scripts/run_rust_suite.py` now reads each run instead of counting it — `CRASH` / `FAILED` / `INCOMPLETE` / `TEARDOWN` / `BUILD`, retrying only `CRASH` — keying on exactly the per-target `test result:` line this row and `.cargo/config.toml` both say to key on. It rests on one measured fact about the fault: a target killed mid-run has already printed its `running N tests` line, so a crash removes the summary but not the section, and the crashed target can still be named. Only with that in place does the quarantined budget move to six (≈5% red); raising it earlier would have bought a lower rate at the cost of more chances to launder a real failure into a pass. **This is the row's sixth measurement and it still does not fix the fault** — it makes the fault legible, which is a different thing, and A2 (probing the 0.10 pre-release) remains the only item that could delete this row rather than manage it. **Probed 2026-08-02 (0.8.0, [D-111](s13-decision-register.md#d-111)), and it does not delete the row: R15 reproduces on `0.10.0-pre.4`.** The pre-release resolves and compiles unchanged and the full suite passes on it first attempt — so an eventual 0.10 upgrade is a version bump, not a port — but the fault is observed directly on both sides of the boundary: Rust control 1/10 at 48 concurrent opens, Python probe 1/12 at the same width, Rust claim arm 0/10. **The most instructive number is the baseline.** Run in the same session on the same machine, `0.9.30` scored **0/10** against the 2/10 recorded for it at 0.6.0 — so the old engine beat the new one, and the only defensible reading is that ten runs cannot distinguish these rates in either direction. A clean arm on a new engine is therefore not evidence of a fix, which is the control-arm argument of `examples/r15_soak.rs` applied one level up. Every mitigation stays; `libsql` stays at 0.9.30. **A regression was reported here on 2026-08-02 (0.8.0, during B5) and there was no regression. Retracted and corrected on 2026-08-03 ([D-124](s13-decision-register.md#d-124)).** The retracted claim was that the quarantined gate had gone red on `main`, that `doctrine_property_tests` was faulting far above its recorded rate, and that the six-attempt budget could no longer clear it — on 8 runs per arm showing 5/8, 6/8 and 5/8 against 1/8 for `integrity_property_tests`. Three things were wrong with it. **First, the baseline was a stale number**: "its recorded rate" was taken from a `~3/25` comment in the test file dating to 0.5.4, while this row, `.cargo/config.toml` and `ci.yml` had all moved to ≈60% at 0.7.0 — the measured rate was in line with the real baseline and was only a regression against a figure nothing else believed. **Second, `main` was never red**: CI passed on all five 0.8.0 commits (`30762261075`, `30764173389`, `30767607046`, `30768128858`, `30770381302`), on Windows, macOS and Ubuntu. What was red was one developer machine, which is a different claim. **Third, eight runs could not have supported the comparison anyway.** Re-measured with the arms interleaved at n = 20 each: the doctrine binary built at `v0.7.0` faults **9/20**, the binary built at `55b7844` faults **15/20 and then 9/20 on two consecutive runs of the same executable**, and an arm with one property *removed* scored **above** the arm containing it. The noise band is ~30 points at n = 20, so no comparison at n ≤ 20 in this row's history distinguishes arms — including several of the earlier ones. There is no 0.8.0 regression: a binary that predates every 0.8.0 change faults at the same rate. Two things this did establish. The fault is **effectively Windows-only in practice** — in run `30770381302` the quarantined step took 46 s on macOS and 58 s on Ubuntu against 4 m 30 s on Windows — and the rate now lives in `.cargo/config.toml` **only**, with the two copies that drifted replaced by pointers to it. One candidate is recorded there untested rather than left to be re-invented: the harness uses a multi-thread Tokio runtime, so the three connections of a `Database::open` can overlap even with libtest serialised, which is the concurrency this row has never located; a current-thread build scored 10/20 against 15/20, inside the noise band and therefore settling nothing. **Raising the retry budget remains the laundering [D-110](s13-decision-register.md#d-110) exists to prevent**, and nothing here asks for it — the budget is not under strain on CI. **Seventh measurement, 2026-08-08 (0.12.0, [D-147](s13-decision-register.md#d-147)), and it retires the idea that this row has a rate at all.** The quarantined *step* was measured directly for the first time — every figure above is one binary, and README and `ci.yml` were both quoting the step — at **93 of 100 attempts** on a developer Windows box under sustained load, 95% interval 86–97%. Six attempts at that rate is 65%, and the step is plainly not red 65% of the time: `ci.yml`'s own 2-in-9 implies ≈78% on the runner. So the six figures this row and its neighbours have published — 45%, 60%, 75%, 78%, 93% — were never competing estimates of one constant. **They are five machines under five loads**, and the noise-band finding above was the same result seen one release early and read as a property of the instrument rather than of the quantity. Quote the figure you measured, name the machine and the load beside it, carry it nowhere; `.cargo/config.toml` remains the only home. Two things the study also established, both about measuring rather than about R15. A flaky test biases a crash rate **downward** — `classify()` reports a genuine failure before it looks for a crash, so a run where one binary crashed and another failed hides the crash, and this study's first pass read 71% for that reason. And the cold arm that would separate machine from load — runs spaced minutes apart rather than back to back — **has still not been taken**, and is named in [Appendix C](appendices.md#named-for-0130-and-both-come-from-measuring-0120) rather than implied by these numbers. **Eighth measurement, 2026-08-15 (0.12.1, [D-148](s13-decision-register.md#d-148)), and it replaces this row's diagnosis rather than refining it: R15 is a cumulative `connect()` volume fault, not a concurrency fault.** Every mitigation this row has shipped serialises something, and `examples/r15_soak.rs` gained a `storm` arm that runs the open storm with no soak database, no readers and no actor, with each variable behind its own flag. Serialising `build()` faults 6/6; serialising `connect()` 5/6; dropping every handle one at a time in the parent 6/6; removing overlap entirely 4/6. **And `--sequential --current-thread` — one task, one OS thread, `build → connect → query → drop` in a loop, no overlap and no worker migration anywhere — faults 2/10 in release**, with its clean runs reaching 9,792–10,416 opens. The only arm that eliminates the fault is `--first-use build`, which never calls `connect()` and survives ~880,000 opens per run: a 100× volume margin over every arm that dies. Read those counts as *eliminated / not eliminated* and never as rates — n = 6–10 against the ~30-point noise band [D-124](s13-decision-register.md#d-124) measured. **The old diagnosis survived six releases because one row of its reproducer stopped at 500.** The concurrency sweep (0/10 at 4, 8, 16; 2/12 at 32; 5/12 at 128) was sound; the single sequential row, *500 opens, 0/10*, was three orders of magnitude too short, and every downstream document inherited its conclusion. 500 is under the threshold, not safe. This also discharges the anomaly `.cargo/config.toml` has carried unexplained since 0.5.6 — every binary 0/15 alone while the serialised suite is 5/10 — with no hidden concurrency required: **the suite makes far more cumulative `connect()` calls than any one binary does.** The same reading covers the rest of this row's history: the suite figures track suite *size* (171 → 221 tests) rather than thread count, and [D-147](s13-decision-register.md#d-147)'s five irreconcilable rates are five machines running the same work at five speeds, which is five totals per unit time. The standing untested candidate is retired too: the multi-thread runtime was suspected because `Database::open`'s three connections can overlap on different workers even with libtest serialised, and `--current-thread` settles that it is not the mechanism. **No mitigation changes.** `RUST_TEST_THREADS = "1"` stays — it lowers the rate, and only the recorded mechanism was wrong; it plausibly lowers connections per unit time. The `property-tests` quarantine stays and is better justified, a property case opening a database per generated case being the highest-volume shape in the repo. **And this row's load-bearing claim comes out stronger:** *one process, one file, a bounded set of connections opened once and never churned* is exactly the shape that never accumulates `connect()` calls, so the 500-sequential-clean figure now reads as confirmation rather than as the edge of what was tested. What is exposed is the suite. **Refined twice more in the same release.** *Distinct databases, not merely calls:* every arm above opened a fresh file per iteration, so cumulative `connect()` and cumulative distinct databases moved together. Holding one path and reopening it faults **1/8** with seven clean runs reaching 40,352–43,360, against 6/8 faulting from 2,272 with a fresh file each time — so the dominant variable is distinct databases, with `connect()` as the call that pays for them, and reopening one file is safer but not immune. **That places this crate's production shape at the safest point on both axes at once**, and the suite, which creates a temporary database per case, at the worst on both. *And there is no threshold:* instrumented fault positions pooled over n = 20 span 2,144–40,416 while the three clean runs stopped only because time ran out — a per-`connect()` probability of very roughly 1 in 20,000–25,000 here, not a leak with a ceiling. **One near-miss is recorded because it nearly shipped as a finding:** 8 of 11 faults in the first session landed on exactly 17,536, which reads as a hard threshold and did not replicate — once in eight on a re-run of the identical configuration. [D-124](s13-decision-register.md#d-124)'s noise band in a new coordinate, caught only by running the same thing twice. **The upstream report is rewritten** as [`docs/libsql-issue.md`](../libsql-issue.md), replacing the 2026-07-31 one whose stated trigger this supersedes; it carries a ~15-line single-threaded reproducer and asks three specific questions. Sending it is the maintainer's action. |
