# Macrame 0.18.0 — the flexible ledger

Crate macrame-db 0.18.0, wheel 0.18.0. Schema v19 → **v21** over two rungs; concept log
payload v2 → **v3**; snapshot container v4 → **v5**; MSRV 1.88 unchanged; `DbError` 42 →
**45** variants. Public surface 1,781 → **1,830 items**, every one additive. Decisions
**D-278 … D-285** (D-281 is reserved for 0.19's blob store and is not in the register yet) — three items on `dev/0.18.0` before this cut.

This cycle began with a **plan document rather than a review**, driven by one consumer:
the OKFgraph rework needed per-usecase extensibility, and the question it put to this
crate was whether it could have that *without* being handed a DDL surface. The answer
shipped here is that the attribute layer opens and the ledger core does not. Time,
assertions, materialization, archive and branching are untouched and still
guarantee-bearing; what applications gained is a place to put their own structure, a place
to put their own operational state, and kinds they can namespace.

**P4, the content-addressed blob store (D-281), is deferred to 0.19 and that is a
consequence rather than a schedule.** Blob eligibility is computed from references inside
log payloads, which did not exist until P1 landed — the refcount design the proposal
carried was withdrawn rather than adjusted, because a versioned `extra` makes it unsound:
a concept version that names a blob names it permanently, and a counter tracking only
present references reaches zero while a past state still depends on the bytes.

## Breaking changes

None to any API. Every surface change is additive and every existing call behaves as it
did.

**Two forward incompatibilities, stated rather than discovered**, both of which are the
designed behaviour of a version gate doing its job:

- **Once 0.18 writes any concept, a 0.17 binary cannot fold the log.** The concept payload
  moves to v3 and 0.17's ceiling check is a single global 2, so it refuses the row — which
  is what a ceiling is for. The corollary is worth printing beside it: **a 0.18 binary
  writing only links stays readable by 0.17**, because the marker is per entry and the
  links shape is untouched at 1. That property is the reason the links marker was *not*
  bumped along with the concepts one
  ([D-285](../architecture/s13-decision-register.md#d-285)).
- **A 0.18 database holding lowercase edge kinds fails validation on a 0.17 binary.** The
  charset relaxed; 0.17's validator did not
  ([D-279](../architecture/s13-decision-register.md#d-279)).

The two **schema** rungs (v19 → v20, v20 → v21) are forward-only in the same sense as
every rung before them — an older crate cannot open a v21 file — and the v21 rung adds a
column with a default, so no ETL is owed.

## Added

**`concepts.extra` — app-defined attributes on the concept row**
([D-278](../architecture/s13-decision-register.md#d-278), schema v20 → v21). A JSON
object, at most 64 KiB, `NOT NULL DEFAULT '{}'`. It rides the concept row rather than a
table of its own, so it inherits lineage, retirement and the bitemporal key for free, and
`ALTER TABLE ADD COLUMN` is what [D-036](../architecture/s13-decision-register.md#d-036)
already permits on a ledger table. The ledger validates that it *is* an object and that it
fits, and reads nothing inside it.

**It is in the log, so changing it is a belief change**, and that is the whole cost of the
item rather than an incidental. The triggers emit an explicit `json_object` and not
`SELECT *`, so a column absent from that list is invisible to `reconstruct` and to every
`AttributeMode::AtTime` read — which is exactly the defect Wave 1 classified when the
omitted column was `embedding_model`.

**Unstated is not empty** ([D-283](../architecture/s13-decision-register.md#d-283)). An
upsert that does not mention `extra` preserves whatever the row holds. Code that knows
nothing about attributes re-upserts rows all the time, and a wipe there would be recorded
by the log as a deliberate belief change: irreversible by design and indistinguishable
from an intention. Clearing is `extra="{}"`, said out loud.

**`Database::register_extra_index(path)`**
([D-284](../architecture/s13-decision-register.md#d-284)). An expression index over a
JSON path in `extra`. Call it unconditionally at startup: it is create-if-absent and there
is no registry table, because **re-assertion is the record** — which is what makes a
restored backup safe, since a file that came back without the index gets it on the next
open and nothing has to have remembered that it should have been there.

> **The query has to spell the expression character for character.** SQLite chooses an
> expression index by comparing expression *trees*, so an index over
> `json_extract(extra, '$.layer')` does **not** serve a filter written
> `extra ->> '$.layer'` — that query returns exactly the right rows and scans the whole
> table doing it. Write the `json_extract` form. This is the schema's first expression
> index, and the `EXPLAIN` gate carries a negative control for precisely this reason.

**`kv_store` — operational state, outside the ledger entirely**
([D-280](../architecture/s13-decision-register.md#d-280), schema v19 → v20). Hashes,
epochs, counters, cursors: `kv_put` / `kv_get` / `kv_delete` / `kv_scan(prefix, limit)`,
on a plain `WITHOUT ROWID` table with **no log trigger, no archive membership and no
lineage**. Branch-global is the semantic and not an omission — one cursor across every
lineage — and what carries it is a **file-level backup**, not a snapshot: a snapshot is a
materialized ledger state and never held KV. Reads go to the read connection and answer
immediately behind a long bulk import.

**Edge kinds relax to `[A-Za-z0-9_:.\-]+`**
([D-279](../architecture/s13-decision-register.md#d-279)), so applications can namespace
their own — `okf:links-to`, `myapp:cites` — without a rename step. Two rules arrive with
the relaxation: **one case per kind** (mixing is refused) and a **64-character cap**. The
case rule narrows the near-miss class — two spellings a reader cannot tell apart — and
does *not* close the collision class, which only the old uppercase-only rule did and which
the relaxation spends. That is said plainly because the weaker guarantee is the one being
shipped.

Two new error variants, `InvalidExtraError` and `InvalidExtraPathError`, both under
`ValidationError` in the Python hierarchy, and one new `CommandKind::RegisterExtraIndex`.

## Fixed

**The read-side payload ceiling stops being global**
([D-285](../architecture/s13-decision-register.md#d-285)). The version marker has been
per entry since the log's first release, but the read side checked one constant against
every row *before* dispatching on `table_name`. That was sound while one version existed
and stopped being sound the day Wave 1 took concepts to v2 and left links at 1: from then
a links row stamped 2 passed the gate and decoded under v1 field names. The check now runs
after the dispatch and reads per-shape constants. **It cannot refuse a row any version of
this crate minted** — none ever wrote a links payload above 1 — so it fires only on rows
that were already being silently mis-folded.

**`verify` gains a body probe for the concept log triggers**
([D-282](../architecture/s13-decision-register.md#d-282)). It read bodies for the three
delete guards and named only them, so a concept log trigger with the right name and a
stale body was invisible: present, named, and writing a payload that omits a column
sitting plainly in `concepts`. A stale trigger now refuses the open instead of writing
incomplete history.

## Performance

**The concept-write budgets were re-measured against a control at the previous commit**,
not against the figures in §9, because those are for named reference hardware and this is
not that machine. Two criterion sessions each side: `upsert_concept` 310.9 / 312.9 µs →
333.8 / 341.2 µs (+8%), `bulk_chunks/concepts_500` 21.36 / 20.53 ms → 23.88 / 23.06 ms
(+12%), `chunk_budget/concepts/70` 3.337 / 3.370 ms → 3.452 / 3.344 ms (inside session
noise).

That is the cost `extra` imposes on a caller who never uses it: a wider row, a wider log
payload, and `idx_concepts_extra_layer` maintained on every insert. The shape is what the
mechanism predicts — per-row index maintenance shows up where the rows are, and the
70-row chunk is dominated by the per-transaction floor. **No §9 row moves from met to
missed because of this release.** One row is missed on this box in *both* arms — `Chunk
commit, concepts, 70 rows` reads 3.34 ms before the change against a ≤ 3 ms budget — which
is why the control was run at all: without it the reading would have been published as
this release's regression.

## Acceptance

The plan's nine gates, all closed:

1. **Round-trip under archive.** A concept carrying `extra` archives, rehydrates and
   compares byte-equal across all six explicit column lists.
2. **Cold tolerance.** A pre-0.18 cold file attaches, reads and rehydrates with no `extra`
   column present, is not written to by the reader, and is upgraded only by the archive
   writer.
3. **Mixed payload fold.** A log holding v1, v2 and v3 concept entries folds to the state
   the entries describe, with `extra` present only where written.
4. **Snapshot refusal.** A v4 snapshot meeting a v5 build is refused *and* the fold runs
   from the log — both halves, because either alone would mislead.
5. **Stale trigger refusal.** A v2 trigger body under a current version stamp fails
   `verify` with a message naming the trigger, and the two current triggers are not dragged
   in with it.
6. **Expression index plan, with a negative control.** `idx_concepts_extra_layer` is chosen
   for the `json_extract` form and *not* chosen for the `->>` form.
7. **Upsert preservation.** A concept upserted twice, with `extra` set only on the first
   call, still carries it — and both log entries say so.
8. **Ladder re-run.** Above, with a control.
9. **Per-shape ceiling.** A hand-minted links row stamped v3 is refused with `max: 1`; a
   concepts row stamped v4 with `max: 3`.

## What is not closed

- **The 64 KiB cap on `extra` is provisional.** It has not been checked against OKFgraph's
  real frontmatter sizes. It is a named constant (`MAX_EXTRA_BYTES`), which makes moving it
  a one-line change and a minor version.
- **`extra` is not reachable from `concepts_fts`.** Out of scope for 0.18 and not raised as
  a question here.
- **P4, the blob store**, is 0.19's, for the reason at the top of this note.

**One of those steps was red at its own commit**, and it is recorded rather than tidied
away: at P2's commit `doc_link_tests::every_cross_reference_resolves` failed, because two
cross-references pointed at D-279 before the register held it. The register only admits
what has shipped, so an item that cites its own entry is red until the release lands. P3's
commit made the references plain text with a note saying so, and this commit restores them
as links.

R15 is unchanged and is the Windows fault it has always been: a run that dies with
`STATUS_ACCESS_VIOLATION` and no named failure is re-run per the documented protocol
(`.cargo/config.toml`, [D-147](../architecture/s13-decision-register.md#d-147)), and a
binary that fails *alone* is a real failure.
