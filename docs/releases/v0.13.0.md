# Macrame 0.13.0 — what you can observe and control

**Crate `macrame-db` 0.13.0 · wheel `macrame-db` 0.13.0 · schema v11**

*Six waves, twenty-six commits, and one rung. This is the release where the pre-1.0 window is spent deliberately rather than allowed to close.*

**One schema rung and no breaking API change.** A 0.12.0 database migrates to v11 on open — `links-archive-indices`, two indexes, no data movement — and every public signature from 0.12.0 still compiles. **There is one default-build change**, and it is the point of the release: the `metrics` feature is now on by default, so `violations()` answers in the build you actually ship.

Written after the fact. 0.13.0 shipped without a release note; this is it, and it is written against the commits rather than against the plan, which is why two of its sections are corrections.

---

## The theme, stated plainly

Every wave here is about the same thing from a different side: **a crate organised around a latency bound must be able to say whether the bound is met, and a planner asked to choose an index must have something to choose on.** 0.12.0 made the chunk loop adaptive and could not tell you what it adapted to. 0.13.0 is the release that closes that gap on both the measurement side and the control side.

---

## W1 — R15 was never a concurrency bug, and the reproducer that said so stopped too early

R15 — an access violation opening databases under libSQL 0.9.30 — has carried a concurrency diagnosis since 0.8.0. The plan's instruction was to reproduce it under control and *not* to put a mutex in `open()` on a hypothesis. That instruction paid for itself immediately.

Serialising `build()` changes nothing. Serialising `connect()` changes nothing worth having. And `--sequential --current-thread` — one task, one OS thread, no overlap and no worker migration — **still faults 2 runs in 10** in release, with its clean runs reaching 9,792–10,416 opens.

**R15 is not a concurrency bug in any of the three available senses** — simultaneity, thread migration, or teardown. What survives every arm is cumulative `connect()` volume: `build()` alone is clean at ~880,000 opens per run, and adding `connect()` kills the process within a few thousand however the work is spread across threads and time.

**The old diagnosis survived six releases because one row of its reproducer stopped at 500.** The concurrency sweep was sound; the single sequential control was three orders of magnitude too short, and every downstream document inherited its conclusion.

Two consequences worth carrying:

- **`RUST_TEST_THREADS = "1"` is not the mechanism it is documented as.** It serialises, and serialising does not help. It plausibly lowers connections-per-run enough to reduce the rate, which is a different claim from the one `.cargo/config.toml` made. **No mitigation changed** — the setting works, and only its recorded reason was wrong.
- **The production claim gets stronger.** *One process, one file, a bounded set of connections opened once and never churned* is exactly the shape that never accumulates `connect()` calls. The exposed party is the test suite, which opens thousands of databases per run.

It also discharges an anomaly open since 0.5.6: every binary is 0/15 alone while the serialised suite running those same binaries is 5/10. No hidden concurrency is needed. The suite makes far more cumulative `connect()` calls than any one binary, and D-147's five irreconcilable machine rates are five totals per unit time.

## W2 — The planner had never had statistics, and that was not a tuning gap

`ANALYZE` and `PRAGMA optimize` appeared **nowhere in `src/`**. So `sqlite_stat1` existed in no database this crate had ever created, and SQLite costed every plan against its built-in defaults: ~1M rows, each bound equality column divides by ten.

That estimate is *structural*. It depends on how many columns a query binds, not on what the table holds — which is `index_plan_tests`' own summary of this schema's worst defect standing as a permanent condition rather than a bug: **a covering index captures a query because it contains the columns, not because it discriminates.** [D-042](../architecture/s13-decision-register.md#d-042), [D-059](../architecture/s13-decision-register.md#d-059) and [D-064](../architecture/s13-decision-register.md#d-064) are three instances of a planner doing the only thing available to it.

`Database::analyze()` ships with `PRAGMA analysis_limit = 400` so the work is schedulable rather than unbounded, `PRAGMA optimize` runs on close and after bulk load, and the plan-pinning fixture finally has **rows and statistics** rather than an empty schema — because a plan pinned against an empty table pins the defaults, not the choice.

The plan registry also gained a second direction: it could be written to and not read back, so a pinned plan that had silently stopped being produced looked exactly like one that was still holding.

## W3 — Two indexes, and the first rung since v10

`links` carried a primary key and nothing else. The PK leads on `source_id`, and **neither archive predicate seeks on `source_id`**, so both scanned the ledger. Measured before and after on the now-populated, now-analysed fixture:

| query | before | after |
|---|---|---|
| `LINKS_ARCHIVABLE` | `SCAN links` | `SEARCH links USING INDEX idx_links_recorded_at (recorded_at<?)` |
| `CONCEPTS_ARCHIVABLE` | `SCAN links USING COVERING INDEX` | `MULTI-INDEX OR`, both arms seeking |

Shipped as the **v10 → v11 rung `links-archive-indices`**. Both entries are in the plan registry, in both directions, which is what W2.3 was for.

## W4 — `metrics` becomes a default feature, and the measurement is the story

**The argument is not that the counters are cheap.** It is that a crate organised entirely around a latency bound must not ship a default build that cannot report whether the bound is met. `violations()` answers the only question this design asks about itself, and from 0.6.0 to 0.12.10 the default build could not. [D-093](../architecture/s13-decision-register.md#d-093) made exactly this argument for the Python wheel and won it; the Rust default sat on the wrong side of the same reasoning for six releases.

`--no-default-features` remains, built and tested.

**Cost, as arithmetic:** 11–14 relaxed atomic RMWs per turn plus ~1.6 KB. The clock is not part of it — that has been unconditional since 0.12.0.

### The naive experiment gave the opposite answer, and that is why it is in the release note

One run per arm: metrics-off **9.0% faster** on `assert_edge`, **16.0%** on `upsert_concept`, both *p* < 0.05, criterion printing *"Performance has improved."*

False. 9% of 275 µs is ~25 µs, and fourteen relaxed atomics cost tens of *nanoseconds* — off by three orders of magnitude. Re-run alternating, three rounds under load put the confound in the open: `control/select_1`, a bare `SELECT 1` that never enters the write actor at all, differed **+4.8%** between arms — *more* than `upsert_concept`'s −0.7%.

The instrument was measuring the machine.

### The starvation floor was missing, and it is hit

`MetricsSnapshot` gains `low_starved_turns` and `low_starved_run_max`. The **run** is the one with teeth: a large total on a busy database says the tiers are working, and only a long run distinguishes *prioritised* from *starved*.

This is not a near miss. A 39-edge chunked `bulk_import` raced by 64 concurrent `upsert_concept` calls gives `starved_turns=63`, `run_max=63`, `turns=70` — identical across five runs. **The run equals the total**: the bulk import sat behind every single queued high-priority write with no interleaving at all, and run length is bounded by nothing in the crate, only by offered high-priority load.

The quiet half is asserted too — a sequential caller queues nothing and reports `run_max == 0` — which is what stops the counter reporting starvation everywhere forever. The fix is scheduled as W10.4 in 0.14.0, deliberately: the counter shipped in the release that would carry the fix, and a before/after taken with it alone measures the fix against itself.

## W5 — One `Tuning` struct, a checkpoint you can call, and a WAL you can bound

`Database::open_tuned(path, Tuning { .. })` consolidates the `open*` family. The three existing constructors stay, delegate, and are **not deprecated** — `open(path)` is the right call for most callers and should not acquire a warning.

**Two corrections to the planned design, both found by building it.** `#[non_exhaustive]` on the struct does not compile for the use it was added for: a non-exhaustive struct cannot be built with literal syntax outside its crate at all, and `..Default::default()` *is* literal syntax, so the attribute makes exactly that expression `E0639` for every external caller.

`Database::checkpoint()` is a `HighPriCommand`. `Tuning::wal_autocheckpoint` takes a `WalCheckpointPolicy` — `Default | Disabled | EveryPages(u32)` — applied to the write connection only, which is the only connection that commits and therefore the only one whose threshold can fire. The default does not move: 1,000 pages stays.

Not `Option<u32>` as specified, for [D-155](../architecture/s13-decision-register.md#d-155)'s reason: in a `Default` struct a `None` that disables a mechanism disables it for everyone who did not mention it, and this is the mechanism that keeps the WAL bounded. `EveryPages(0)` is deliberately **not** remapped to `Disabled` — a computed zero is a caller's bug, and inheriting SQLite's overload would turn it into an unbounded WAL silently.

F-30 also turned out to be a **tail, not an oscillation**, which is a different fix than the one the finding implied.

### And one thing was documented rather than fixed, on purpose

**`as_of(ts)` read `ts` on two different clocks** ([D-160](../architecture/s13-decision-register.md#d-160)). The same timestamp was compared against `links.valid_from`/`valid_to` — valid time — for the graph's shape, and against `transaction_log.recorded_at` — transaction time — for concept attributes under `AttributeMode::AtTime`. So `as_of("2020-06-01")` returned the edges that held in 2020 labelled with *what was believed in 2020*: a title corrected today to fix a 2020 typo came back uncorrected.

Right answer to *what did we believe*; wrong answer to *what was true*, and the method's name promised the second.

**Stated a release before it was changed, deliberately.** Fixing it changes answers callers already depend on, so it belongs to a release allowed to break them. Writing the semantics down first is what made the change reviewable against a stated position rather than argued in the commit that made it — and it is what [D-174](../architecture/s13-decision-register.md#d-174) was checked against when the split landed in 0.13.2.

## W6 — Python reaches parity, including with what this release added

The rule W6 exists to enforce: **a binding gap opened in the release that created the feature never becomes a convention.** So `analyze()`, `checkpoint()`, `Tuning`, the WAL and cache knobs, and the two new starvation counters all cross in the same release that made them.

Also closed:

- **Six constants a Python caller had to reason against and could not read.** `MAX_ARCHIVE_SESSIONS` and the four `chunk_rows` ceilings, following `BULK_ATOMIC_WARN_HOLD`'s precedent. The archive ceiling is a *refusal* rather than a clamp ([D-080](../architecture/s13-decision-register.md#d-080)), so session count is arithmetic the caller can do before the call — but only with the constant. Without it the limit is learned by catching `ArchiveWindowError` afterwards, which is the shape D-080 chose not to have.
- **`registered_models()` and `declared_dimension()`** — the vector registry could be written to and not read back.
- **Clock injection**, the one gap that cost test *capability* rather than convenience: the Python suite could not see the transaction-time axis at all without it.
- **`shadow_step`'s omission is recorded as a decision**, beside `raw()`'s. Silence reads as oversight.

## §8 acceptance: two items resolved as corrections

The acceptance list's wording asks for *measurement*, not confirmation, and two items took it up on that.

**Item 2 asked whether `analysis_limit` bounds `ANALYZE`'s hold. It does not.** The pragma is in force and worth 3–4×, and what is left still grows with the table: `analyze()` holds **19.1 ms at 40,000 edges against a 3 ms budget**. `budget_violations()` had been naming it since 0.12.4 — **the instrument worked and nobody had read it** ([D-166](../architecture/s13-decision-register.md#d-166)). `analyze()` stays counted, and the exemption waits for the split rather than being granted here.

**Item 4 miscounts its own spec.** W2.3 names three queries plus two indexes, not four queries. All covered.

Two more things fell out of closing the wave:

- **A rustdoc had described the wrong method since 0.12.13** — `checkpoint()`'s summary line was `rebuild_current`'s, and `rebuild_current` had none ([D-167](../architecture/s13-decision-register.md#d-167)).
- **The feature-off build had been broken for two releases** by an example added during them, past an acceptance item checked one release *before* the break landed ([D-169](../architecture/s13-decision-register.md#d-169)). An acceptance item that passes and then stops being true is a gate that reports on the past.
