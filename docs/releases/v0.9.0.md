# Macrame 0.9.0 — concepts cross the archive boundary, in both directions

**Crate `macrame-db` 0.9.0 · wheel `macrame-db` 0.9.0 · schema v7/v8 → v10**

Concepts can now be archived to cold storage and brought back. Everything else in
this release exists to make that true without the ledger lying about it.

---

## Read this first: schema rungs, and they do not go backwards

**Which rungs you climb depends on where you are coming from, and for most
people that is 0.7.0.** 0.8.0 was tagged late and published after 0.9.0 was
already finished, so the last release most users have is **0.7.0, on schema
v7** — and that path is the expensive one. The ladder runs automatically the
first time 0.9.0 opens the file:

| from | rungs applied | shape |
|---|---|---|
| **0.7.0** (schema v7) | `v7 → v8`, `v8 → v9`, `v9 → v10` | **one table rebuild** plus two trigger swaps |
| **0.8.0** (schema v8) | `v8 → v9`, `v9 → v10` | two trigger swaps, nothing else |

| rung | name | what it does |
|---|---|---|
| `v7 → v8` | `concepts-rowid-pk-and-unread-indices` | **rebuilds `concepts`** — adds `rowid_pk INTEGER PRIMARY KEY`, re-keys the FTS index onto it, drops two unread indices. The only rung that suspends foreign keys |
| `v8 → v9` | `concepts-guard-marker-gated` | the concepts delete guard becomes conditional on an archive session |
| `v9 → v10` | `concepts-log-insert-marker-gated` | the concepts insert log trigger becomes conditional on the same marker |

**The two 0.9.0 rungs replace one trigger each and touch no table.** No rows
move, nothing is rebuilt, no index is recreated, neither suspends foreign keys,
and the cost does not scale with your data.

**The `v7 → v8` rung does scale, and it is measured rather than estimated**
([D-125](../architecture/s13-decision-register.md#d-125)):

| concepts | links | log rows | file before | migrate | peak disk |
|---|---|---|---|---|---|
| 10,000 | 30,000 | 40,000 | 35.7 MiB | 0.07 s | 1.09× |
| 50,000 | 150,000 | 200,000 | 181.4 MiB | 0.58 s | 1.09× |
| 200,000 | 600,000 | 800,000 | 733.5 MiB | **2.65 s** | 1.09× |

**~10–13 µs per concept, and the outage is short and linear** — 2.7 s on a
733 MiB database, scaling with your concept count rather than with the file
size. Nothing here needs a maintenance window.

**Peak disk is 1.09×, not 2×, and it settles back to 1.00×.** If you have read
that a copy-and-swap needs twice the space, that is true of the *table* and not
of the *file*: `concepts` is a small share of a database whose bulk is `links`
and `transaction_log`, so twice a small thing is a 9% bump. The space is
borrowed, not kept — after a `wal_checkpoint(TRUNCATE)` the file is its original
size. The figure is flat across four scales, which is what makes it a rule
rather than a data point.

**One shape where that headline would mislead you.** `foreign_key_check` runs
inside the rung and is 13–17% of it, but it is a **whole-database** scan — it
grows with `links` and the log, not with `concepts`. On a database with a large
ledger relative to its concept count, the part that does *not* scale with
concepts is the part that dominates. Budget from your total row count, not from
your concept count, if those differ by a lot.

**They are still irreversible, and that is the one thing to plan around.** A
migration is the single change a user cannot undo. After 0.9.0 opens your
database it is stamped `user_version = 10`, and an older build will refuse it
rather than guess:

```
database is at schema v10; this build understands v7 and will not operate on a
schema it does not know. Upgrade macrame rather than opening the file with an
older build.
```

(A 0.8.x build says `v8` in place of `v7`; the refusal is the same.)

That refusal is deliberate and it is not a bug. A build that does not know about
the marker gating would treat the guards as it always has, which is exactly the
silent corruption the gating exists to prevent.

**So: take a copy of the database file before the first 0.9.0 open.** That is the
whole of the rollback plan, and there is no other one.

**Rust users are not upgraded by accident.** Neither `macrame-db = "0.7"` nor
`"0.8"` accepts `0.9.0` under Cargo's caret rule for `0.x` versions, so a routine
`cargo update` cannot move you across the rungs. Crossing them requires editing
your manifest to `macrame-db = "0.9"`, which is the point.

Python users **are** upgraded by a plain `pip install -U macrame-db`. If you pin,
pin before upgrading.

## What is new

**Concepts archive.** `archive(cutoff)` now moves concepts to the cold file as
well as links and log rows. A concept is archivable when it is retired, its
`valid_to` is before the cutoff, its `recorded_at` is before the cutoff, and **no
surviving row of hot `links` names it in either direction**. Archivability is
reachability, not expiry — so concept archival is strictly downstream of link
archival, and the predicate is evaluated after the link delete inside the same
session.

You can ask which concepts qualify without archiving anything:

```rust
let ids = macrame::temporal::archivable_concepts(db.read_conn(), cutoff).await?;
```

The predicate says **eligible**, never **due**.

**Concepts rehydrate.** The new counterpart brings them back:

```rust
let report = db.rehydrate(&["c1", "c2"]).await?;
report.concepts_rehydrated;   // how many actually moved
report.rowids_reassigned;     // normally 0 — see below
```

```python
report = db.rehydrate(["c1", "c2"])
report.concepts_rehydrated
```

Ids that are not in the cold file are **skipped, not refused**: your list
generally comes from an earlier cold-side query, so being partly stale is the
normal case rather than an error.

**Rehydration is a move back, not a re-assertion.** It writes no
`transaction_log` rows and is invisible to both clocks, so `reconstruct(t)`
answers identically before archival, while archived, and after rehydration — bit
for bit, asserted against a never-archived control in both the Rust and the
Python suites. A rehydrated concept reacquires its old identity; it does not
arrive as something newly learned.

That is what the `v9 → v10` rung is for. The fold resolves last-writer-wins by
`seq_id`, not by timestamp, so a log row written at rehydration would take a new
sequence number, outrank the concept's own retirement, and bring it back **alive**
at every instant after its creation. Suppressing the trigger inside the session
is what stops that.

## Behaviour changes without a compile break

These change what your program does without the compiler telling you.

**Archiving now deletes embeddings and analytics annotations for archived
concepts.** The concept row itself crosses column for column, `content`
included — a move that drops a column is a rewrite. Its `analytics_annotations`
and `embeddings_<model>` rows are **deleted rather than moved**, because both are
derived artifacts recomputable from the content that did cross, and because
`F32_BLOB` and DiskANN do not exist on a plain ATTACHed file. Entity data
crosses; derivative data does not.

**If you archive concepts, you will need to re-embed them on rehydration.**
Nothing recomputes automatically.

**The concepts delete guard is now conditional.** `DELETE FROM concepts` from raw
SQL is still refused, exactly as before. What changed is that it is now permitted
*inside a declared archive session* — which only `archive()` and `rehydrate()`
open. If you were relying on the guard being unconditional as a safety net around
your own session-like code, it is not one any more.

**The unreachable-archive error message gained a diagnosis.** When a
`reconstruct` needs the cold file and cannot reach it, the error now says how
many log rows were archived out of the database and how far back the hot log
still reaches:

```
replay corrupt at seq 0: archive database file "…\kb_archive.db" does not
exist; 3 log rows have been archived out of this database; the hot log now
begins at seq_id 4 (2026-08-06T22:16:04.531638Z)
```

That is real output, path elided. The error class is unchanged — `ReplayCorrupt`
in Rust, `ReplayCorruptError` in Python — and only the sentence is longer, so
code matching on the class is unaffected and code matching on the message text
is not.

This is also the answer to a question 0.8.0 left open. A hot-side marker
recording *archived at* and *horizon* was considered for this release and
**refused**: the two facts a caller actually needs — how much went, and how far
back what remains reaches — are already derivable from the log itself, and an
archive timestamp is neither of them. So the better message arrived with no third
rung.

## Breaking changes

**`ArchiveReport` gained a field.** `concepts_archived: usize` sits between
`links_archived` and `log_entries_archived`. The struct is not
`#[non_exhaustive]`, so this breaks any Rust code that constructs it with a
struct literal or destructures it exhaustively. Reading fields by name is
unaffected. This is why the release is `0.9.0` rather than `0.8.5`.

Python is unaffected — `ArchiveReport.concepts_archived` is a new read-only
property and nothing was removed.

**`RehydrateReport` is new** in both surfaces, and is a class in Python rather
than a tuple despite carrying two fields, so that it reads like the
`ArchiveReport` it is the counterpart of.

## What it costs

Measured on the reference machine, one session, with a fixed control operation
in the same run to normalise against machine noise:

| | |
|---|---|
| Rehydrate, 1 concept | 3.71 ms |
| Rehydrate, 100 | 10.89 ms |
| Rehydrate, 1,000 | 77.70 ms |
| Rehydrate, 10,000 | 1.105 s |
| Archive, the same 1,000 concepts | 20.37 ms |

**About 3.7 ms fixed and ~74 µs per concept, linear to a thousand and not
beyond.** Ten times the rows cost 14.2× the time at the next decade. The cause is
FTS5 index maintenance, not the row movement: with the search-index trigger
dropped the same sweep is linear to within 1%, so the index is 32% of the cost at
a thousand concepts and 53% at ten thousand.

**Rehydration takes one transaction with no window boundaries**, deliberately —
it cannot half-happen. There is no `rehydrate_windowed` counterpart to
`archive_windowed`. A ten-thousand-concept rehydration therefore holds the write
lock for about 1.1 s, and every queued write waits that long: a channel wait in
Rust, which `busy_timeout` does not bound. That is well inside a contract that
already tolerates ~50 s for `rebuild_current()` on a large graph, but if you
rehydrate in bulk on a latency-sensitive path, do it in batches of your own
choosing.

Graph shape does not affect any of this. An archivable concept is one no edge
names, so topology cannot reach the rows being moved — measured across four
fixture shapes, 5.8% spread, which is noise.

## Upgrading

1. **Back up the database file.** The rungs do not go backwards.
2. Rust: change `macrame-db = "0.7"` (or `"0.8"`) to `"0.9"` in `Cargo.toml`.
   Python: `pip install -U macrame-db`.
3. Open the database once. The rungs apply automatically. From v8 that is
   milliseconds; from v7 budget a few seconds per 200k concepts, plus 9% free
   disk transiently.
4. If you archive concepts, plan to re-embed anything you later rehydrate.

No API you were already calling changed shape, apart from `ArchiveReport`'s new
field.

## Where the reasoning lives

The decision register carries the argument for each of these, including the
alternatives that were rejected and why:

* **D-128** — archivability is reachability, not expiry, and it reads both clocks
* **D-129** — the `v8 → v9` rung, and why `CREATE TRIGGER IF NOT EXISTS` kept a
  stale body that `verify()` could not see
* **D-130** — what crosses the archive boundary: entity data yes, derivative no
* **D-131** — rehydration is a physical move back, and why `seq_id` rather than
  `recorded_at` is what makes the `v9 → v10` rung necessary
* **D-132** — the measurements, and the hot-side archive marker refused outright
* **D-133** — the Python surface, and what of the doctrine gate does not cross it

See [`docs/architecture/s13-decision-register.md`](../architecture/s13-decision-register.md).
