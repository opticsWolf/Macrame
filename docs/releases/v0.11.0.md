# Macrame 0.11.0 — a number explained, a constant defended, and a rule that outgrew its own answer

**Crate `macrame-db` 0.11.0 · wheel `macrame-db` 0.11.0 · schema v10, unchanged**

*Both items Appendix C named for this release have landed. Crate and wheel are at 0.11.0; schema stays at v10.*

**No schema rung, no API change, no behaviour change.** A 0.10.0 database opens under 0.11.0 with no migration and nothing to do. Every public signature is what it was. **This release changes no code that runs in production** — what it changes is what this project knows about the code it already shipped, and one constant it now declines to change on purpose.

If you are upgrading and want the short version: nothing is required of you, and `chunk_rows::EDGES` still misses its latency budget on a populated database. That was true in 0.10.0 too. The difference is that it is now explained.

---

## The 3× budget miss has a cause

0.10.0 measured a 90-row edge chunk into an 8,000-edge table at **9.06 ms** against a 3 ms bound, and said in as many words that the cause was unknown. It is `trg_links_current_sync` — the trigger that keeps `links_current` in step with `links`.

Isolated by dropping the three `links` insert triggers one at a time and reading the *growth* from an empty table to an 8,000-edge one, because the residual is by definition whatever gets more expensive as the table fills:

| component | growth |
|---|---|
| total, all three triggers | **+4.15 ms** |
| ├ `trg_links_single_open` (the guard) | −0.85 — **zero within noise** |
| ├ `trg_links_current_sync` | **+4.65** |
| ├ `trg_links_log_insert` | +0.11 |
| └ bare `INSERT INTO links` | +0.24 |

Effectively all of it is the `links_current` write, and within that trigger **89% of the growth is secondary-index maintenance** rather than the upsert itself — the same statement run directly against the same 8,000-row table costs 0.49 ms, against the ~5 ms it costs inside the trigger.

**The guard contributing nothing is the other half of the result.** That is [D-059](../architecture/s13-decision-register.md#d-059)'s `v5 → v6` index doing exactly what it shipped to do, visible as a measurement rather than as an absence of complaints — and `chunk_rows::EDGES`'s own comment had been blaming that guard until this release.

### Four explanations that were tested and are wrong

Recorded because the next person to look at this row will think of them too. Each was a live hypothesis with a mechanism, and each is refuted by a measurement rather than by argument.

| hypothesis | result at 8,000 rows |
|---|---|
| page-cache pressure | no help |
| foreign-key enforcement | no help |
| an artifact of the instrument | no help |
| the fixture's key distribution | indistinguishable |

The third nearly published a wrong cause. The per-index arms came out *super-additive* — dropping either index alone recovered ~80%, which index maintenance cannot do — and the three fast arms turned out to be exactly the three that had run a `DROP INDEX` before measuring. "Any substantial write warms the connection" explained every number on the table without involving indexes at all. Two more arms separated them: a schema write touching no data, and a WAL checkpoint. Both read slow, so the instrument is not the story ([D-142](../architecture/s13-decision-register.md#d-142)).

**Nothing is fixed by this**, and the obvious fix is a trade rather than a defect. The expensive index is [D-042](../architecture/s13-decision-register.md#d-042)'s covering index for the traversal, and its width is the point — the recursive step never touches the base table. Narrowing it moves cost onto the read path six columns were chosen to protect.

## Four shapes agree on a constant, and it is not adopted

[D-059](../architecture/s13-decision-register.md#d-059) left the chunk constants open in these words: they *"are empty-database figures and need a realistic fixture, which requires deciding what 'realistic' means"*. The [D-088](../architecture/s13-decision-register.md#d-088) fixture matrix has been that decision since 0.6.0 and had never been applied to them.

**Three of the four constants hold** on a populated database, with headroom, and shape cannot reach them — those paths never read `links`:

| path | constant | populated | headroom |
|---|---|---|---|
| concepts | 70 | 1.76 ms | 1.7× |
| annotations | 600 | 1.34 ms | 2.2× |
| embeddings | 30 | 1.68 ms | 1.8× |

**The edge constant misses by 2.7×**, and all four shapes agree the largest size inside the bound is **20**, against a constant of 90:

| rows | star | clustered | chain | dense_small |
|---|---|---|---|---|
| 20 | 2.11 | 2.50 | 2.55 | 2.32 |
| 45 | 3.98 | 4.27 | 5.37 | **9.70** |
| 90 (the constant) | **8.22** | 8.75 | 10.83 | 12.60 |

Appendix C asked for "four shapes, four constants". The answer is four shapes and *one* constant that needs anything — and the three that hold are why the item was worth running rather than assuming.

The matrix earns its keep twice here. **The verdict is shape-independent and the cost is not**: `dense_small` is 2.4× the star at 45 rows, reproduced to 9.70 and 9.71, so the agreement is a result rather than an artifact of measuring one thing four times. And **`chain` is the worst shape at five rows** — 1.53 ms against 0.38 — which inverts the expectation that a hub is the hard case. Below the crossing, fixed transaction cost dominates.

### Why the constant stays at 90

**Because 20 is not a fix. It is the same defect at a different population.**

Per-row cost on this path grows with the size of `links_current`, which is the mechanism above. 20 rows meet 3 ms *at 8,000 edges*; at 80,000 they will not, and re-deriving a row count per release is a treadmill rather than a design. Against that, the cost of moving it is certain and immediate — [D-058](../architecture/s13-decision-register.md#d-058) measured chunking as a throughput *loss* on this path, so cutting 90 to 20 turns eleven chunks into fifty and pays that on every bulk import, to buy conformance at one table size ([D-143](../architecture/s13-decision-register.md#d-143)).

### What the re-derivation actually found

The question was mis-shaped, and [D-058](../architecture/s13-decision-register.md#d-058) had already said so without anyone noticing the consequence: **the golden rule is a bound on duration, and a row count is "an answer to the rule"** rather than the rule. The four constants are that answer fitted at one population, and this is the measurement showing it has expired on one of the four paths.

So the fix is not a number. It is for the chunk loop to stop on **elapsed time** approaching `CHUNK_BUDGET`, with the constants becoming an upper bound rather than the criterion — a write-actor design change with its own alternatives, named for 0.12.0 rather than taken as a side effect of measuring.

**Nothing needs to wait for it.** [D-079](../architecture/s13-decision-register.md#d-079)'s `MetricsSnapshot` already counts holds over `CHUNK_BUDGET` and names the longest with the command that caused it, so a deployment actually suffering this can see it today. That is why the miss is a documented, measured limitation rather than an emergency.

## The claim registry learned to cite an experiment

`tests/perf_claim_tests.rs` shipped in 0.10.0 keyed to criterion groups. Both findings above are attributions — sets of arms differing by one component — and criterion measures one arm at a time, so neither could be registered. The field now also accepts `example:<file>/<experiment>`, matched against the `match` arm that selects the experiment rather than against the name anywhere in the file.

**An unregistered example file is a panic, not a pass.** That is the whole risk of widening a gate: a check that silently accepts what it does not recognise is worse than no check, because it reads as one. Every new gate was made to fail before being trusted — five mutations, five reds, all reverted.

Without this the registry could only cover figures produced by `benches/`, which is a minority of what this project publishes; [D-056](../architecture/s13-decision-register.md#d-056) and [D-059](../architecture/s13-decision-register.md#d-059) are both example-backed. A registry that cannot express its own evidence silently narrows to the claims that happen to fit it.

## One stale sentence, found in the file that measures the constant it describes

`chunk_scaling`'s doc comment said *"Every size here is ≤ `CHUNK_ROWS`, so each measurement is exactly one chunk and one transaction."* That was true in 0.5.5, when `CHUNK_ROWS` was a single constant at 1,000. [D-058](../architecture/s13-decision-register.md#d-058) replaced it with four per-path constants of 90 / 70 / 600 / 30 **in the same release**, and the sentence was not revisited — so on three of its four paths the sweep's larger points are several transactions, measuring the chunked path rather than a chunk.

Same defect class as the 47.7 ms figure 0.10.0 spent itself correcting: a sentence that stayed behind when the thing it described moved.

## What has not changed

* **No schema rung.** Schema v10, same as 0.9.0 and 0.10.0.
* **No API change and no behaviour change.** Every public signature is what it was, and no code path executes differently. The only edits to `src/` are documentation.
* **`chunk_rows::EDGES` is still 90**, and still misses the 3 ms bound on a populated database. Deliberately, with the reasoning above.
* **R15 is not fixed.** The upstream libSQL access violation on concurrent database opens is unchanged, and so are its mitigations.
* **The performance budgets are still not CI gates** ([D-055](../architecture/s13-decision-register.md#d-055)).
