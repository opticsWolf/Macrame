# Macrame 0.12.0 — the chunk loop stops on time, and two measurements say less than they were meant to

**Crate `macrame-db` 0.12.0 · wheel `macrame-db` 0.12.0 · schema v10, unchanged**

*The single item Appendix C named for this release has landed. Crate and wheel are at 0.12.0; schema stays at v10.*

**No schema rung and no API change.** A 0.11.0 database opens under 0.12.0 with no migration and nothing to do, and every public signature is what it was. **There is a behaviour change**, and it is the point of the release: `bulk_import`, `write_concepts`, `write_analytics_annotations` and `upsert_embeddings` no longer split their batches at a fixed size.

If you are upgrading and want the short version: the typical stall behind a bulk write is about half what it was, the worst stall is unchanged, and the number of `recorded_at` stamps a bulk write produces is no longer reproducible run to run. That last one is the only thing that can affect you, and only if you were relying on it.

---

## The row count stopped being chosen ahead of time

0.11.0 re-derived the four `chunk_rows` constants against all four [D-088](../architecture/s13-decision-register.md#d-088) shapes and reached a conclusion about the question rather than the answer: **no row count can bound a duration on a path whose per-row cost grows with the table.** All four shapes said the largest in-budget edge chunk was 20 against a shipped 90, and 20 would have been wrong at 80,000 edges for the same reason 90 is wrong at 8,000.

So the loop measures instead. The actor times its own transaction and returns the duration with the row count; the caller-side chunk loop sizes the next chunk from it. The four constants are now **ceilings** — where the loop starts and the largest chunk it will ever send — and every derivation [D-058](../architecture/s13-decision-register.md#d-058) gave them still applies to them in that reading.

The control law is deliberately asymmetric. Over budget it shrinks proportionally; comfortably under, it grows by a quarter; between, it holds. *Back off fast from a bound you are exceeding, approach it slowly.* It is a pure function with unit tests, so the clamps are checked without a database, a clock or an actor.

### Three things it does not do, all from one fact

The SQLite write lock is not preemptible. That is the fact §5.1.5 has been built on since 0.4.5, and it makes this **feedback, not preemption**:

1. The chunk in flight always commits in full. Nothing is aborted, and a caller queued behind one still waits for all of it.
2. A batch small enough to be a single chunk gets no protection at all, because there is no next chunk to size.
3. The bound is met only *after* the loop has been told it was missed.

---

## What it bought, and what it did not

Measured on the [D-088](../architecture/s13-decision-register.md#d-088) matrix — a 900-edge `bulk_import` into each of the four shapes at 8,000 edges, read from the actor's own per-transaction timings, two sessions ([D-146](../architecture/s13-decision-register.md#d-146)):

| | adaptive | fixed at the ceiling |
|---|---|---|
| **typical stall** (mean hold) | **3.4–3.7 ms** | 7.1–8.3 ms |
| **worst stall** (longest hold) | 7.7–10.2 ms | 7.6–15.2 ms |
| throughput | — | **9–20% faster** |

**The typical stall halved.** That is what an interactive write arriving at a random moment actually experiences, and it is the number §5.1.5 exists to protect.

**The worst stall did not move.** The worst chunk is the *first* one, at the ceiling, before any feedback exists — limitation (3) above, which turns out to be the dominant effect on this path rather than a footnote. Fixing it needs a warm-up chunk, which is a size chosen ahead of time by another name; it is named for 0.13.0 with the measurement it requires, not taken here as a side effect.

### The floor is the operating point, not a backstop

`CHUNK_FLOOR = 35` stops the loop shrinking indefinitely, which it otherwise would: per-row cost on the edge path grows with the table, so there is no size at which the fixed ~0.8 ms of a transaction stops dominating, and an unbounded loop reaches chunks of one or two rows and never finishes.

Measured, the trace is `[90, 35, 35, …]` on **all four shapes**. The proportional shrink from a 90-row chunk proposes ~31 rows, which clamps — so the loop reaches its operating point in one step and never selects a size between the two. On this path the controller is not finding an optimum; it is a mechanism for arriving at 35 without 35 having been fitted, which is the property [D-143](../architecture/s13-decision-register.md#d-143) says a constant cannot have.

A 35-row chunk costs **3.11–3.43 ms** against a 3 ms bound. That miss is steady state and deliberate, and it is defended by the argument the bound answers to rather than by the bound: an interactive assertion waits ~3.2 ms for the chunk in flight and then runs its own ≤ 5 ms write, so **~8.2 ms against a 16.7 ms frame**.

**That figure is also a correction.** The floor shipped documented at "≈4.1 ms, a ~1.1 ms miss", extrapolated from the size sweep rather than measured against the loop — a real measurement applied to a question it does not answer. It was caught when the loop was finally measured, in the same wave.

## The fidelity boundary gained a sentence, and it is a real loss

[§5.1.6](../architecture/s5-modules.md#516-the-fidelity-boundary-of-chunked-writes) promises that each chunk is a distinct learning event under its own `recorded_at`. Everything it promises survives: one transaction per chunk, one stamp per chunk, `reconstruct(ts)` mid-write still observes a prefix and never a partial chunk, `seq_id` is still strictly monotonic, [Doctrine III](../architecture/s0-s3-foundations.md#doctrine-iii) and [Doctrine IV](../architecture/s0-s3-foundations.md#doctrine-iv) are untouched.

**What is no longer promised is that two identical batches produce identical stamps.** The boundaries now depend on how fast the machine was. If you need reproducible stamping, `write_bulk_atomic` is the escape hatch and always was.

That found a caller relying on it inside this repo: a test seeding two databases and comparing their contents, `recorded_at` included. It now runs both rebuilds over one seeding, which is the stronger comparison anyway — identical input rather than input that was supposed to be identical.

## Two tests that had to stop asserting where the boundary falls

`bulk_import_is_atomic_per_chunk_not_overall` is the executable form of §5.1.6 and pinned exact row counts. It now asserts the property: a contiguous prefix commits, and each stamp covers one contiguous run of it — checked as *number of distinct stamps equals number of runs in batch order*. Whole-chunk rollback moved to a single-chunk case, where the boundary is known without naming a size.

**And the first version of that rewrite was still wrong**, which is the more useful half of the story. It asserted `committed < n`, meaning *at least one good row shared the failing chunk* — true only when the violation does not land first in its chunk, which is now a fact about the machine. The test written to stop pinning boundary positions pinned one, three lines below a doc comment naming that exact hazard. It failed **26 times in 120 runs** and was found by a measurement aimed at something else entirely.

## R15: the study replaced a number with the reason there isn't one

README carried *"alone it is ~50/50"* for the quarantined property-test step. Measured directly — `--features property-tests`, one attempt, 100 consecutive runs — it is **93 of 100** on that machine under sustained load, 95% interval 86–97% ([D-147](../architecture/s13-decision-register.md#d-147)).

**And the step is not red 65% of the time in CI**, which is what six attempts at 93% predicts. CI's own 2-in-9 on `main` implies ~78% on the runner. Both numbers are real. So the five figures this project has published for R15 — 45%, 60%, 75%, 78%, 93% — were never competing estimates of a constant. **They are five machines under five loads.** The rate is a property of the box, and `.cargo/config.toml` is the only place it lives; README, `ci.yml` and `run_rust_suite.py` now point there instead of restating it.

The retry budget is unchanged. At any rate in this range no budget makes the step a gate, and more attempts only buy more chances to launder a real failure into a pass.

Two methodological notes are recorded with it, because both cost time. **A flaky test biases a crash rate downward** — the classifier reports a genuine failure before it looks for a crash, so the study's first pass read 71% where the second read 93%; that was not a quieter session, it was the same number with a bug standing in front of it. And the study's own harness misattributed failures to two binaries that had never failed, because it scraped the log tail instead of reading the classifier's attribution.

## A gate for a claim about where things live

`docs/quickref.md` credited `util/limits.rs` with five constants, of which it holds one; the other four are in `connection.rs` and `temporal/replay.rs`. Five releases, no test could see it, found by a reader passing through.

`a_passage_that_places_a_constant_names_the_file_it_is_in` is the executable form: a passage naming a source file and a constant must name the file the constant is declared in. It runs on the documents where a file name is an inventory entry — quickref, README, Appendix A — and not on the architecture set, because §5.1 contains a *correct* sentence that names one file and one constant declared elsewhere, as a contrast, and nothing reading names and proximity can tell that from a misplacement.

## What has not changed

* **No schema rung.** Schema v10, same as 0.9.0 through 0.11.0.
* **No API change.** Every public signature is what it was. `ChunkOutcome` is new and public only because `LowPriCommand` is; it is not re-exported at the crate root.
* **`chunk_rows::EDGES` is still 90.** It is now a ceiling rather than a size, for the reasons [D-143](../architecture/s13-decision-register.md#d-143) gave for not moving it.
* **R15 is not fixed.** The upstream libSQL access violation on concurrent database opens is unchanged, and so are its mitigations. What changed is what this project claims to know about its rate.
* **The performance budgets are still not CI gates** ([D-055](../architecture/s13-decision-register.md#d-055)).
* **`HoldTimer` left the `metrics` feature gate**, so one `Instant::now()` pair per actor turn is now paid in every build. [D-079](../architecture/s13-decision-register.md#d-079)'s histogram is still gated and `ActorMetrics` is still an empty ZST without the feature. Gated, the timer returned `Duration::ZERO`, which the controller reads as *comfortably under budget*.
