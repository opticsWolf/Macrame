# Macrame 0.19.0 — the blob store

Crate macrame-db 0.19.0, wheel 0.19.0. Schema v21 → **v22**, one rung; concept log
payload v3 and snapshot container v5, both unchanged; MSRV 1.88 unchanged; `DbError` 45 →
**47** variants. Public surface 1,836 → **1,909 items**, every one additive. Decisions
**D-281, D-287, D-288** — the number 0.18 held open, and two new ones. One item, P4, on
`dev/0.19.0`.

0.18 opened the attribute layer; this release gives those attributes somewhere to point at
bulk bytes, under the rule the 0.18 plan set for it: **the store gets no reclamation path
of its own and uses the archive's.** A blob is kept while anything still reads a log entry
that names it, and goes to the cold file — never away — when nothing does.

## Breaking changes

None to any API. Every surface change is additive, and `ArchiveReport` and `Tuning` were
already `#[non_exhaustive]`, so their new fields break no caller.

**Forward incompatibility, stated rather than discovered.** A v22 database handed to a 0.18
binary is refused at open on schema version, as every rung has been. There is no partial
read path to protect: 0.18 has no blob API to read one with.

**A new dependency.** `sha2` 0.11 (RustCrypto, MIT OR Apache-2.0), pure Rust,
`rust-version` 1.85. It adds **seven** packages to `Cargo.lock` — `sha2`, `digest` 0.11,
`block-buffer` 0.12, `crypto-common` 0.2, `hybrid-array` 0.4, `const-oid` 0.10 and
`cpufeatures` 0.3. The plan expected some to be shared with libsql's TLS stack; none are,
and the plan's sentence is corrected in place.

## Added

**`Database::blob_put(&[u8]) -> String`, `blob_get(&str)`, `blob_stat(&str)`**
([D-281](../architecture/s13-decision-register.md#d-281)). Content-addressed bytes. The
address is **SHA-256 as 64 lowercase hex characters** — exactly what
`hashlib.sha256(data).hexdigest()` and `sha256sum` print, so an application can compute it
without the database and check whether the store already holds a file before sending it.
A re-put of bytes the store holds adds no row and refreshes `put_at`. `blob_get` reads the
hot file, then the cold one; `blob_stat` returns size, `put_at` and which file answered,
without reading the bytes. Capped at `Tuning::max_blob_bytes`, **8 MiB** by default
(`DEFAULT_MAX_BLOB_BYTES`), because libsql 0.9.30 passes a blob only as a whole
`Vec<u8>`. Two errors: `BlobTooLarge { size, max }` (Budget) and `InvalidDigest`
(Validation), the second so a malformed address is not mistaken for an absent blob.

**A reference is the digest's text** ([D-287](../architecture/s13-decision-register.md#d-287)).
Put the address anywhere in a concept or link — `extra`, `content`, a link's `properties`,
inside a URL — and that is the reference. No reserved key and no prefix: a scan that
recognizes too much holds a blob a little longer, one that recognizes too little archives
one a hot entry needs, and only the first is harmless. Uppercase, base64 or a truncated
prefix is **not** a reference, which is the one sentence the API documentation carries.

**The archive moves blobs, and brings them back**
([D-288](../architecture/s13-decision-register.md#d-288)). Each `archive` session, after
the log has been archived, moves to `cold.blobs` every blob that no hot log entry names and
that was last put before the cutoff, and copies back any cold blob a hot entry names again.
History counts as a reference: superseding the concept that named a blob does not release
it while the superseded entry is still hot — which is precisely what a reference count would
get wrong, and why the 0.18 proposal's refcount was withdrawn rather than adjusted.
`archive_branch` runs no blob step; the next `archive` finds what it released.
`ArchiveReport` gains `blobs_archived`, `blobs_restored` and `blob_scan_bytes` — the last
`0` when there was no blob to decide about, which is what an unused store costs.

**The table is guarded like the ledger** ([§4.10](../architecture/s4-schema.md#410-blobs--content-addressed-bytes-reclaimed-by-the-archive-0190-d-281-d-287-d-288)).
`trg_blobs_frozen_update` refuses any rewrite of `sha256`, `size` or `bytes`, unconditionally
(`AbortKind::BlobImmutable`); `trg_blobs_guard_delete` admits a delete only inside an
archive session. `verify` requires both and body-probes the second for the marker. The
address rule — 64 lowercase hex — is a `CHECK` on the file, not only on the API.

**Python**: `Database.blob_put(bytes) -> str`, `blob_get(str) -> bytes | None`,
`blob_stat(str) -> BlobStat | None`; `BlobStat` with `location` as `"hot"` / `"cold"`;
`open(max_blob_bytes=)`; `DEFAULT_MAX_BLOB_BYTES`; `InvalidDigestError` and
`BlobTooLargeError` with their attributes; the three new `ArchiveReport` fields. No digest
helper — `hashlib` is the helper, and a test asserts the two agree.

## Changed from the plan

**Cold reads use their own connection, not `ATTACH`.** The plan had `blob_get` reach the
cold file through the `ATTACH`/`DETACH` discipline `rehydrate` uses. That is safe on the
writer, which runs one command at a time, and not on `read_conn`, which every reader on the
handle shares: an `ATTACH` for one blob read is visible to — and can be detached under — a
concurrent reader. The landed design is a dedicated `SQLITE_OPEN_READ_ONLY` connection to
the cold file, opened on first use and dropped on any error, which also makes *a blob read
never writes the cold file* a property of the open flags. Recorded in D-288.

## Performance

Measured by the two new bench groups in `benches/budgets.rs`, release build, one session on
the reference machine (gate 12).

| size | SHA-256 alone | `blob_put` | hash share | `blob_get` (hot) |
|---|---|---|---|---|
| 64 KiB | 29 µs | 471 µs | 6 % | 14 µs |
| 1 MiB | 455 µs | 5.97 ms | 8 % | 747 µs |
| 8 MiB | 3.72 ms | 47.9 ms | 8 % | 10.3 ms |

**Hashing is not where a put spends its time**, which is what D-281 amendment 3 claimed in
choosing SHA-256 over BLAKE3 and now has a number for: a hash several times faster could
save at most the third column. The writer's hold is the put minus the hash, since the hash
runs on the caller's side before the command is queued — **~44 ms at the 8 MiB cap**, under
`BLOB_WARN_HOLD`'s 100 ms by a factor of about two.

The archive's blob step, over a hot log nothing leaves, with unreferenced 64-byte blobs so
the scan cannot stop early:

| candidates | 2,000 entries | 20,000 entries |
|---|---|---|
| 0 | 8.3 ms | 38.6 ms |
| 10 | 10.5 ms | 49.8 ms |
| 10,000 | 282 ms | not run |

The scan is the 0 → 10 difference — ~2 ms and ~11 ms, about a fifth of the session at the
larger size — so D-287's escalation (a write-time reference table) is not taken. The 10,000
row is the *move*, not the scan.

## Acceptance

The plan's thirteen gates. 1–11 are `tests/blob_tests.rs` unless noted.

1. **Round trip.** The NIST vectors, the empty input included; byte-equal reads; a re-put
   adds no row and advances `put_at`. The Python half asserts equality with `hashlib`.
2. **Cap.** One byte over is refused naming both numbers; a raised `Tuning` admits it; a
   lowered one bites; the empty blob is legal.
3. **The negative control.** Version 1 names `X`, version 2 names `Y`: after an archive `X`
   is cold, `Y` hot, `reconstruct` at version 1 names `X`, and `blob_get(X)` returns it.
4. **Pinned history.** A fork between the versions keeps `X` hot; `archive_branch` plus
   `archive` sends it cold.
5. **Branch-only references** hold a blob until the branch is archived.
6. **Placements.** Link `properties`, concept `content`, a URL and a longer hex run each
   hold a blob; an uppercase digest does not.
7. **Age guard.** Old and unnamed goes cold; young stays; old but re-put after the cutoff
   stays.
8. **Copy-back.** `blobs_restored == 1`, the blob hot, the cold copy still present, and the
   next session a no-op.
9. **Cold tolerance.** A cold file with its `blobs` table dropped answers `None`, is
   byte-identical afterwards, and the next archive creates the table.
10. **Guards.** Inside a hand-made session a delete is admitted and a rewrite of `bytes`
    is not; outside one, and `verify`'s refusal of an ungated guard body, are in
    `tests/migration_tests.rs`.
11. **Zero cost when unused.** `blob_scan_bytes == 0` on a ledger with no blobs, with a
    positive control that the counter moves.
12. **Hold, measured.** Above.
13. **Rung.** v21 → v22 on a populated database with `verify` clean
    (`a_v21_database_climbs_to_v22_and_gains_a_guarded_blob_store`); a newer file is
    refused by `refuses_a_database_from_a_newer_build`.

**Two gates were checked by mutation, not only by passing.** With the scan disabled six of
the twelve blob tests fail — exactly gates 3, 4, 5, 6, 8 and 11, the ones whose answer
depends on finding a reference; with the age clause removed gate 7 fails and nothing else
does. Both mutations were restored from a copy of the file taken before each.

## What is not closed

- **The scan's cost at §9's largest ladder sizes is extrapolated, not measured.** It is
  linear in hot payload bytes by construction; the two measured points put a million-entry
  hot log at roughly half a second per session that has any blob candidate.
- **Moving 10,000 small blobs costs ~27 µs each.** Not the gate's concern and not
  investigated; recorded so the number is not rediscovered.
- **C1 — `MAX_EXTRA_BYTES` against OKFgraph's real frontmatter** — optional in the plan and
  still unchecked.
