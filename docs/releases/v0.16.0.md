# Macrame 0.16.0 — what is guaranteed

Crate macrame-db 0.16.0, wheel 0.16.0. Schema v15 → **v17**; snapshot container v4 and its
v3 header unchanged; MSRV 1.88 unchanged. Public surface 1,624 → **1,761 items**.
`DbError` 41 → **42 variants**. Decisions **D-243 … D-263** — twenty-one of them, one per
release, across waves W13, W14, W15 and W16, plus the two that made this note's own
acceptance list checkable ([D-262], [D-263]).

The cycle began with a written review of 0.15.0: twenty-four numbered code findings and six
architectural notes. Twenty-six of those thirty are closed here. That is the boring half.

**The interesting half is that the review was reliably right that something was wrong and
much less reliably right about why**, and every correction in this release is a measurement
rather than a re-reading. Its only **High** was High. Its C-4 asked for an index that is
*never faster than no index*. Its C-11 named three structs and the defect was twenty-one
structs wide. Its C-8's suggested fix repeats the bug it describes, one line further down
the query. Its A-2 was scheduled behind a cache that turned out to cost more than the thing
it caches. Its C-9's obvious compromise was refused by the numbers. Its C-13 — filed
**Low**, with the words *"nothing downstream is wrong"* — is a live data-availability bug
that makes an ordinary public call render a database's whole history unreadable.

And the largest single defect of the cycle is not in the review at all. `links_at_tx` had
been running as a co-routine inside the recursive step since 0.13.2 — **10.6 s where the
answer takes 59 ms** — hidden from eleven releases of branching probes because they were all
shaped to time the branched read, and the branched read's window materialises on its own.

## Breaking changes

- **Twenty-one more public structs are `#[non_exhaustive]`** (W15.3, D-255). C-11 named
  three and gave the argument; the argument applies unchanged to every public struct with
  public fields, counted off the checked-in surface. Struct literals and exhaustive
  destructuring of these types stop compiling outside the crate. They are all in one release
  because there is one pre-1.0 window and splitting it costs a caller two breaks for one
  decision. This **reverses [D-155]**, which had declined the attribute on report structs.

  The attribute has a second failure mode and it is the silent one: on a struct nothing else
  can build, it makes the type *unconstructible* from outside while the crate keeps
  compiling. It fired three times, so three constructors are new and are part of the
  contract rather than a convenience — `Overlap::new`, `NodeAttributes::new`, and
  `MaterializedState::empty`, the last because `save_snapshot` is public and takes a
  `MaterializedState` **as a parameter**.

- **Schema v15 → v17, two rungs, forward-only.** v16 adds `log_integrity` and
  `trg_txlog_mark_gap` (W14.5, D-249); v17 adds `(table_name, entity_id, branch_id, seq_id
  DESC)` on `transaction_log` and its counterpart on the cold file (W15.2, D-254). Each
  climbs from a database that stopped at the previous version, asserted by its own rung
  test, and each rung asserts *what it is for* rather than that the ladder reached the top.
  An older crate cannot open a v17 file.

- **`FilteredVectorSearch::probe_cap` bounds work, not the answer** (W13.5, D-252). Same
  signature, and it can now return **fewer** ids for the same cap. The old form ran the
  traversal to the end of the graph and then did `ids.truncate(probe_cap)`, so a name that
  read as a cost ceiling was a ceiling on the size of the result. The cap is now the walk's
  own `limit`, and the two are different numbers: dedupe on `(node, depth)` and the retired
  filter both drop rows the walk has already paid for, so a cut walk yields fewer ids than
  its row count. Anyone who tuned `probe_cap` for a result size needs to re-tune it.

- **`rehydrate` refuses a concept whose lineage has been archived, by name** (W15.1, D-253).
  It used to reach the `branches` foreign key and surface `DbError::Engine` carrying
  `FOREIGN KEY constraint failed`. It now returns **`DbError::BranchArchived { branch,
  concept }`** under `ErrorKind::Branch`, refused *before* the insert. `DbError` is already
  `#[non_exhaustive]`, so the new variant is not itself a break — the change in *which*
  variant an existing call returns is. Python gains `BranchArchivedError` with both names as
  attributes.

- **`diagnostic_conn` no longer hands out an independently owned connection** (W15.4/W15.5,
  D-256, D-257). Same signature, changed guarantee: there is now one connection per
  `Database`, minted on first use, and callers share it. It is **scrubbed on entry** — a
  leaked transaction is rolled back, and a connection carrying temp objects or an attachment
  is discarded rather than handed on. A caller that relied on session state persisting
  between its own `diagnostic_conn()` calls will not find it there.

- **Python: `MaterializedState.edges` documentation now forbids what it used to suggest.**
  Filtering that list by lineage was already wrong and the docstring half-said so; it is now
  explicit that neither half of the resolution rule can be written as a predicate over those
  tuples, because they carry no `recorded_at`. Use `Database.reconstruct_on(ts, branch)`.
  No signature changed; a caller doing the filtering was getting wrong answers before.

## Added

- **`macrame::plan`** — the twelfth public module, and one value for the three qualifiers
  every read surface was spelling for itself (W13.4, D-251, review F-34). `ReadPlan` carries
  lineage, valid instant, recorded instant and `limit`, so *"read `exp` as it stood on
  Tuesday, under what we believed in March"* is something the crate can pass, store and
  compare. `TraversalBuilder::plan`/`read_plan` take and produce one.

- **`Database::edges(ReadPlan)`**, which is the surface that gains a *capability* rather
  than a spelling: `query_as_of_edges_on` has no transaction-time argument, so that question
  previously meant walking from a start node you do not have, or folding the whole log. It
  returns `EdgeBelief`, so a row says which lineage holds it. `query_as_of_edges_on` is now
  that same statement with `recorded` unset, and its own two-arm `match` is deleted.

- **`Database::reconstruct_on(ts, branch)` and `Database::ancestry(branch)`** (W16.1,
  D-259). `reconstruct` answers for the whole ledger and labels every lineage's belief;
  `reconstruct_on` answers for one, applying the nearest-holder rule and each fork point's
  cutoff. `Ancestor { branch_id, dist, cutoff }` is public with `new` and `cutoff`, because
  the pure `resolve_beliefs` should be statable without a database.

- **`WalkOutcome` and `TraversalBuilder::execute_ids_explained`** (W13.5, D-252). `n` counts
  walk rows, and the answer is at most `n`, so `len()` cannot tell you whether the ceiling
  bit. `WalkOutcome` is read from the walk's own row count in the same statement, on a
  projection anchored on that count, so a walk whose every concept is retired still reports.
  Python gains `limit=` and `traverse_ids_explained`.

- **`Database::verify_last_link()`** (W16.2, D-261). The affordable half of
  `verify_snapshot_chain`: re-derives the newest snapshot from the one before it — one
  anchored delta, not a fold from genesis — and returns `None` until there are two
  snapshots. **The snapshot cadence runs it after every anchor it writes**, logging a
  divergence at `warn`, which is the first time anything in this crate has checked snapshot
  composition outside a test. It reports and does not repair.

- **`Database::scrub_diagnostic_conn()`** (W15.5, D-257) — infallible, empties the shared
  slot unless what is in it is fit for the next caller. The Python binding runs it on the
  way out.

- **`Tuning` gains six setters** and `SnapshotCadence` two, as the constructors that
  `#[non_exhaustive]` obliges.

- **Python parity in the same releases**, not behind them: `ReadPlan` (as keyword arguments
  rather than a builder, on purpose), `reconstruct_on`, `ancestry`, `edges`,
  `traverse_ids_explained`, `limit=`, `verify_last_link`, `BranchArchivedError`.

## Fixed

- **The transaction-time fold ran once per walk row** (W13.2, D-244). `links_at_tx` was a
  co-routine inside the recursive step: **10.6 s against 59 ms** on 11,110 edges, on every
  shape, since 0.13.2. `AS MATERIALIZED`, pinned on all three shapes. It survived eleven
  releases of branching work because every probe in that period timed the *branched* read,
  whose window materialises on its own.

- **The archive rebuilt the whole projection to repair a slice of it** (W14.1, D-245, the
  review's only High). The projection is pointwise in the key, so the session now collects
  the keys its `DELETE` will disturb — with the delete's own predicate, before it runs — and
  re-derives only those. `shadow.rs` had kept a private copy of the restricted projection;
  there is one generator now.

- **An archived database refused every recorded-time hydrate**, including instants the hot
  log still covers (W14.2, D-246). `hot_log_answers_for` took a timestamp and ignored it, so
  the first archive session took `as_of_recorded` and `AttributeMode::AtTime` away for the
  ledger's whole history, `now` included. **And a second defect behind it**: with no archive
  file passed, the reach test was still `MIN(recorded_at) <= ts`, so a path-less
  `reconstruct` returned a state holding an edge out of a concept it said did not exist —
  silently.

- **An empty cold file counted as an archive, and an ordinary call created one** (W16.2,
  D-261, review C-13). `ATTACH` creates the file before any DDL runs, so `rehydrate` on a
  ledger that had never been archived attached, met `no such table: cold.concepts`, returned
  that error, and left **0 bytes** on disk. From then on every reader that asked
  `path.exists()` believed rows had been archived, and every `reconstruct` below the newest
  hot stamp took the cold arm and failed with a raw `no such table: cold.transaction_log`.
  Three parts, doing three different jobs: an empty file is not an archive (which **heals a
  database already in that state**, at open, with nothing to delete by hand); `rehydrate`
  does not attach when there is nothing to attach; and `COLD_SCHEMA` moves inside the session
  transaction, which is what makes *non-empty* mean *complete*.

- **The overlap guard was a second spelling of the lineage resolution** (W13.3, D-250),
  fifty lines of it, kept honest by one test asserting the two agreed. Six mutations against
  the replacement; the survivor was a *correctness* hole — an unnarrowed churned set makes
  another key's pre-fork interval this key's overlap — and it has a test now.

- **A leaked `BEGIN` on the shared diagnostic connection pinned a WAL read snapshot** (W15.5,
  D-257). Measured: 200 writes later the diagnostic surface answered **1 row where the
  database held 201**, and `checkpoint()` — a typed public method — moved nothing, leaving
  the WAL at **8.5 MB**. This was the one item on nobody's list, and the only one whose
  damage escapes the diagnostic surface.

- **The shadow swap recreated indexes and triggers by substring match on DDL text** (W16.2,
  C-12). Two named lists now, with tests that fail the build if the schema grows an index or
  trigger they do not carry.

- **`registered_models` hid real models.** `NOT LIKE '%_shadow'` reads as *any character,
  then "shadow"*, so a perfectly ordinary model named `ashadow` was absent from its own
  registry. The arm is **deleted** rather than escaped: the `embeddings_` prefix already
  excludes every libSQL internal, so escaping would have kept a filter that can only fire on
  a real model.

- Smaller, in the same batch (D-261): `save_and_prune`'s `JoinError` arm raises
  `SnapshotWriteFailed` — the arm [D-240] did not reach; `abort_kind` requires
  `SqliteFailure(1811, …)` before it reads any text; the hybrid rank lookup is a `HashMap`
  rather than a scan per hit per list; and the anchored fold's comment stops repeating a
  mechanism [D-049] disproved.

## Performance

Every figure below is one Windows box, measured on both sides of the change in one process.

| Change | Before | After |
|---|---|---|
| Transaction-time fold, 11,110 edges (D-244) | 10.6 s | **59 ms** |
| Forked trunk, current read (D-244) | 43.1 ms | **18.4 ms** |
| Archive repair of a 200-key slice, 2K / 20K / 100K links (D-245) | 13 / 133 / 701 ms | **2.26 / 2.52 / 2.97 ms** |
| `Database::archive` end to end, 20K ledger (D-245) | 447 ms | **115 ms** |
| Reach guard at 500,000 log rows (D-247) | 24.24 ms | **0.004 ms** |
| `hot_log_is_intact` at 500,000 rows (D-249) | 32.6 ms | **0.033 ms** |
| Single-edge write, trunk / forked (D-248) | 0.184 / 0.401 ms | **0.099 / 0.106 ms** |
| Log fold with the v17 index (D-254) | 73.1 ms | **46.2 ms** |
| `reconstruct` (D-254) | 99.5 ms | **72.6 ms** |
| `diagnostic_conn`, warm (D-256) | 82.7 µs | **19.9 µs** |
| Recorded-instant read on a fork, depth 1 (D-259) | 2254.6 µs | **1879.7 µs** |

**The archive repair's result is the shape, not the ratio** — flat where it was linear. So it
is pinned on the *key set* rather than on the answer: a too-wide key set is still correct and
costs back everything the release saves.

**A forked database was paying 2.2× on every write**, almost all of it recompiling the
overlap guard's resolved form (D-248). The actor is the only writer, so it may keep what it
learns; it kept nothing. `ActorState` holds three facts, invalidated by name.

**Three things got slower on purpose, and each is written down.** The v17 index costs
**+8.2% file** and **+5.0%** on single-edge assertions. The diagnostic scrub takes a clean
warm call from **18.6 µs to 29.8 µs**, because no dirt check can see a pragma and the crate's
own must be restated. The shared `visible` join costs the branch write **3.0%**, which buys
the forked trunk **6.6%** by letting it stop taking the resolved form at all.

## Measurements that closed questions

- **C-4's index is never faster than no index.** The review asks for `(entity_id,
  branch_id)` because *"the fold partitions on that"*; the four folds partition on
  `(table_name, entity_id, branch_id)`, `table_name` leading deliberately since a concept's
  id and a link's synthetic id share a namespace. Measured: 73.1 ms against 64.2 with no
  index, and 64.6 against 63.6 on a second run — wide enough to pull the fold off
  `idx_txlog_time` and unable to supply the window's order, so the plan becomes a scan plus
  the same sort. **The `DESC` is the whole effect**: the ascending form of the shipped
  columns is used and still sorts, so the pin is a *negative* one and `Expect` gained a
  `forbidden` field.

- **A-2's cache was the premise, and the premise was false.** W16.1 was scheduled behind
  W14.3's cached `Vec<Branch>` because the read side would need the rows where it used to
  need three aggregates. Loading **all 17 rows costs 9.6 µs against the three-aggregate
  `SELECT`'s 10.4 µs** — the cost was the round trip and never the payload. The rows arrive
  for less than the answer they replace, and the read side gained no cache to keep coherent.

- **The bound `VALUES` ancestry is not a constant, and it crosses.** [D-219] had measured
  the recursive CTE as flat, so portability was the only argument. Joined the way the readers
  join it: **−53% at fork depth 1**, −24% at 8, **+8% at 16**, crossing near **depth 13**.
  The +8% surfaces nowhere through the public API — by the time a read is a traversal it is
  0.02% of it.

- **`build()` opens nothing.** Three documents named `libsql::Builder::…build()` as the open
  and as R15's exposure — the method's own rustdoc, the binding's mutex justification, and
  the probe's docstring — each drawing a right conclusion from a wrong mechanism. It costs
  **0.10 µs** and succeeds against a path that does not exist; `connect()` is **51.5 µs of
  an 82.7 µs call** and is where `SQLITE_CANTOPEN` arrives. R15 re-measured across four
  shapes at width 48: **3/30 per call, 0/30 with one connection** — locating the race past
  *two opens at once*, at minting against the use of connections already out.

- **One pragma through the side door ends the process.** [D-257] bounded its unreachable
  residue as *"cannot change any typed answer"*. Seven pragmas measured, one process each:
  six hold, and `PRAGMA hard_heap_limit = 1` leaves the whole process unable to write, read,
  `checkpoint()`, `close()`, or **open an unrelated database file**, permanently, all
  reporting `out of memory`. `SQLITE_OPEN_READ_ONLY` is no obstacle, because setting it is
  not a write to the file. Re-measured against the 0.15.13 per-call shape the outcome is
  identical, so it is not a cost of sharing and no hygiene reaches it. It belongs with the
  `ATTACH` warning [D-091] has carried from the beginning: both are properties of arbitrary
  SQL, not of the flags. Documented rather than blocked — matching SQL text does not survive
  whitespace or a comment, and would do nothing for a Rust caller holding the connection.

- **The concept caveat D-259 shipped describes a state that cannot exist** (D-260).
  `concepts.id` is `NOT NULL UNIQUE` and `trg_concepts_cross_lineage` refuses the collision
  by name, so four of the five routes to two visible lineages holding one concept id are
  refused by the schema, and the fifth reaches no reader. The tie-break the caveat named was
  not the code's either: the outer select carries no `ORDER BY`. A caveat that overstates a
  hazard is not conservative — it tells a reader to distrust a correct answer. Superseded
  rather than edited, under Doctrine III.

- **The ceiling has to go inside the recursion, and the plan's own sketch repeats the bug.**
  A `LIMIT` on the walk's outer `SELECT` sorts, and a sort materialises the whole walk first.
  On a 20,050-edge hub graph: **outer `LIMIT 20` visits 20,050 edges; `LIMIT 20` inside the
  CTE visits 7,250**.

## Documentation and gates

- **`tests/api_growth_tests.rs`** registers all twenty-nine public types with the reason in
  the entry, and asserts four properties against the checked-in surface. It caught that
  `ConceptUpsert` and `ReadPlan`, attributed releases ago, had never had their
  setter-per-field contract checked. It replaces a canary this cycle had to kill:
  `tuning_tests` constructed `Tuning` by literal.

- **Seven new Rust test targets** — `actor_state_tests`, `api_growth_tests`,
  `archive_projection_tests`, `read_plan_tests`, `reconstruct_on_tests`,
  `rehydrate_lineage_tests` and `walk_limit_tests` — plus a shared `tests/common/`
  harness, and
  **eleven new probes** under `examples/`, each the evidence for a register entry rather
  than a benchmark.

- **`docs/architecture/api-review-0.16.0.md`**, the pre-1.0 surface review C-11 asked for.

- **Mutation testing, everywhere it decided something.** Nine mutations for the walk ceiling
  (the survivor was `AtLeast(probe_cap)` for `AtLeast(ids.len())` — a number nothing
  counted); nine for the rehydrate refusal, two of them caught by a test written four
  releases earlier; six for the guard's lowering; five for `ActorState`, two of which
  required rewriting the test that was supposed to catch them; four for the reach guard's
  reordering. The C-13 regression test was found the same way — the guard replaced by `if
  false`, and the test watched to fail.

- **Two tests passed for years without testing what they were named for**, both found in
  W16.1 and both now pointed at the thing. The cold-arm test never reached the cold arm:
  with an archive present, reach is `NeedsArchive` only when the newest hot stamp is *after*
  the instant asked for, so a read at "now" takes the hot arm however much was archived —
  proven by panicking inside the cold builder and watching the test pass. Re-pointed at an
  early instant it immediately caught a real `ambiguous column name: branch_id`.

- **A comparison that had already decided a design was re-run on request and found to have
  three faults**: the two shapes were timed in different processes against different builds,
  nothing checked that "snapshots on" actually wrote a snapshot, and nothing checked the two
  shapes returned the **same answer**. The probe now rebuilds both from public parts, runs
  them alternately in one process, asserts equality edge for edge, and counts snapshot files
  before quoting a number. **The conclusion held.** It is recorded that it need not have.

**Item 10 was the honest hole in this note, and closing it was worth more than ticking it.**
It stood written as *not met* through two releases, because a green local suite on one
operating system is not what the criterion asks for. When the run finally happened it did
not confirm a clean tree — it found three things, and every one was a gate that could not
see what it was for ([D-263]). **The fuzz crate had not compiled since 0.15.13**: `fuzz/` is
a second workspace no local gate reaches, and [D-255]'s `#[non_exhaustive]` sweep is
refused only *outside* the defining crate, so nine releases of green in-crate builds said
nothing about it. **Nine rustdoc `-D warnings` errors had accumulated**, including a link
to a constant that has never existed, behind a local gate that exists, works, and was being
run in a form — bare `cargo doc` — where its errors arrive as warning lines and a steady
warning count reads as a baseline. **The Windows retry budget was a number with no Windows
measurement behind it**: 3/3 crashed with [D-147]'s signature and zero named failures, where
the local release gate has used eight since 0.12.0. All three are fixed and all three now
have a gate that runs without anyone remembering to run it.

**Two numbers that only this run could produce.** The Windows suite passed on **attempt 7
of 8** — the budget raised at 0.15.21 is what stands between this criterion and a red job,
and the margin is one attempt. And **R15 was not observed on macOS**: `ci.yml`'s own comment
has said since 0.8.0 that the Apple-silicon rate is *unknown, which is not the same as
knowing it is absent*, and both macOS steps completed on attempt 1. Two data points, one
run, and neither was available from this branch before 0.15.20.

## What is not closed

Three of the review's thirty items remain, and all three are on the plan's "ongoing, not a
release" list by decision rather than by omission. **C-23 was the fourth and is closed**
at 0.15.20 ([D-262]) — see acceptance item 10, which is where it stopped being a
convenience and became the thing this note was waiting on.
- **A-4** — `temporal/archive.rs` was 1,385 lines and is now **1,869**. The split into four
  modules did not happen, and the file grew by a third while its contents were being
  corrected. This is the one item the cycle made worse.
- **A-5** — no lineage property generator, and no cost visibility on the budget-exempt kinds.
- **A-6** — Python's `close()` can still be held off indefinitely by a hot read loop.

The `C-` numbering above is the 0.15.0 review's, not §14.1's. §14.1's own carry table
is untouched by this cycle: it closed at 0.15.0 but for `cargo-semver-checks`, which is
named for adoption **at** 1.0 rather than declined, because it wants a released baseline
to compare against ([D-211]).

on one Windows box **and on three CI runners**, run `34026632327`). At 0.15.0 those figures were 637 / 618 / 559, so the cycle added **108
Rust tests and 33 Python tests** — and the 19-test gap between the two Rust figures is
unchanged and still enumerated rather than subtracted.

**The second figure is a CI gate from 0.14.24** ([D-241](../architecture/s13-decision-register.md#d-241)):
it is *run* on ubuntu rather than merely compiled, because until then nothing in this
repository could falsify it. The three `property-tests` binaries run as their own quarantined
step, non-blocking since 0.14.19 (D-236) and reporting a four-state verdict rather than an
exit code. **R15** ([D-147](../architecture/s13-decision-register.md#d-147)) is attributed
per the documented protocol rather than retried away — an intermittent libSQL
`0xC0000005` on cumulative distinct-database `connect()` volume, which does not raise and
kills the process. It was loud during this release: the feature-off figure above took three
runs of eight attempts, killing a different target each time, and each named target passed
cleanly when run alone, which is the documented signature of the crash rather than of a
failing assertion. `scripts/run_rust_suite.py` exists to tell those two apart, and a bare
`cargo test --no-default-features` still cannot — it stops at the first crash and reports
the partial count as the total.

**CI confirmed the shape and put a number on the platform split** ([D-263]). On the same
commit, the main suite completed on **attempt 1 of 3** on ubuntu and macOS and on **attempt
7 of 8** on Windows, with six crashes first — `analyze_tests`, `storage_boundary_tests`
three times, `diagnostic_conn_tests`, then two at once — and zero named failures anywhere.
The quarantined property step completed on attempt 1 on both ubuntu and macOS, **768 across
61 targets**, and returned `crashed-R15` at 6/6 on Windows with zero named failures, which
is [D-236]'s read and the reason that step is non-blocking. R15 is a Windows fault, and
there is now evidence for the second half of that sentence as well as the first.
