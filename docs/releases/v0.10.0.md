# Macrame 0.10.0 — a disarm switch nobody was watching, and a complexity claim that was wrong for four releases

**Crate `macrame-db` 0.10.0 · wheel `macrame-db` 0.10.0 · schema v10, unchanged**

*Every wave has landed. Crate and wheel are at 0.10.0; schema stays at v10.*

**No schema rung.** A 0.9.0 database opens under 0.10.0 with no migration, no
rebuild, and no trigger swap — unless it is carrying the condition below, which
is the one thing this release will refuse to open.

---

## Read this first: 0.10.0 refuses a database that 0.9.0 would have opened

If a table named `macrame_archive_session` is present in your database as
committed state, `Database::open` now fails with a new error,
`ArchiveSessionLeaked`.

**This is not a false alarm and it is not a schema problem.** That table is how
Macrame tells its own delete guards that an archive is in progress. While it
exists:

* physical deletes from `concepts`, `links` and `transaction_log` are
  **permitted** — all three guards evaluate their condition to false;
* concept inserts write **no `transaction_log` row** — the ledger silently stops
  recording them.

Doctrine IV and Doctrine V are both suspended, with no error and no counter. A
database in this state has been accepting deletions the ledger exists to forbid.

**An archive cannot leave it behind.** Both archive paths create and drop the
table inside a single transaction, so a commit removes it and a rollback
discards it; there is no crash that strands it. If you are seeing this error,
something created the table outside Macrame's write actor.

**What to do.** The error message carries both halves:

```sql
DROP TABLE macrame_archive_session;
```

Then audit for deletions and missing log rows since the table appeared.
Dropping the table re-arms the guards; it does not undo what happened while they
were off, and that is the part worth your attention.

**This detects, it does not prevent.** A writer holding a raw connection can
still create the table and use it for the life of that process — the schema has
no way to forbid a table's existence. What 0.10.0 changes is that the condition
can no longer survive to the next open unnoticed. Recorded in
[§4.7](../architecture/s4-schema.md#47-what-this-schema-does-not-enforce) as a
fourth row rather than as a closed gap
([D-135](../architecture/s13-decision-register.md#d-135)).

### The API break

`DbError` is not `#[non_exhaustive]`, so a new variant is a breaking change for
any caller matching exhaustively. That break is why this is 0.10.0 and not
0.9.1. Python gains `ArchiveSessionLeakedError`, under `IntegrityError`.

## The single-assertion budget was never O(out-degree), and nine places said it was

§9 published a caveat on the single-edge-assertion row — *not met at high
out-degree* — that has been false since 0.5.6, when `idx_lc_open_interval`
shipped as the `v5 → v6` rung. It survived four minor releases and one
deliberate review that considered dropping it and declined
([D-127](../architecture/s13-decision-register.md#d-127)), because nothing had
ever measured it.

`overlap_guard` — a bench that already existed and had never been run for
publication — now measures the assertion into tables of increasing size:

| edges in table | hub out-degree | median | vs. `control/select_1` |
|---|---|---|---|
| 0 | 0 | 983 µs | 647× |
| 2,000 | 666 | 920 µs | 597× |
| 8,000 | 2,666 | 882 µs | 577× |

Flat. Median of three sessions; the control read 1.521 µs across them.
The two columns differ because the fixture is a chain of stars, in which the
probed hub is the source of a third of the edges — the same fixture, and the
same relationship, as D-059's own "8,000-edge hub".
The caveat is retired and the nine documentation locations are corrected
([D-134](../architecture/s13-decision-register.md#d-134)).

**These are a shape, not a decimal.** Session-to-session spread on this path is
~11%, and normalising by the control does not remove it — the same arm reads
736× / 693× / 647× across sessions. Read them as *sub-millisecond and flat*, not
as three-digit figures.

**The real cost is O(version count per edge key)** — the number of intervals
recorded for one `(source, target, edge_type)`, which archival caps. That
property governed a published budget while living in exactly one rustdoc
comment; it now has a register entry.

### One number that got *worse* on inspection

§9 and `chunk_rows::EDGES` both published **47.7 ms** for a 90-row edge chunk
into an 8,000-edge table, and attributed it to the index defect. That figure is
the **pre-index** measurement, left in place after the index shipped in 0.5.6.

It is now **9.06 ms, measured** — two sessions at 9.08 and 9.05, against
empty-table arms of 2.69 and 2.65 ms beside them
([D-136](../architecture/s13-decision-register.md#d-136)). The budget is 3 ms,
so the row is missed by ~3× rather than 16×, and the residual is recorded as
**unattributed**: it is not the missing index, and nothing has measured what it
is.

This needed a new bench arm. `chunk_budget` seeds concepts and no links by
design, so until 0.10.0 nothing in the suite wrote a chunk into a populated
table — the replacement figure was, briefly, as unfalsifiable as the one it
replaced.

### A correction to the table above, made before release

The `overlap_guard` arms are labelled by **edges in the table**, and an earlier
draft of these notes published them as out-degrees. The fixture is a chain of
stars in which the probed hub is the source of a third of the edges, so the
arms are out-degree 0 / 666 / 2,666 rather than 0 / 2,000 / 8,000.

The conclusion is unaffected — out-degree still rises by thousands with no
change in latency — but the figure "measured at out-degree 8,000" was wrong by
3× and appeared in nine places. All are corrected. D-059's own "8,000-edge hub"
means the same thing, which is what keeps the two comparable.

## The Python diagnostic path is bounded to one open at a time

`diagnostic_query` and `explain` are the only methods on the handle that open
the database file — every other call runs on connections established at `open`.
`block_on` releases the GIL, so threads sharing **one** handle were reaching
libSQL's concurrent-open fault without ever calling `open` twice, which is the
opposite of what the binding's own guidance implied.

Measured at width 48, 18 runs per arm:

| arm | bad runs | how |
|---|---|---|
| before | **7 / 18** | 2 × `0xC0000005`; 4 × `database is locked`; 1 × `bad parameter or other API misuse` |
| after | 0 / 18 | — |

Most failures came back as a *returned* `EngineError` rather than a crash —
which is worse-shaped here, because a survivable error on `diagnostic_query`
reads as a fact about the database, on the surface you reach for when the typed
answer is already in doubt.

**This bounds R15; it does not fix it.** The fault is upstream in libSQL 0.9.30
and is not this crate's to close. `Database::open` from many threads is
unchanged, the README's Known Risks row stays exactly where it is, and the Rust
`Database::diagnostic_conn` is **documented rather than locked** — its rustdoc
promises the connection is the caller's own, and a hidden queue would make that
false. Rust callers get the numbers and the advice
([D-138](../architecture/s13-decision-register.md#d-138)).

`ATTACH` was probed at the same time, because it is the one statement that opens
a second database on a connection documented as read-only. It inherits the
flags: writes into an attachment are refused, and a nonexistent path is
`SQLITE_CANTOPEN` rather than a new file. No back door
([D-137](../architecture/s13-decision-register.md#d-137)).

## Published performance claims now have a tripwire

The drift above was invisible because **nothing gated prose against
measurement**. `tests/perf_claim_tests.rs` inverts it, on the pattern
`index_plan_tests` established for indices: a registry keyed by the thing being
claimed, where a claim without its justification is a red test.

It does **not** assert any number is correct — [D-055](../architecture/s13-decision-register.md#d-055)
rules that out and [D-070](../architecture/s13-decision-register.md#d-070)'s
session noise is why. It asserts that every published claim is traceable to a
bench that exists and a decision that ratified it, and that one fact is not
published as two numbers.

The key is `(operation, fixture, metric)`. The fixture is in there because the
dry-run — required before any test code — found the two-part key would have
gone red against *correct* documentation: `224 µs` and `983 µs` are both the
single assertion's median on different fixtures, as are `2.39 ms` and `9.06 ms`
for the chunk row ([D-139](../architecture/s13-decision-register.md#d-139)).

Sixteen entries, six tests, and each gate was made to fail before being
trusted.

The sixteenth entry and the sixth test were not planned. Registering the 0.10.0
column's chunk-commit figure put **2.39 ms** and **2.71 ms** under one key and
the one-value rule went red — correctly, on its first real drift. The fix was
not to split `metric` until they stopped sharing a key, which would have passed
the test by hiding what it detected; `Status::Contested` keeps the key, records
the conflict, and names who reconciles it
([D-141](../architecture/s13-decision-register.md#d-141)).

## What has not changed

* **No schema rung.** Schema v10, same as 0.9.0.
* **R15 is not fixed.** The upstream libSQL access violation on concurrent
  database opens is unchanged. 0.10.0 neither fixes it nor narrows it; the
  existing mitigations (`RUST_TEST_THREADS=1`, the run classifier, the
  feature-gated property tests) are what they were.
* **`--all-features` is no longer published as a test configuration.** It is
  `metrics` + `property-tests` together, which puts the R15-prone binaries back
  inside the main run. Measured: 4 of 4 runs crashed at one attempt, 4 of 5
  still red at the six-attempt retry budget. The count is dropped rather than
  gated ([D-140](../architecture/s13-decision-register.md#d-140)); the two
  supported configurations are unchanged.
* **The performance budgets are still not CI gates**
  ([D-055](../architecture/s13-decision-register.md#d-055)). An absolute
  threshold asserted on a shared runner is an assertion about the runner.
