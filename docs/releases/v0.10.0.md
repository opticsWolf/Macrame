# Macrame 0.10.0 — a disarm switch nobody was watching, and a complexity claim that was wrong for four releases

**Crate `macrame-db` 0.10.0 · wheel `macrame-db` 0.10.0 · schema v10, unchanged**

*Draft — waves W1, W2 and W3 have landed. W4 and W5 have not.*

**No schema rung.** A 0.9.0 database opens under 0.10.0 with no migration, no
rebuild, and no trigger swap — unless it is carrying the condition below, which
is the one thing this release will refuse to open.

---

## Read this first: 0.10.0 refuses a database that 0.9.0 would have opened

If a table named `macrame_archive_session` is present in your database as
committed state, `Database::open` now fails with a new error,
`ArchiveSessionLeaked`.

**This is not a false alarm and it is not a schema problem.** That table is how
Macrame tells its own delete guards that an archive is in progress. While it
exists:

* physical deletes from `concepts`, `links` and `transaction_log` are
  **permitted** — all three guards evaluate their condition to false;
* concept inserts write **no `transaction_log` row** — the ledger silently stops
  recording them.

Doctrine IV and Doctrine V are both suspended, with no error and no counter. A
database in this state has been accepting deletions the ledger exists to forbid.

**An archive cannot leave it behind.** Both archive paths create and drop the
table inside a single transaction, so a commit removes it and a rollback
discards it; there is no crash that strands it. If you are seeing this error,
something created the table outside Macrame's write actor.

**What to do.** The error message carries both halves:

```sql
DROP TABLE macrame_archive_session;
```

Then audit for deletions and missing log rows since the table appeared.
Dropping the table re-arms the guards; it does not undo what happened while they
were off, and that is the part worth your attention.

**This detects, it does not prevent.** A writer holding a raw connection can
still create the table and use it for the life of that process — the schema has
no way to forbid a table's existence. What 0.10.0 changes is that the condition
can no longer survive to the next open unnoticed. Recorded in
[§4.7](../architecture/s4-schema.md#47-what-this-schema-does-not-enforce) as a
fourth row rather than as a closed gap
([D-135](../architecture/s13-decision-register.md#d-135)).

### The API break

`DbError` is not `#[non_exhaustive]`, so a new variant is a breaking change for
any caller matching exhaustively. That break is why this is 0.10.0 and not
0.9.1. Python gains `ArchiveSessionLeakedError`, under `IntegrityError`.

## The single-assertion budget was never O(out-degree), and nine places said it was

§9 published a caveat on the single-edge-assertion row — *not met at high
out-degree* — that has been false since 0.5.6, when `idx_lc_open_interval`
shipped as the `v5 → v6` rung. It survived four minor releases and one
deliberate review that considered dropping it and declined
([D-127](../architecture/s13-decision-register.md#d-127)), because nothing had
ever measured it.

`overlap_guard` — a bench that already existed and had never been run for
publication — now measures the assertion across a 4,000× range of out-degree:

| out-degree | median | vs. `control/select_1` |
|---|---|---|
| 0 | 983 µs | 647× |
| 2,000 | 920 µs | 597× |
| 8,000 | 882 µs | 577× |

Flat. Median of three sessions; the control read 1.521 µs across them.
The caveat is retired and the nine documentation locations are corrected
([D-134](../architecture/s13-decision-register.md#d-134)).

**These are a shape, not a decimal.** Session-to-session spread on this path is
~11%, and normalising by the control does not remove it — the same arm reads
736× / 693× / 647× across sessions. Read them as *sub-millisecond and flat*, not
as three-digit figures.

**The real cost is O(version count per edge key)** — the number of intervals
recorded for one `(source, target, edge_type)`, which archival caps. That
property governed a published budget while living in exactly one rustdoc
comment; it now has a register entry.

### One number that got *worse* on inspection

The chunked-write row is unchanged in substance and more honest in wording. §9
and `chunk_rows::EDGES` both published **47.7 ms** for a 90-row edge chunk into
an 8,000-edge hub, and attributed it to the index defect. That figure is the
**pre-index** measurement; post-index the same chunk is **8.0 ms and flat**. The
budget is 3 ms, so the row is still missed — by 2.7× rather than 16× — and the
residual is now recorded as **unattributed** rather than blamed on a defect that
was fixed in 0.5.6. Nothing has measured what it actually is.

## What has not changed

* **No schema rung.** Schema v10, same as 0.9.0.
* **R15 is not fixed.** The upstream libSQL access violation on concurrent
  database opens is unchanged. 0.10.0 neither fixes it nor narrows it; the
  existing mitigations (`RUST_TEST_THREADS=1`, the run classifier, the
  feature-gated property tests) are what they were.
* **The performance budgets are still not CI gates**
  ([D-055](../architecture/s13-decision-register.md#d-055)). An absolute
  threshold asserted on a shared runner is an assertion about the runner.
